## 一、現況：數過的，不是估的

### 1.1 資料模型：42 個裡有 20 個是空殼

`packages/db/schema.prisma` 定義了 42 個 model。逐一在 `apps/web`、
`apps/ai`、`tools` 底下搜尋是否有程式真的讀寫它：

| 分類 | 數量 | 說明 |
|---|--:|---|
| 真的在用（有讀也有寫） | 20 | 全部落在「匯入 → 校對 → 入庫」這條路徑，加上登入與稽核 |
| 半成品（只讀或只寫） | 2 | 見 §2.3 |
| **純骨架（零引用）** | **20** | 有資料表、有遷移，**沒有任何一行程式碼碰過** |

零引用的那 20 個是：通知的三張表、教科書索引的四張表、課綱的兩張表、
評分量表的三張表、重複題的兩張表、家長綁定、系統設定、AI 預算計數器、
出版社、官方來源抓取紀錄。

換句話說，**通知、教科書索引、課綱對應、非選題評分量表、重複題偵測、
家長端——這六塊在資料庫裡看得到，在程式裡不存在。**

### 1.2 網頁端：7 個頁面、12 個 API

```
頁面   登入、改密碼、首頁（轉址）、題庫列表、匯入列表、新增匯入、匯入詳情
API    登入 / 登出 / 改密碼、健檢 ×3、匯入 ×6
```

`app/(admin)/` 是一個**空目錄**——路由群組建好了，裡面零個檔案。

前端不是靜態的：校對介面 `Review.tsx` 有 480 行、上傳表單 `Upload.tsx`
有 479 行，都是有狀態的 client component，防抖自動存檔、鍵盤快捷鍵、
拖放上傳都有。**但沒有 `components/` 目錄、沒有元件庫、沒有表單函式庫、
沒有狀態管理**——樣式是直接寫 class name 對著一份 `globals.css`。
這代表下一個畫面要從頭刻，第三個畫面也是。

### 1.3 AI 服務

`apps/ai` 13,726 行 Python、189 項測試，**完全不碰資料庫**（沒有任何
psycopg / asyncpg / SQLAlchemy）。它是一支無狀態的管線服務，所有
持久化都經過 `apps/web`。這個切法是對的，維持。

## 二、五個結構性欠債

這五項的共同點是：**現在補很便宜，愈晚補愈貴**，而且它們都不是
「還沒做的功能」，是「做法上的欠債」。我建議在寫任何新功能之前
先還掉。

### 2.1 沒有統一的租戶範圍過濾層

文件 05 階段 0 寫得很清楚：

> 權限的統一範圍過濾層必須在這裡建好，之後每個模組都會用到；
> 如果留到後面補，會變成散落各處的權限判斷，遲早出漏洞。

實際上沒有建。目前每一個查詢都自己帶 `tenantId`，資料庫層**沒有
row-level security、沒有 policy**。現在只有 12 個 API 路由，漏一個
還看得出來；等到 80 個路由，漏掉的那一個就是水平越權漏洞，而且
不會有任何錯誤訊息。

**這一項與白牌化直接相關。** 你說過之後要授權給其他補習班。文件 05
的法遵分析已經指出：一旦多家機構共用，`INTERNAL_USE_ONLY` 與
`UNVERIFIED` 這兩類內容的隔離**必須做到資料庫層**——因為 A 補習班的
詳解洩漏給 B 補習班，法律性質從「內部使用」變成「對外散布」，
評價完全不同。

現在做：約 1 人週。等到功能寫完再回頭做：要重寫每一個查詢，並且
沒有任何自動化方式確認有沒有漏。

### 2.2 知識點圖譜沒有建置路徑

文件 05 說知識點圖譜是「唯一一個不能延後的前置項」，因為匯入、
分析、智慧老師三個模組都依賴它。

實際上：`KnowledgePoint` 在程式裡**只被讀、從來沒被寫**。唯一的
資料來源是種子檔裡的 10 筆示範資料。沒有任何介面可以建立知識點、
沒有介面可以編前置關係、沒有環路偵測。

後果現在就看得到：匯入管線的標註階段會去 `knowledge_points` 做
pg_trgm 相似度比對，而那張表裡只有 10 筆——所以**標註階段實際上
是失效的**，它只會回報「找不到合適的候選知識點」。

而知識點圖譜的建置不只是寫程式：文件 05 估**每科 4 到 8 小時的老師
工時，11 個學科合計 44 到 88 小時**。這筆時間要排進去，不能假設
「系統做好之後老師自然會去填」。

### 2.3 知識點標註寫了但沒有人讀

`QuestionKnowledgePoint` 這張關聯表在 `lib/commit.ts:261` 被寫入
（而且是 `.catch(() => {})` 吞掉錯誤），**全 repo 沒有任何一行讀它**。

這代表能力分析的整個資料基礎現在是惰性的：題目與知識點的關聯有在
累積，但沒有任何東西消費它，所以也沒有任何東西會發現它是空的、
是錯的、或根本沒寫進去。加上 2.2 的知識點只有 10 筆，實際上這張表
現在幾乎是空的。

### 2.4 沒有前端基礎

沒有 `components/` 目錄。校對介面與上傳表單各自把按鈕、輸入框、
對話框、載入狀態、錯誤提示重刻了一遍。

剩下要做的畫面至少還有三十個（學生作答、成績、錯題、智慧老師、
班級管理、組卷、派任務、家長端、營運……）。**沒有共用元件的話，
第三十個畫面會跟第一個長得不一樣，而且維護時要改三十個地方。**
「使用體驗不佳」這一項多半就是從這裡來的。

現在建：約 1.5 人週（設計語彙已經在文件 15 定義過了）。三十個畫面
之後再統一：不會發生，因為那時候沒有人敢動。

### 2.5 AI 預算計數器是死程式碼

`AiBudgetCounter` 這個 model 零引用。實際的預算控制是在
`import-pipeline.mjs` 用 `AiUsageLog` 即時彙總算出來的。功能是好的，
但 schema 裡留著一張沒人用的表，下一個人會以為那是規範來源。

**要嘛用它，要嘛刪掉。** 這是小事，但這一類「schema 說一套、程式做
另一套」的地方會慢慢累積成沒有人相信 schema。

## 三、「商用可交付」是什麼意思

你要的是商用方案，不只是功能做完。這一節列的是功能清單之外的部分，
而它們的工時常被漏算。

系統的定位已經定案為**補習班的完整營運系統**（文件 00 v1.9），這句話
有一個超出工時的後果：**停機一天，補習班無法正常營運**。這不是教學
輔助工具的可用性要求。具體代表：

**備份與還原要演練過，不是寫過。** `deploy/scripts/` 底下有 `backup.sh`、
`restore.sh`、`verify-restore.sh`，腳本存在，但**從來沒有真的跑過一次
完整的「毀掉資料庫再還原回來」**。RTO 4 小時／RPO 15 分鐘的目標
在沒有演練之前只是一句話。

**監控與告警要有人收得到。** `deploy/monitoring/` 有設定，但告警送到
哪裡、誰值班、半夜資料庫滿了會不會有人知道——這些沒有定義。

**個資保存期限要真的會刪。** 文件 01 §16 定義了保存期限（作答至畢業後
兩年、稽核五年），**沒有實作**。到期不清理既違反個資最小保存原則，
也讓資料庫無限膨脹。這是法遵項目不是效能項目。

**退費試算是法遵功能。** 依短期補習班設立及管理準則第 24 條，退費比例
是法定的，**算錯會被告**。它需要法規版本控管與試算軌跡留存，測試
嚴謹度要比一般功能高一級。

**壓測要真的壓。** 300 人同時作答是規格上的目標，沒有測過。作答尖峰
是全系統最集中的負載，而且發生在最不能出錯的時刻。

**資安檢測要外部做一次。** 重點在水平越權（見 2.1）、檔案上傳、
提示詞注入這三類。

**Docker 從來沒有真的建起來跑過。** `deploy-check.mjs` 檢查的是設定檔的
正確性，不是「映像建得起來、容器起得來、服務彼此連得上」。

## 四、施工批次

工時單位是**人週**，假設開發者熟悉技術棧。每一批都標了**驗收條件**，
而且刻意寫成非工程師可以自己驗證的形式——「能不能做到某件事」，
不是「某個模組完成了」。

### B0 — 還債與地基（6 人週）

還掉第二節的五項欠債，加上真正的階段 0 缺口。

| 項目 | 人週 |
|---|--:|
| 資料庫層租戶隔離（RLS + 統一範圍過濾層 + 越權測試） | 1.5 |
| 帳號與班級管理：建班、編班、CSV 批次匯入學生、家長綁定、家長同意流程 | 2 |
| 知識點圖譜的建立與編輯介面（含前置關係圖形編輯與環路偵測） | 1 |
| 前端元件基礎（按鈕、表單、對話框、表格、載入與錯誤狀態、無障礙預設） | 1.5 |

**驗收條件**：櫃檯人員可以自己開一個班、匯入 30 位學生的名冊、綁定
家長帳號；數學老師可以自己建 20 個知識點並拉出前置關係；用 B 補習班
的帳號登入之後，任何一個 API 都拿不到 A 補習班的任何一筆資料
（越權測試自動化，每次部署都跑）。

### B1 — 題庫的人工路徑（4 人週）

現在題目**只能**經由 AI 匯入進題庫。文件 05 把「保留純手動建題的完整
路徑」列為最大技術風險的緩解措施——即使 AI 匯入完全失效，系統仍然
可用——而那條路徑不存在。

手動建題與編輯（涵蓋全部題型含混合題組）、數學式編輯與渲染
（含 KaTeX 的 mhchem 擴充，現在還沒裝）、題庫的複合篩選與全文搜尋
（pg_trgm 已裝、索引與介面沒做）、題目版本與 diff、知識點標註介面、
去重的複核介面。

**驗收條件**：老師在沒有任何 AI 的情況下，20 分鐘內可以建好一份
10 題的小考題目並標註知識點；輸入「三角函數」搜得到相關題目；
修訂一題時看得到改了什麼。

### B2 — 組卷與派任務（5 人週）

手動組卷與拖曳排序、藍圖自動組卷、任務派發（對象、時間、規則、
發布策略）、四種作業型態（測驗／練習／訂正／閱讀／繳交）、
繳交狀態機（未開始、進行中、已繳、遲交、補交、已批改、要求重做）、
班級矩陣視圖。

**驗收條件**：老師可以從題庫挑 20 題組成一份卷、派給兩個班、設定
開放時間與時限；老師在一個畫面上看得到「這班誰還沒交」。

### B3 — 學生線上作答（5 人週）

作答介面（題目導覽、計時、標記待複查）、離線暫存與同步、
**伺服器權威計時**、續考機制、自動交卷、分頁載入、無障礙、
手機響應式。

這是可靠性要求最高的一段。**離線與續考的測試必須做扎實**：拔網路線、
關瀏覽器、換裝置、時間到自動交卷，以及這些情況的組合。

**驗收條件**：學生用手機在 20–50 Mbps 的熱點下完成一份 40 題的考卷；
作答到一半關掉瀏覽器再開，進度還在、剩餘時間正確（以伺服器為準）；
50 台 iPad 同時作答不掉線。

### B4 — 客觀題評分與成績（3 人週）

自動評分（多選部分計分、選填的數學等價判定）、成績計算與呈現、
班級與全校統計、級分與五標換算（含小樣本）、成績發布流程、匯出。

**這一批的單元測試必須完整覆蓋**，它是全系統最不能出錯的部分。
至少要涵蓋：多選部分計分 `(n−2k)/n` 的所有邊界；選填的數學等價
（`1/2`、`0.5`、`2/4`、`0.50` 要判相同）；**級分換算的上限截斷**
`min(15, ceil(X/L))`（照抄定義敘述就會踩到的溢位）；各科滿分非 100
（社會 144、自然 128）；小樣本的三種策略切換。

**驗收條件**：交卷後 10 秒內看得到客觀題成績；隨機抽 20 份人工核算，
分數完全相同；老師可以匯出全班成績的 Excel。

> ### ▶ 里程碑 R1（累計 23 人週）：可用的線上測驗系統
>
> 到這裡，補習班可以真的拿去上課：建班、建題、組卷、派卷、學生作答、
> 出成績。**強烈建議在這裡停下來實際用兩到三週再往下**——後面每一批
> 的設計都會因為真實使用回饋而改變，先做完再改比較貴。

### B5 — 通知模組 T0（4 人週）

事件來源、模板、渠道抽象（站內／Email／LINE）、使用者偏好、
免打擾時段、送達狀態、重試與退避、批次發送。

**這一批是六處功能的共同相依**：作業催繳、錯題複習到期、成績發布、
老師批註回覆、家長週報、營運模組的到班離班通知。不先做一個統一的
匯流層，這六處會各自接一次 LINE API、各自實作重試，最後沒有一個
地方回答得出「這位家長今天收到幾則通知」。

LINE 的兩件實務要先算：Messaging API 超過免費額度後**按則計費**，
到班離班是每生每天兩則，數百人的量級不小；家長要主動加官方帳號
並完成綁定，**綁定完成率是這個功能能不能用起來的關鍵**，要設計成
櫃檯報名時當場掃碼，不是發一張紙讓家長回家自己弄。

**驗收條件**：作業截止前 24 小時，沒交的學生收到站內與 LINE 通知；
免打擾時段內不會送出；一則通知送失敗會重試並且看得到狀態。

### B6 — 解析與錯題（6 人週）

分層解析的生成與一致性檢核、多來源解析並存、AI 補充層、下架回退、
錯題佇列與狀態機、**四階段訂正排程**（階段 0 答錯後立即、有提示、
不計分；階段 1／2／3 分別隔 1／3／7 天、無提示、計分）、錯因由學生
確認、舉一反三、錯題本 PDF 匯出。

**「解析不足」是你訪談時說的第一個痛點，這一批直接對著它。**

錯題本 PDF 匯出單獨值得一提：台灣學生仍然大量使用紙本，把線上資產
接回既有的讀書習慣，投報率可能是全表最高的。

**驗收條件**：學生答錯一題，看得到分層解析與「為什麼其他選項是錯的」；
那一題自動進入錯題佇列，隔天提醒重做（重做而不是重看）；
連續三次答對才出本；可以把本週錯題印成一份 PDF 帶走。

### B7 — 智慧老師（5 人週）

狀態機、五階段提示設計、以老師自編解析作為教學依據的對齊、
硬性約束的系統層實作、變化題檢索、教學摘要回寫、串流回應、
安全與關懷偵測。

**這一批的品質高度依賴提示的迭代**，五週裡有相當比例是調校而非寫
程式。建議提早找幾位學生做真實測試。

守住一條：**不做「一鍵看答案」的捷徑**。先診斷、再引導、最後才解鎖
答案的狀態機是刻意的；任何捷徑都會讓整個教學設計失效，因為學生
一定會走捷徑。

**驗收條件**：學生說「我不會」，系統先問他卡在哪，而不是直接講解；
學生連續兩次答不出前置觀念時，會退回去補那個觀念；每位學生的
每日配額生效。

### B8 — 能力分析與教師端報表（5 人週）

BKT 實作與參數校準、IRT 批次估計、遺忘衰減、錯因分類、推薦演算法、
學生端分析介面（一句話結論加行動建議、熱力圖、雷達圖、趨勢）、
教師端班級分析、需關注學生偵測、教師首頁待辦聚合、題目品質回饋。

精熟判定要採文件 09 §4 的三項修正：門檻用「連續答對 N 題」而非
答對率、**分數只升不降**（否則學生不敢重練，而重練正是要鼓勵的
行為）、精熟會降級（學過會忘）。

**驗收條件**：學生看得到「你在三角函數是熟練、在對數是入門」，
以及「下一步該練什麼」；老師看得到全班在哪個知識點最弱；
「三週沒碰的觀念」會降級並提示。

> ### ▶ 里程碑 R2（累計 43 人週）：完整教學閉環
>
> 匯入 → 出題 → 作答 → 評分 → 解析 → 智慧老師 → 能力分析 → 錯題 → 再練。
> 到這裡，你訪談時說的兩個痛點（解析不足、AI 功能不好用）才算真的
> 被解決。

### B9 — 非選題 AI 評分（5 人週）

評分量表資料模型與編輯介面（`Rubric` 三張表現在是空殼）、官方評分
原則的結構化匯入、AI 量表草稿、雙評加仲裁、依據高亮、校準機制、
複核介面、申訴流程。

依科目排序：社會與自然的簡答申論先（2 週）、數學計算證明次之
（1.5 週，含 SymPy 步驟驗證）、國英作文最後（1.5 週，定位為練習
回饋工具而非正式評分）。

**驗收條件**：老師複核 30 份 AI 評過的簡答，同意率高於某個事先講定的
門檻（建議 85%）；每一分的給分都指得出答卷裡的哪一句；學生看得到
評分依據並且可以申訴。

### B10 — 教科書索引與細目表組卷（5.5 人週）

章節樹、AI 抽取目錄、與課綱映射、班級版本設定；雙向細目表組卷
（兩套認知分類法並存、矩陣介面、正向與反向、匯出）。

**這一批影響老師第一天的使用感受。** 台灣老師找東西的第一層索引不是
知識點，是「翰林第三冊第二課」。沒有這一層，老師打開系統找不到東西。

**驗收條件**：老師選「翰林 高中數學 第三冊 4-1」就列得出該章節的題目；
組卷介面是老師認得的矩陣（章節 × 認知層次），不是知識點配比。

### B11 — 自主練習與題目參數化（7.5 人週）

學生自選範圍組卷、四級呈現與精熟三修正、「距下一級還差多少」；
題目參數化模板語法、生成管線與驗證、AI 反推模板。

參數化**同時解決三個問題**：反作弊（每人數字不同就無從對答案）、
題庫枯竭、錯題重練時「同一題已經背起來了」。而且我們已經決定不做
監考 Client，參數化正好從另一個方向補上那個洞，**不需要學生安裝
任何東西**。

**驗收條件**：學生可以自己選「三角函數、中等難度、20 題」立刻開始練；
同一道參數化題目派給 30 個學生，30 份的數字都不同而且答案都算得對。

### B12 — 防作弊（4 人週）

L1 題目層（隨機題序與選項、分頁載入、浮水印）、L2 瀏覽器層（全螢幕、
焦點偵測、貼上記錄、多分頁與多裝置、心跳）、L3 行為分析
（**答案相似度分析**、作答節奏、文風比對）、誠信報告、複核與申訴、
告知與同意介面。

答案相似度分析是投報率最高的一項，重點是**比對錯誤答案而非正確答案**
——兩個學生都答對第 12 題不能說明什麼，但兩人連續五題都選同一個
罕見的錯誤選項，機率極低。純後端統計，零誤殺風險，因為它產出的是
「值得複查」的名單而不是指控。

守住一條：**系統絕不在考試中對學生發出作弊警告。** 誤判一次的信任
損失遠大於抓到十次的收益，異常一律走事後報告。

**驗收條件**：一場考試結束後，老師收到一份誠信報告，裡面是「值得
複查」的名單與理由；考試中學生沒有收到任何指控性提示。

### B13 — 家長端（3 人週）

每週自動報告（到班次數、完成任務、進步的知識點、需注意的地方，
用 LINE 推送而非要求登入）、親師留言、繳費與收據查詢介面。

原則：**只給趨勢不給排名**，預設隱藏班排校排。**家長不即時看到每一次
答錯**——學生需要一個可以安全犯錯的空間。

**未決事項**：家長能不能看智慧老師的對話。我的建議仍是「開放摘要與
安全警示、逐字對話不開放，並讓學生知道規則」，但這一項需要你決定。

### B14 — 補習班營運模組（20 人週，規格尚未撰寫）

到班離班刷卡與 LINE 通知、出缺席、請假與補課排程、排課與衝堂檢查
（班級／教室／師資三維）、繳費與分期、**法定退費試算**、續報與退班
預警、問班追蹤、教師鐘點與薪資、教室與設備資源、教材領用、
教育局 BSB 申報、定型化契約線上簽署。

**這一批要先寫規格**（估 1 人週），而且它會引進一個新角色
（行政人員／櫃檯），權限與現有六種都不重疊——角色一新增就牽動
權限矩陣與稽核設計，不是純粹加功能。

**到班離班通知是補習班的第一賣點**，家長付錢買的是安心。

### B15 — 打磨、壓測與導入（5 人週）

效能調校與壓力測試（模擬 300 人同時作答）、外部安全測試、
無障礙檢測（WCAG 2.1 AA）、**備份與還原的實地演練**、
**個資保存期限的自動清理**、監控與告警的接收端、使用文件與教學影片、
以及**實際導入的陪跑**。

最後一項常被低估。第一次全校使用一定會遇到沒預期的問題（某個瀏覽器
版本、某台電腦的網路設定、老師找不到某個按鈕），需要有人在現場。

### B16 — 白牌化（4 人週，可延後但要先決定）

多租戶的資料庫層隔離（B0 已打底）、租戶的品牌與設定、
授權與計費、跨租戶的內容隔離稽核、開放 API。

**要先決定的是 B0 的 RLS 做到什麼程度**，那個決定現在就要做。

### B17 — 升學輔導模組（29 人週）

規格已完整（文件 06、07）。S0 制度規則引擎與 S1 簡章抽取可以在 R2
之後與其他批次平行；S2 級分預測依賴 B8 的 `theta`；S4 繁星賽局建議
優先於 S3 個申落點（時序更早，而且是外部工具做不到的功能）。

**第一年的資料建置工時要另外算**：估 150 至 200 小時的人工作業，
需要熟悉升學業務的人而非開發者。

## 六、風險登記簿

依「後果嚴重度 × 現在的不確定性」排序。

**一、AI 抽取的實際準確率完全未知。**（最高風險）
八人週的匯入模組蓋在沒驗證過的假設上。文件 05 把驗證排在動工之前，
那兩週沒有發生，因為沒有金鑰。**緩解**：`tools/verify-ai.py` 已經
寫好，接上金鑰就能跑，先跑六頁看數字。若數學式辨識率或漏題率遠低於
預期，整個匯入模組的設計可能要改——**愈晚知道愈貴**。

**二、老師不願意使用。**（最高非技術風險，也是這類系統最常見的死因）
**緩解**：校對介面的體驗要做到位（如果校對比自己打字還累，老師寧可
不用）；在 R1 就進真實課堂；找一兩位種子老師共同設計。**B1 的手動
建題路徑是這一項的保險**——即使 AI 完全失效，系統仍然可用。

**三、考試日的系統故障。**（後果最嚴重）
系統定位是核心業務系統，停機一天補習班無法營運。**緩解**：考前檢查
清單、考試期間暫停背景任務、預備紙本應急方案，以及最重要的——
**在真正的大考之前先做小規模實戰演練**。

**四、知識點圖譜的建置工時被低估。**
44 至 88 小時的老師工時，而且在關鍵路徑上。**緩解**：先只做數學 A
（結構最清晰），驗證價值後再擴充；這件事可以與 B0 平行開始，
不必等程式寫完。

**五、範圍蔓延。**
這個系統的想像空間很大，很容易一直加功能而永遠上不了線。
**緩解**：嚴守 R1 的定義；文件 13 §9 那份「我建議不要做的」清單
（公開排行榜、遊戲化、視訊監考、即時作弊警告、過細的時間監控、
一鍵看答案）要當成真的約束。

**六、AI 成本失控。**
智慧老師是最大的持續成本項。**緩解**：配額（每組織月度上限、
每學生每日對話數）、超額時降級而非中斷、批次 API 用於所有不急的
任務、提示快取的刻意設計。

**七、水平越權。**
見 §2.1。**緩解**：B0 的 RLS，加上自動化的越權測試。

## 七、建議的下一步

**第一件事，跟寫程式無關：把金鑰接上跑 `tools/verify-ai.py`。**
六頁就好，先看數字。這是目前投報率最高的三十分鐘——它可能推翻
一整個模組的設計，而愈晚知道愈貴。

**第二件事：B0。** 五項欠債現在補要 6 人週，等到三十個畫面之後補
要三倍以上，而且 2.1 的越權風險會一直帶著。

**第三件事，可以與 B0 平行、由老師做：數學 A 的知識點圖譜。**
用試算表整理就好，之後匯入。這是唯一不需要等程式的工作，而且
它在關鍵路徑上。

**然後照 B1 → B2 → B3 → B4 走到 R1，停下來實際用兩到三週。**

## 八、上線前檢查清單

這一份是 B15 的驗收依據，但現在就該知道它長什麼樣。

**功能**：R1 到 R3 的每一項驗收條件都通過，且由**老師本人**驗證而非
開發者。

**AI**：實跑驗證報告存在且數字可接受；高信心題目的錯誤率經人工抽驗
30–50 題確認；非選題評分與人工評分的相關性量過。

**效能**：300 人同時作答壓測通過；50 台 iPad 在教室網路下同時交卷
不掉單；作答頁在 20 Mbps 熱點下首屏 3 秒內。

**可靠性**：完整的「毀掉資料庫再還原」演練做過並計時（RTO 4 小時／
RPO 15 分鐘）；監控告警送得到真人；考試期間的降級模式演練過。

**安全**：外部資安檢測完成（水平越權、檔案上傳、提示詞注入）；
`.env` 權限 600；`WEB_BIND` 是 127.0.0.1；備份加密金鑰不在對外容器裡。

**法遵**：個資蒐集告知與家長同意流程上線；保存期限自動清理實作並
測過；退費試算有法規版本控管與試算軌跡；著作權的權利聲明與範圍
強制生效；AI 生成內容有標示。

**無障礙**：WCAG 2.1 AA 檢測通過；語音朗讀與逐項無障礙開關可用。

**導入**：使用文件與教學影片完成；第一週有人在現場陪跑；
紙本應急方案準備好。

## 九、這份藍圖不包含的

**監考 Client 已決定不做**（文件 04 §6、文件 08）。省下 9 至 17.5 人週，
以及 Windows 程式碼簽章年費、Apple Developer 組織驗證、學生自備裝置的
安裝支援、作業系統每次大版本更新的回歸測試。

代價是防作弊止於瀏覽器層與行為分析，這使得 **B11 的參數化題目**與
**B9 的非選題評分**優先度提高——它們原本就在路線圖上，只是現在同時
扮演防作弊的角色。

若日後單獨需要「看得到人」，**第二鏡頭是可分離的**——它跑在學生手機
的瀏覽器上，不依賴 Client，約 2 人週加 TURN 部署。
