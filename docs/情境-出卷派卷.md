# 情境測試：數學老師第一次出一份段考卷並派給三個班

**受測者設定**：數學老師，帶高三忠（32 人）、高三孝（28 人）、高三仁（30 人）。
週三晚上八點坐下來出「第一次段考模擬」，25 題、100 分。
**忠班週五下午考、孝班與仁班週六上午考。另外有兩位學生要補考。**
題庫裡已經有大約 400 題數學題（前一份情境測試建的）。會用電腦，不寫程式。

**測試方式**：唯讀走查 v0.21.0 的程式碼，逐步模擬動線。**沒有修改任何程式。**

**與 `功能清單.md` 第十一節的關係**：那一節列的是「以為有、實際沒有」的功能缺口。
這一份列的是**組卷與派卷的實際操作成本、時間設定的心智模型、以及考前改卷子這種真實需求**。
重疊的只註記關聯，不重寫。第十一節的第 1 項（沒有題目編輯）、第 4 項（沒有能力分析）、
第 12 項（沒有監考 Client）、第 15 項（派出去不能加班、題庫不分頁）在這條動線上會被踩到，
但這裡只寫「踩到之後老師實際要怎麼辦」，不重述缺口本身。

## 步驟 1：`/papers`——建一份新卷子要填什麼

### 卡點 1｜科目下拉是全校 13 科，而且預設第一科

**你看到什麼。** 按「建一份新卷子」，展開兩個欄位：**卷名**（自動聚焦）與**科目**。
科目那一格已經填好了，寫著「國文」。底下一行小字：

> 科目建立之後不能改——已經挑進來的題目會對不上。

**你會怎麼想。** 「卷名打『第一次段考模擬 數學A』，科目……欸它預設國文？」
多數人會注意到並改掉。但這是一個**沒有理由存在的機會**。

**實際發生什麼。**
`papers/page.tsx:47` 查的是 `prisma.subject.findMany({ where: { active: true }, orderBy: { order: 'asc' } })`
——**沒有任何依授課科目的過濾**，所以安裝時種下的 13 科全部出現。
`NewPaper.tsx:14` 取 `subjects[0]?.id`，也就是 `order` 最小的那一科。

沒改掉的話按下「建立並開始挑題」，`api/papers/route.ts:63-64` 會回 403：
「你不是這一科的授課老師」。擋是擋住了，但那是**送出之後**才說的，
而且那句話對一個只是沒注意到預設值的人來說像是權限出了問題。

**嚴重度：難用。**（擋得住，不會出錯，只是把「不可能對」的選項擺在預設位置。）

**修法建議。** 下拉只列這位老師 `canEditSubject` 為真的科目（管理員與召集人仍列全部）。
只有一科時直接顯示成唯讀文字。這一頁已經有 `canEditSubject`（`lib/auth.ts:86`）可用。

### 卡點 2｜「考試說明」沒有地方填，而它本來要印在學生的作答畫面上

**你看到什麼。** 只有卷名與科目兩個欄位。沒有「注意事項」、沒有「作答說明」。

**你會怎麼想。** 「『本卷共 25 題，第 1–20 題單選、第 21–25 題選填，
不可使用計算機』——這句話要寫在哪？」

**實際發生什麼。** 這個欄位存在，一路做到一半：

| 層 | 狀態 |
|---|---|
| schema | `ExamPaper.instructions`，註解寫「**說明文字，會印在作答畫面最上方（「請以 2B 鉛筆…」這類）**」（`schema.prisma:1377-1378`） |
| lib | `createPaper` 與 `updatePaper` 都收（`lib/paper.ts:101`、`:129-132`） |
| API | POST 與 PATCH 的 zod schema 都收（`api/papers/route.ts:57`、`api/papers/[paperId]/route.ts:20`） |
| 建卷表單 | **沒有這個欄位**（`NewPaper.tsx:40-61` 只有 title 與 subjectId） |
| 改卷工具 | **沒有**。`PaperTools.tsx:50-53` 的「改名」只送 `title` |
| 學生作答畫面 | 資料傳到了（`lib/attempt.ts:964`、`:1097`），**但整頁沒有任何一處 render 它**（`grep instructions app/(app)/take/` 是空的） |

所以這是一條**兩端都斷掉**的線：老師填不進去，就算填進去了學生也看不到。

**嚴重度：會出錯。** 「不可使用計算機」這種話沒有地方寫，老師只好口頭講，
而週六早上考的孝仁兩班是另一個時段——口頭講的規則兩班不一定一致。

**修法建議。** 建卷表單加一個 textarea（`instructions`），
`PaperTools` 的「改名」改成「編輯卷頭」同時收兩欄；
作答畫面在 `paperTitle` 底下把它畫出來。三處都是十行以內的改動，lib 與 API 不用動。

## 步驟 2：`/papers/[paperId]`——從 400 題裡挑 25 題

畫面是左右兩欄：左邊「題庫」，右邊「這份卷子」。上面一排篩選：知識點、關鍵字。
（科目那一格不出現——數學不是合科，`page.tsx:146` 的 `scope.length > 1` 是 false。）

### 卡點 3｜只看得到最新 60 題，而且沒有第 61 題以後的路

**你看到什麼。** 左欄標題右邊一行灰字：

> 顯示前 60 題，請用篩選縮小範圍

底下 60 列。捲到底——**沒有「下一頁」，沒有「還有 340 題」**。

**你會怎麼想。** 「上個月匯入的那份翻譯本裡有幾題不錯的，怎麼找？」

**實際發生什麼。** `page.tsx:17` 定 `const PAGE = 60`，`:86-87` 是
`orderBy: { createdAt: 'desc' }, take: PAGE`。沒有 `skip`、沒有 cursor、
`searchParams` 只認 `q`、`kp`、`sub` 三個（`:35`）。

也就是說**題庫裡第 61 題以後的題目，只能靠「知識點」或「關鍵字」把結果壓進 60 以內
才看得到**。壓不進去的話——例如「三角函數」底下就有 80 題——那 20 題永遠不會出現，
而畫面上唯一的提示是那句「顯示前 60 題」，它不會告訴你被藏起來的有幾題。

`/bank` 的情況一樣（固定 `take: 100`，已在第十一節第 15 項），但 `/bank` 只是瀏覽，
這裡是**唯一的挑題入口**。

**嚴重度：阻斷。** 「從幾百題裡挑 25 題」這件事，系統只讓你看見最新的 60 題。

**修法建議。** 三選一，由易到難：

1. 最小：`take: PAGE + 1`，多的那一筆換成「還有更多，請用篩選」＋**符合條件的總數**
   （`prisma.question.count` 同一組 where）。至少老師知道自己漏了多少。
2. 加 cursor 分頁（`createdAt` + `id`）。左欄底部一顆「再載 60 題」。
3. 知識點下拉每一項後面加題數（一句 `groupBy`），讓老師知道哪個知識點值得點。

### 卡點 4｜篩選缺了老師實際用來挑題的每一個維度

**你看到什麼。** 兩格篩選：**知識點**（下拉）、**關鍵字**（輸入框）。

**你會怎麼想。** 「我要 20 題單選 4 分、5 題選填 4 分。單選在哪裡篩？」

**實際發生什麼。** `page.tsx:79-97` 的 where 只組得出三件事：
`subjectId`、`status`、以及 `q`（題幹 contains）與 `kp`（知識點）。
而 `select`（`:88-96`）明明取了 `type`、`difficulty`、`nationalCorrectRate`、`sourceRef`
四個欄位**畫在每一列的側註上**（`:216-220`），卻沒有一個可以拿來篩。

老師看得到「單選　配分 5　難度 0.62　全國答對率 48%　110學測」，
但要挑出所有單選題，只能用眼睛掃 60 列。

**嚴重度：會出錯。** 25 題的題型配比是段考卷的骨架。用眼睛掃 60 列去湊配比，
漏掉一題（例如放了 21 題單選）不會有任何提示——`setPaperStatus` 不看題型（見卡點 14）。

**修法建議。** 篩選列加三格，全部走現有的 GET 表單：題型（`type`）、
難度區間（`difficulty`）、來源（`sourceRef` contains，能打「110學測」）。
每一格都是 where 裡多一行。

### 卡點 5｜關鍵字搜的是原始碼，不是老師看到的字

**你看到什麼。** 一個叫「關鍵字」的框，placeholder 寫「題幹裡的字」。

**實際發生什麼。** `page.tsx:83`：

```ts
...(sp.q ? { content: { contains: sp.q, mode: 'insensitive' as const } } : {})
```

`Question.content` 存的是**混排原始碼**——`MathText` 要靠 `$…$` 才排得出式子
（`components/MathText.tsx:52`）。所以：

- 搜「橢圓」→ 找得到（中文在原始碼裡是原樣）
- 搜「x²/4」→ 找不到，原始碼裡是 `$\frac{x^2}{4}$`
- 搜「向量」→ 找得到題幹裡的，找不到**只出現在選項裡**的那些（`options` 沒有進 where）
- 搜「餘弦定理」→ 找不到只在**詳解**裡提到的那些

**嚴重度：難用。** 不會出錯，但搜不到的時候老師不知道是「題庫裡沒有」還是「搜錯了」。

**修法建議。** placeholder 改成「題幹裡的中文字（搜不到數學式）」——
一句話就把期待調對了。真的要做全文檢索是另一件事（`Question.embedding` 是
`vector(1024)` 而且 pgvector 已裝，見第十一節第 4 項）。

### 卡點 6｜題幹只看得到兩行，選項與答案一個字都看不到

**你看到什麼。** 每一列是這樣：

```
 12   設 f(x)=x³-3x²+2，則下列敘述何者正確？（甲）f 在 x=0 有極大值…
      單選　配分 5　難度 0.62　全國答對率 48%　110學測                      [加入]
```

第二行就被截掉了。**沒有展開、沒有點進去看、沒有 hover。**

**實際發生什麼。** 兩件事疊在一起：

1. `globals.css:1112-1116` 的 `.yz-pick__text` 是
   `-webkit-line-clamp: 2`。全站沒有任何地方解除它。
2. `page.tsx:88-96` 的 `select` **根本沒有查 `options`**，也沒有查
   `answerKeys` / `answerText` / `answerSlots`。所以就算解除夾行，
   選項與答案也不在資料裡。

右欄「這份卷子」是同一個 class（`Composer.tsx:116`），同樣夾兩行、同樣沒有選項。

也就是說：**老師從頭到尾沒有辦法在系統裡看到一整題。** 挑題是靠題幹的前兩行。
而數學題最常見的情況正是「同一組的變化題只差一個負號或一個指數」——
`page.tsx:211-213` 的註解自己就這樣寫。

配上第十一節第 8 項（校對介面改不了題型與選項）與第 1 項（入庫後不能編輯），
結果是**題目入庫之後，這個系統裡沒有任何一個畫面看得到它的選項與答案**。

**嚴重度：阻斷。** 出卷的核心動作是「讀這一題，決定要不要」，而讀不到。

**修法建議。** 左欄每一列加一個 `<details>`：收起來時維持兩行，
展開顯示完整題幹、選項、與**標準答案**（這是老師的畫面，不是學生的）。
資料只要在 `select` 裡多兩行（`options: { select: { label, content, order } }`、
`answerKeys`）。這一項與卡點 12、13 是同一塊資料，做一次三個都解決。

### 卡點 7｜看不出這一題上次段考用過沒有

**你看到什麼。** 已經在**這一份**卷子上的題目會標「已在第 3 題」，
底色也不一樣（`page.tsx:225`、`globals.css:1121`）。

其他什麼都沒有。上一次段考用過的題目，在這裡與從來沒用過的長得一模一樣。

**實際發生什麼。**

- `ExamPaperItem` 有 `@@index([questionId])`（`schema.prisma:1407`）——
  **這個索引就是為了「這一題被哪些卷子用過」而建的**。
- 全 repo 的 `examPaperItem` 查詢共 10 處，`grep -n "examPaperItem\.\(findMany\|findFirst\|count\)"`
  的結果全部帶 `paperId`（`lib/paper.ts:165/289/302/349/372/430/479`、
  `api/papers/[paperId]/items/route.ts:102/126`、`papers/[paperId]/page.tsx:70`）。
  **沒有任何一句是用 `questionId` 反查的。** 索引建了沒人用。
- `Question.responseCount` 與 `Question.correctRate` 永遠是 null
  （第十一節第 4 項），所以「這題我們班考過幾次」也答不出來。

**你實際會怎麼做。** 開第二個分頁到 `/papers/上次那份段考`，
把兩份的題幹前兩行人工對照。25 × 25 次比對，而且比對的是被夾成兩行的文字。

**嚴重度：會出錯。** 段考卷裡放一題上次剛考過的，是老師最怕的事之一——
背過答案的人分數會虛高，而那個異常在成績頁上看起來只是「這題答對率特別高」。

**修法建議。** 左欄每一列加一句側註：「**用過 2 次**（113上第二次段考、113上小考三）」。
一句 `examPaperItem.findMany({ where: { questionId: { in: 這 60 題 } }, include: { paper: ... } })`，
一次查完再分組——與 `countRecipients` 同一種寫法（`lib/assignment.ts:542`）。

## 步驟 3：配分——25 題湊到 100 分

### 卡點 8｜25 題要 25 次來回，沒有任何批次動作

**你看到什麼。** 右欄每一列右邊一個窄輸入框，裡面是 `1`。底下：

> 總分　**25**

**你會怎麼想。** 「25 題 100 分，每題 4 分。有沒有『全部設成 4 分』？」——沒有。

**實際發生什麼。** 預設配分是這樣來的：

- 匯入時 `lib/commit.ts:216` 寫 `score: c.score ?? 0`——AI 沒抽到配分就是 0。
- 加進卷子時 `lib/paper.ts:295`：`question.score > 0 ? question.score : 1`。

所以出版社題本（配分印在卷頭而不是每題旁邊）匯進來的題目，**25 題全部是 1 分**。

改的路徑一次只有一題：

- 前端：`Composer.tsx:133-142` 的 `onBlur` 送一題（`{ itemId, score }`）
- API：`api/papers/[paperId]/items/route.ts:77-80` 的 `Patch` 是一個 `z.union`，
  **兩種形狀二選一**——整份順序，或**一題**的配分。沒有批次形狀。
- lib：`setPaperItemScore` 只收一個 `itemId`（`lib/paper.ts:370`）

每一次 blur 之後 `send()` 會 `router.refresh()`（`Composer.tsx:76-78`），
而 `/papers/[paperId]` 是 server component：一次 refresh 重跑三個查詢
（items、bank 60 題、全部知識點）並在伺服器端把 60 題題幹交給 KaTeX 排一次
（`MathText` 沒有 `'use client'`，見該檔 `:15-19`）。

**25 題 ＝ 25 次 PATCH ＋ 25 次整頁重繪。**

**嚴重度：會出錯。**（單看是難用；配上卡點 9、10 就會真的掉資料。）

**修法建議。** 右欄標題列加一格「每題　[ 4 ] 分　`全部套用`」。
API 的 `Patch` union 多一種形狀 `{ scores: [{itemId, score}] }`，
lib 在同一個交易裡 `updateMany` 之後 `recalcTotal` 一次。
25 次往返變成 1 次，而 `recalcTotal` 的既有保證（同交易內重算）不變。

### 卡點 9｜一送出，25 個框一起變灰，Tab 連打不可能

**你看到什麼。** 你在第 1 題打「4」，按 Tab。畫面閃一下，
**25 個配分框同時變成灰色**，游標不在任何地方。再按 Tab 沒有反應。
一秒後恢復，但焦點已經掉到頁面最上面。你得用滑鼠去點第 2 題的框。

**實際發生什麼。** `Composer.tsx:132`：

```tsx
disabled={busy}
```

`busy` 來自整個 `Composer` 共用的一個 `useAction()`（`:61`），
所以**任何一題在存檔，25 題全部停用**。`Button` 也一樣（`components/Button.tsx:52`）——
25 組 ↑↓ 與「移除」跟著一起變灰。

而 `busy` 的持續時間是：PATCH 的往返（伺服器端是 `findFirst` ＋
`requireEditablePaper` 的兩次查詢 ＋ 交易內 `update` + `recalcTotal` ＋ `auditLog.create`，
共約 7 次查詢）加上 `router.refresh()` 觸發的整頁重繪。

（對照組：左欄的「加入」是**每一列各自一個** `useAction`（`AddQuestion.tsx:26`），
所以加題不會互相停用。同一頁上兩種做法。）

**嚴重度：會出錯。** 25 個數字要用滑鼠點 25 次、每次點完等一秒。
而「等一秒」在 iPad 上（README 說主力裝置是 iPad）加上網路是兩秒。

**修法建議。** 每一列各自一個 `useAction`（照 `AddQuestion` 的做法），
或者改成本地樂觀更新 + 單一 debounce 佇列。
最小的改法是把 `disabled={busy}` 拿掉、只留按鈕的停用——
配分是冪等的，重複送同一個值不會壞。

### 卡點 10｜存檔失敗時，畫面上仍然是你打的數字

**你看到什麼。** 什麼都沒看到。這就是問題。

**實際發生什麼。** 三行程式湊出來的：

```tsx
// Composer.tsx:131
defaultValue={item.score}        // ← 不受控的輸入框
// Composer.tsx:79-81
if (!ok) setList(items);          // ← 只還原 React 的 list，還原不了 DOM
// Composer.tsx:109
{error && <Note tone="error">{error}</Note>}   // ← 畫在整份清單的最上面
```

配分框是 **uncontrolled**（`defaultValue`，而且 `key` 是 `item.id` 所以節點不會重建），
所以存檔失敗時 `setList(items)` 還原得了順序，**還原不了你剛打進去的數字**——
它就留在畫面上。

而錯誤訊息畫在 `<ul>` 之前。你正在改第 22 題，畫面捲到清單下半部，
那句紅字在螢幕外。

最可能觸發的失敗正是這條動線上的事：**週五下午忠班一開始考，這份卷子就鎖住了**
（`requireEditablePaper`，`lib/paper.ts:562-578`）。老師在辦公室調配分，
每一次都失敗、每一次都沒看到訊息、每一個數字都留在畫面上。

唯一的線索是最上面那個「總分」（`page.tsx:112`、`Composer.tsx:180-186`）不會動。
它是對的——但要老師自己把 25 個數字加起來才發現對不上。

**嚴重度：阻斷。** 這是「畫面說成功、資料庫是舊值」，而且沒有任何提示。

**修法建議。** 三件都要：

1. 配分框改成受控（`value` + `onChange` 存本地 state），失敗時真的還原成伺服器值。
2. 錯誤訊息改成貼在**那一列**旁邊（`AddQuestion.tsx:43` 就是這樣做的）。
3. 失敗那一列標成紅框，直到重試成功。

### 卡點 11｜新加的題一律排到最後

**你看到什麼。** 挑完 25 題，你想把三題選填放到最後。
第 8 題要往後移 17 格 → 按 17 次 ↓，每一次畫面凍住約一秒。

**實際發生什麼。** `lib/paper.ts:302-308`：新題目的 `order` 是
`max(order) + 1`，一律接在最後。移動只有 ↑↓ 一格

`Composer.tsx:33-38` 的註解自己承認了這件事，並說「那件事可以之後再補一個
『移到第幾題』」——那個東西還沒有補。

**嚴重度：難用。**（會做完，只是慢。25 題的卷子調一次順序容易破百次點擊。）

**修法建議。** 那個註解裡寫的東西：每一列的題號改成可輸入的
`<input type="number">`，打「12」按 Enter 就送整份新順序。
伺服器端一行都不用改——`reorderPaperItems` 收的本來就是完整順序。

## 步驟 5：標記為「可派發」

### 卡點 14｜檢查只有兩項，而 25 題 25 分照樣通過

**你看到什麼。** 頁面上方一塊灰底提示：

**你會怎麼想。** 「25 分？……喔它把配分加起來了。可是它讓我派出去了。」

**實際發生什麼。** `lib/paper.ts:164-178` 只檢查兩件事：

```ts
if (n === 0) throw ...            // 沒有題目
if (paper.totalScore <= 0) throw ...  // 總分是 0
```

**大於 0 就過。** 沒有檢查的：

| 該檢查的 | 為什麼 |
|---|---|
| 總分是不是整數／常見值 | 25 題 25 分、97.5 分都通過。老師跟學生說「這份 100 分」，成績頁的得分率會用 25 當分母（`grades/[assignmentId]/page.tsx:236`） |

| 有沒有非選題 | `ESSAY` / `TRANSLATION` / 沒設 `scoringRule` 的 `SHORT_ANSWER` 永遠拿不到最終分數（第十一節第 3 項）。這裡是唯一攔得住的地方 |
| 題型配比 | 老師說「20 單選 5 選填」，實際 21 + 4 也一樣通過 |

`PaperTools.tsx:87-96` 的提示已經把 `itemCount` 與 `totalScore` 印出來了，
所以資料都在手邊——只是沒有拿它們說一句話。

**嚴重度：會出錯。** 這一顆按鈕是這條動線上唯一的閘門
（`PaperTools.tsx:12-18` 的註解自己這樣定位它），而它只擋掉「完全空白」。

**修法建議。** 這一顆按鈕改成一個確認視窗，把「這份卷子的體檢表」攤出來：

```
第一次段考模擬 數學A
25 題　總分 25 分
單選 20（各 1 分）　選填 5（各 1 分）
⚠ 總分是 25，不是常見的 100。確定嗎？
⚠ 有 25 題的配分是 1 分——匯入時沒有抓到配分的題目預設就是 1 分。
```

非選題那一項要更硬：直接列出「第 23 題是作文，交卷後不會有最終分數，
而系統目前沒有評分介面」。

## 步驟 6：`/assignments`——派給三個班

### 卡點 15｜三個班要派三份，而畫面沒有說

**你看到什麼。** 「派給誰」那一區是三個並排的勾選框：

> ☐ 高三忠（34 人）　☐ 高三孝（29 人）　☐ 高三仁（31 人）

三個都勾得起來。底下一句「最多 94 人」。

**你會怎麼想。** 「太好了，一次派給三個班。」——然後你想起忠班週五、孝仁週六。
「那時間怎麼設？」——**設不了兩個時間。** 一個任務只有一組 `openAt` / `dueAt`。

**實際發生什麼。** `Assignment` 的時間是任務層級的
（`lib/assignment.ts:63-76` 的 `AssignmentInput`），`AssignmentTarget` 只有
`classId` 與 `userId`（`lib/assignment.ts:663`）。**沒有 per-target 的時間窗。**

而且就算三個班同一時段，合派也還有一個代價：**成績頁分不出班級**。
`ClassStats.scores`（`lib/scoring.ts:587-589`）沒有 `classNames`，
`classStats`（`:646-704`）也沒有查 `ClassMembership`。
90 個人一張平表，依分數排序，沒有班別欄，也沒有分班的平均。
（`Recipient` 型別有 `classNames`（`lib/assignment.ts:419`）——那份資料算得出來，
只是成績頁沒有用它。）

所以正確答案是**三份任務**：忠班一份、孝班一份、仁班一份。
而畫面上唯一暗示這件事的是那三個勾選框——它們看起來正是在鼓勵你一次勾三個。

**嚴重度：難用。**（結論是對的，只是老師要自己推出來，而且推錯了要重來。）

**修法建議。** 兩件小的：

1. 勾了兩個以上的班時，在「時間」那一區上面加一句：
   「這三個班會共用同一組開放與截止時間，成績也會合成一張表。
   不同時段考、或要分班看成績，請分開派。」
2. 派完之後，任務列表那一列加一顆「**照這一份再派一次**」——
   帶入全部設定、只清空班級與名稱。它同時解決卡點 16。

### 卡點 16｜派完再打開，時間還是上一份的，班級卻被清掉了

**你看到什麼。** 忠班那一份派好了，畫面回到「派一個新任務」。
你按下去要派孝班——**表單裡開放時間還寫著「2026/07/31 13:30」、
截止時間還寫著「2026/07/31 15:00」**，而任務名稱是空的、班級一個都沒勾。

**你會怎麼想。** 「名稱要重打、班級要重勾……好，勾孝班，打『第一次段考模擬（孝）』，
派出去。」——**時間你沒有再看一眼，因為它看起來已經填好了。**

**實際發生什麼。** `NewAssignment.tsx:125-128`，送出成功之後只重設四樣：

```tsx

```

`openAt`、`dueAt`、`timeLimit`、`mode`、`allowLate`、`maxAttempts`、

（`:50-60` 宣告的那十個）**全部留著**。

**後果。** 週六早上九點，孝班 28 人加仁班 30 人打開任務，看到的是：

> 這份任務已經在 7/31 15:00 截止了

（`lib/attempt.ts:343-344`）58 個人坐在教室裡開不了卷。

**嚴重度：阻斷。** 這是這條動線上最可能真的發生的一次事故：
它需要的只是「派第二份的時候沒有重看時間」，而表單的設計正在鼓勵這件事。

**修法建議。** 送出成功之後把時間欄位一起清掉——與名稱、班級同一個等級。
真正該保留的重複輸入，用卡點 15 說的「照這一份再派一次」明確地做，
而且那顆按鈕開出來的表單要把時間欄位**標成待確認**（黃底、focus 在上面）。

### 卡點 17｜「開放／截止／作答時限」三者的關係沒有寫

**你看到什麼。** 三個欄位，三行提示：

| 欄位 | 提示 |
|---|---|
| 開放時間 | 留白代表立刻開放。 |
| 截止時間 | 留白代表不設截止。 |
| 作答時限（分鐘） | 從學生按下開始作答起算，由伺服器計時。留白代表不限時。 |

**你會怎麼想。** 「開放 13:30、截止 15:00、時限 90 分。」——三個都填了，看起來很合理。

**實際發生什麼。** `lib/attempt.ts:399-406`：

```ts
const bounds: number[] = [];
if (assignment.timeLimitMin) bounds.push(now.getTime() + assignment.timeLimitMin * 60_000);
if (assignment.dueAt && assignment.dueAt > now) bounds.push(assignment.dueAt.getTime());
const expiresAt = bounds.length ? new Date(Math.min(...bounds)) : null;
```

**截止時間會把作答時限砍掉。** 13:38 才點開始的學生，`min(15:08, 15:00)` = 82 分鐘。
他的畫面上就是一個 82 分鐘的倒數，沒有任何說明。
一場「90 分鐘」的考試，實際上每個人的時間都不一樣，而且沒有人被告知。

（這個 clamp 本身是對的——不然學生 14:55 開始還能寫到 16:25。
問題是它是三個欄位交互作用出來的結果，而三行提示各說各的，沒有一句把它們接起來。）

反方向的錯更糟：老師以為「時限管一切」，**截止時間留白**。
那時 `expiresAt = now + 90 分`，考試本身正常，但——見下一項。

**嚴重度：會出錯。**

**修法建議。** 三格底下加一行動態的白話摘要，隨著輸入即時更新：

> 學生可以在 **7/31 13:30 – 15:00** 之間開始作答，
> 每人最多寫 **90 分鐘**，但一律在 **15:00** 結束。
> 13:38 之後才開始的人，實際時間會少於 90 分鐘。

這一句在前端就算得出來（三個值都在 state 裡），不用改伺服器。

### 卡點 18｜預設「截止後開放」＋ 截止時間可以留白 ＝ 學生永遠看不到檢討

**你看到什麼。** 「解析什麼時候給看」預設就選著「截止後」，提示寫：

**實際發生什麼。** 兩個預設值撞在一起：

- `NewAssignment.tsx:60`：`useState('ON_DUE')`
- `lib/assignment.ts:131`：`releasePolicy: (input.releasePolicy ?? 'ON_DUE')`
- `dueAt` 是 optional，`normalizeWindow` 對「只有 openAt 沒有 dueAt」完全放行

```js
    return scoreOnly('這份任務設定為截止後開放檢討，但老師還沒有設定截止時間。' +
                     '想看逐題檢討與解析，請告訴老師。');

```

學生交完卷看得到分數，**永遠看不到逐題檢討與解析**。
訊息本身寫得很好（它明確說是設定問題、也說了去找誰）——問題在老師那一側：

- 首頁待辦（`app/(app)/page.tsx:244-325`）**沒有這一項**。
  它只列 MANUAL 沒放行的（`:191-198`、`:276-285`）。
- `releaseControl`（`lib/release.mjs:208-211`）第一行就是
  `if (assignment.releasePolicy !== 'MANUAL') return { applicable: false, ... }`，
  所以成績頁那一塊放行狀態**整塊不出現**。
- 任務列表的「開放 → 截止」欄會顯示「7/31 13:30 → —」，
  但那個「—」看起來只是「不設截止」，不像是壞掉。

**這個系統裡沒有任何一個畫面會告訴老師「你的學生看不到檢討」。**
他會在下週一被學生問。

**嚴重度：阻斷。**（對「線上出成績、顯示講解與解析」這個產品的核心承諾而言。）

**修法建議。** 兩層：

1. `createAssignment` / `updateAssignment` 在 `releasePolicy === 'ON_DUE' && !dueAt`
   時直接擋，訊息：「選了『截止後開放』就要有截止時間，否則那一刻永遠不會到。
   不想設截止時間的話，解析開放請選『交卷後』或『老師手動放行』。」
2. 首頁待辦補一項：「N 份考試的檢討永遠不會開放」，連到 `/assignments`。

```tsx
// NewAssignment.tsx:314
hint="正式考試選「截止後」，全班同時看到，先寫完的人不會洩題。"
```

這句話在**一個班**的範圍內是對的（`release.mjs:143-152` 的整段註解就是在講這件事）。
跨班考同一份卷子的時候它是錯的，而它是唯一一句在場的指引。

正確的設定是三份任務全部選 `MANUAL`，等仁班週六考完再到成績頁按放行。
**系統沒有任何地方提到這種做法**，而 `MANUAL` 在派卷表單上的標籤只寫「老師手動放行」，
連帶還有卡點 21 的誤解（老師以為 MANUAL 只擋解析、分數照給）。

**嚴重度：阻斷。**

**修法建議。** 兩層，第一層就夠擋住這一次：

1. 建立任務時，若這份卷子已經有**其他還沒截止的任務**，而這一份是 `ON_DUE`，
   就在送出後給一個警告（不擋，但要說）：
   「這份卷子還有 2 個任務要在 8/1 09:00 之後才考。
   這一份設定為『截止後開放』，代表 7/31 15:00 之後這一班就看得到全部的答案與詳解，
   而另外兩班還沒考。要避免的話，三份都改成『老師手動放行』，
   等最後一班考完再一起放行。」
   判斷只要一句 `assignment.findMany({ where: { paperId, id: { not: 自己 } } })`。
2. 卷子層級的「同卷任務」檢視：`/papers/[paperId]` 上列出所有用這份卷子的任務
   與各自的時間（與卡點 24 同一塊 UI），並在時間交錯時標紅。

### 卡點 28｜兩位補考的學生，兩條路都有代價，而系統不說是哪一種

**你看到什麼。** 週一要讓兩位學生補考。你面前有兩顆按鈕：
任務列表那一列的「調整」，以及「派一個新任務」。

**路 A：把忠班那份任務的截止時間改到週一。**

`AssignmentTools.tsx:176-183` 讓你改 `dueAt`，
`lib/assignment.ts:262-270` 在有人作答之後仍然允許改
（檔頭決定二明說「最常見的請求就是『再延一天』」）。改完存檔，成功。

**代價沒有人告訴你。** `maySeeResult` 是**即時**讀 `dueAt` 的
（`release.mjs:130`、`:140`），所以：

- 忠班 32 個人從週五 15:00 就看得到的逐題檢討，**在你按下儲存的那一刻消失**，
  變回「逐題檢討與解析要等 8/3 10:00 截止之後才會開放」。
- 而且那兩位補考生也還沒被排除在「開始作答」之外——
  任何一位忠班學生在週一之前都還能……不能，`maxAttempts` 是 1，他已經交過了。
  但**沒交過的人**（斷線卡住的那幾份被作廢之後）可以。

`AssignmentTools` 的 `dueAt` 提示只寫「要立刻結束這場考試，把它改成現在。
留白代表不設截止」——**沒有一個字提到它同時是解析的開放時刻**。

**路 B：另外派一份，個別指定那兩位。**

這條路是對的，而且系統支援得不錯：
`NewAssignment.tsx:33-36` 的註解就是為這個情境寫的，
`assignableStudentIds`（`lib/assignment.ts:643-650`）確保只能指定自己班上的人。
打兩個學號、按兩次「加入」、選同一份卷子、設週一的時間，派出去。

**代價也沒有人告訴你：**

- 兩份任務 ＝ **兩張成績表**。忠班 30 個人在一張、補考 2 個人在另一張。
  沒有任何畫面把它們合起來（`classStats` 是 per-assignment 的）。
- 補考那一份的**百分位與級分是在 2 個人裡算的**
  （`stats.scores` 的 `percentile`、`level` 來自 `gsatLevels`）。
  成績頁會顯示「人數不足」之類的話——那是對的，但老師要的是
  「這兩位在忠班 32 人裡排第幾」，而那個數字算不出來。
- 兩位補考生看到的班平均與同學不同。

**嚴重度：會出錯。** 路 A 有一個看不見的副作用，路 B 有一個說不出口的結果，
而畫面上沒有任何一句幫老師選。

**修法建議。**

1. `AssignmentTools` 的 `dueAt` 欄位，在 `releasePolicy === 'ON_DUE'` 時
   加一句紅字：「這一份設定為『截止後開放檢討』。往後延截止時間，
   **已經看得到檢討的 32 位學生會再次看不到**，直到新的截止時間。」
   判斷資料都在 props 裡（`releasePolicy`、`attempts`），純前端。
2. 補考的正解是路 B，所以把它做順：任務列表加「照這一份再派一次」
   （卡點 15 的同一顆按鈕），並在成績頁加一句「這份任務與『第一次段考模擬（忠）』
   用的是同一份卷子」的互相連結。

## 一位老師出一份 25 題的卷子並派給三個班，實際要花多久、點幾下

**設定**：數學 A，25 題 100 分，題庫裡約 400 題（六個章節），三個班分兩個時段考。
「一次點擊」＝ 一次滑鼠點擊或一次按鍵動作，不含打字的每一個字元、不含捲動。
「一次往返」＝ 一次伺服器請求，而在這一頁上**每一次都伴隨整頁 RSC 重繪**
（3 個查詢 ＋ 最多 60 題題幹的伺服器端 KaTeX 排版，`MathText.tsx:15-19`）。

### 逐段算帳

**A. 建一份卷子**

| 動作 | 點擊 | 往返 |
|---|---|---|
| 「建一份新卷子」→ 打卷名 → 確認科目 → 「建立並開始挑題」 | 4 | 1 |

約 **1 分鐘**。

**B. 找題與挑題**——這一段是最大的一塊

左欄一次只給 60 題（卡點 3），所以動線一定是「一個章節篩一次」。

| 動作 | 點擊 | 往返 | 時間 |
|---|---|---|---|
| 六個章節各篩一次（選知識點 ＋ 按「篩選」） | 12 | 6 | — |
| 讀候選題目：每輪掃 60 列 × 6 輪，每列 2 行、沒有選項、沒有答案（卡點 6）。粗估一半一眼跳過，另一半各花 3–5 秒 | 0 | 0 | **9–15 分** |
| 「這題上次段考用過沒有」——開第二個分頁比對上一份卷子的 25 題（卡點 7） | ~10 | ~2 | **5–10 分** |
| 按 25 次「加入」，每次一個 POST ＋ 整頁重繪 | 25 | 25 | **1–2 分**（純等待） |

小計：**47 次點擊、33 次往返、15–27 分鐘。**

**C. 配分**

匯入沒抓到配分的題目一律 1 分（`commit.ts:216` → `paper.ts:295`），
所以起手是「25 題、總分 25」。100 ÷ 25 ＝ 每題 4 分，25 個框打的都是同一個「4」。

不能用 Tab 連打（卡點 9：blur 一送出，25 個框一起 disabled，焦點掉光）。
所以每一題是：**點框（1）＋ 全選（1）＋ 打字（1）＋ 點空白處讓它 blur（1）＝ 4 次點擊**。

| 動作 | 點擊 | 往返 | 時間 |
|---|---|---|---|
| 25 題 × 4 次 | **100** | 25 | 每次要等一次往返，實測體感 0.5–2 秒 → **8–14 分** |

沒有任何批次動作（卡點 8：API 的 `Patch` union 一次只收一題）。

**D. 排序**

若接受匯入順序：**0**。
若要把 5 題選填排到最後（很常見）：每題平均往後移 6 格 → **30 次點擊、30 次往返、5–8 分鐘。**
（新加的題永遠排最後，`paper.ts:302-308`。）

**E. 檢查這份卷子**

沒有預覽（卡點 12）、不能自己試考（`assignment.ts:719-724`）、印不出來（卡點 13）。
所以這一段在系統裡是 **0 次點擊、0 分鐘**——因為做不到。

**要紙本考卷**：回去開原始 PDF／Word，把這 25 題重排一份。
**這一段完全在系統外，20–40 分鐘，而且是重工。**

**F. 標記為可派發**

1 次點擊、1 次往返。檢查只有「有題目」與「總分 > 0」（卡點 14）。

**G. 派三份任務**

每一份：

| 動作 | 點擊 |
|---|---|
| 「派一個新任務」 | 1 |
| 試卷下拉 | 1 |
| 任務名稱（打字） | 1 |
| 班級勾選 | 1 |
| 開放時間（`datetime-local` 五段：年月日時分） | 5 |
| 截止時間（同上） | 5 |
| 作答時限（打字） | 1 |
| 題序隨機 ＋ 選項隨機（預設沒勾，卡點 19） | 2 |
| 「派出去」 | 1 |
| **小計** | **18** |

× 3 ＝ **54 次點擊、3 次往返、10–14 分鐘。**

**H. 確認派對了**

系統只給一個數字（卡點 22）。要確認是**哪** 32 個人，得另開
`/classes/[classId]` 三次、人工數。**3–5 分鐘。**

### 總計

```
                                   點擊    往返    時間
A 建卷                                4      1     1 分
B 找題與挑題                         47     33    15–27 分
C 配分（25 題各打一次「4」）        100     25     8–14 分
D 排序（把選填排到最後）             30     30     5– 8 分
F 標記可派發                          1      1     ~0
G 派三份任務                         54      3    10–14 分
H 核對三班名單                        ~6     3     3– 5 分
                                   ────   ────   ────────
                                    242     96    42–69 分鐘
```

**中位數約 55 分鐘、242 次點擊、96 次伺服器往返（每一次都是一整頁重繪）。**

再加上**系統外的紙本**（20–40 分鐘），
以及步驟 8「第 12 題印錯了」的修補：

- 週四晚上（還沒有人作答）：移除 ＋ 找替代題 ＋ 加入 ＋ 按 12 次 ↑ ＋ 改配分
  → **約 20 次點擊、15 次往返、8–12 分鐘**
- 週五下午（忠班已經開始）：卷子鎖死，錯誤訊息叫你「另外建一份」，
  而沒有複製功能（卡點 25）→ **整段 B + C + F 重來，約 30–45 分鐘**

### 對照組

老師現在的做法：從上次的 Word 段考卷剪貼、改幾題、存成 PDF。
**40–60 分鐘，而且產出的直接就是可以印的紙本。**

### 結論

> **這個系統目前在「出一份卷子」這件事上，沒有比 Word 快，而且少了紙本。**
> 55 分鐘 ＋ 20–40 分鐘的系統外重工，換到的是一份看不到選項、
> 不能預覽、印不出來的卷子。
>
> 它真正省下的在後面：**派發與自動計分**。
> 90 個人 × 25 題人工改卷是 3–5 小時，這裡是 0。
> 那筆帳是划算的——但老師要先付前面這 55 分鐘，
> 而且在第一次用的時候，他還沒看到後面那筆回報。

### 瓶頸排序

1. **配分佔了 100 次點擊，是全部的 41%**（卡點 8、9）。
   一個「每題 N 分・全部套用」的按鈕，把 100 次點擊 ＋ 25 次往返
   變成 3 次點擊 ＋ 1 次往返。**這是投入產出比最高的一項。**

2. **挑題那 15–27 分鐘裡，大半花在系統沒有給的資訊上**
   （卡點 3、4、6、7）。看不到選項、看不到答案、看不到用過沒有、
   看不到第 61 題以後。加一個 `<details>` 展開與一句「用過 2 次」，
   這一段可以砍掉三分之一。

3. **紙本那 20–40 分鐘完全在系統外，而且是所有「印錯了」的來源**
   （卡點 12、13）。一頁 `/papers/[paperId]/preview` 同時解決預覽與列印，
   而它的資料層是零成本的（`items` join `question` 而已）。

4. **派三份要把同樣的設定打三次**（卡點 15、16）。
   一顆「照這一份再派一次」砍掉 36 次點擊，
   而且**順手消滅卡點 16 那個會讓 58 個人週六早上開不了卷的陷阱**。

## 這條動線上最該先修的三件事

不是按嚴重度排，是按「一改就同時關掉好幾個洞」排。

**一、`/papers/[paperId]/preview`（卡點 6、12、13）。**
一頁 server component，把卷子從頭到尾攤開：題號、完整題幹、選項、配分、
可收合的答案欄，加一份 `@media print`。
它讓老師第一次真的看見自己出的卷子，也是紙本唯一的出路。
資料層零成本。

**二、`releasePolicy` 那一格的三個洞（卡點 18、21、27）。**
- `ON_DUE` ＋ 沒有 `dueAt` 直接擋（否則學生永遠看不到檢討，而老師不會知道）
- 標籤統一成「成績與解析什麼時候給看」，選 MANUAL / NEVER 時說出「連分數都看不到」
- 同一份卷子還有未截止的任務時，`ON_DUE` 要出一句跨班洩題的警告

第三點是這份報告裡唯一一個**會讓考試本身失效**的問題，
而它現在的觸發條件是「照著表單的提示做」。

**三、派卷表單送出後把時間欄位一起清掉，並加一顆「照這一份再派一次」（卡點 16、15）。**
現在的行為是**清掉安全的欄位、留下危險的欄位**，
而三個班分兩個時段考是這個系統最基本的使用情境。
兩行程式碼加一顆按鈕。
