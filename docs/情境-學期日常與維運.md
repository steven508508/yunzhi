# 情境：學期日常與維運

**視角**：補習班主任兼維護者。系統上線三個月，200 位學生、7 個班、每科 3 位老師，
沒有 IT 人員。這份走的是**時間跨度**——那些第一天不痛、第三個月才痛的東西。

**與其他四份的分工。** `情境-裝機第一天` 走的是安裝到第一份卷子派出去；
`情境-建題庫`、`情境-出卷派卷`、`情境-學生應考` 各走一條當天完成的動線。
它們問的是「今天做得完嗎」。這一份問的是**「做了三個月之後會變成什麼樣」**，
以及**「半夜出事時我一個人處理得了嗎」**。

已經被 `docs/功能清單.md` 第十一節記過的缺口（沒有題目編輯、沒有能力分析、
沒有智慧老師、沒有通知、沒有家長端、姓名改不掉）在這裡不重述，只在它們
**因為時間累積而變成另一種問題**時才展開——例如「姓名改不掉」在第一天是小事，
在第三個月變成「兩百筆名冊裡有八個錯字而且永遠不會對」。

**判定方法。** 每一項都走到畫面上：不是「lib 有這支函式」，是「點得到那顆按鈕」。
所有結論都附檔案路徑與行號。部署腳本只讀不跑，`doctor.sh --help` 除外。

# 第一部：學期中的日常

---

## 1. 新生插班

**狀況。** 開學三週後來了 5 位新生，要進忠班。

**你會怎麼做。** 開 `/classes/[忠班]`，把 5 個人的 CSV 丟進「匯入名冊」，
試算、確認、抄下 5 組初始密碼、逐一登錄家長同意。

**實際上做不做得到。** 做得到，而且這一段是整個系統做得最好的地方之一。

`applyRoster`（`apps/web/lib/roster.ts:274`）對名冊上已存在的帳號只 upsert 班級關係、
不重建帳號（`roster.ts:305` 的 `findFirst`、`roster.ts:345` 的 `classMembership.upsert`），
所以丟一份 5 列的 CSV 進一個已經有 30 人的班，結果是加 5 個人，不是把班洗掉。
`planRoster`（`roster.ts:174`）會先告訴你「新增 5 個帳號、0 位已有帳號」。
一次 5 個人的 bcrypt 大約 1.8 秒，不會撞到 `maxDuration = 300`
（`app/api/classes/[classId]/roster/route.ts:33`）。

**但接下來兩件事沒有人告訴你。**

**（一）這 5 位新生立刻收到過去三週的每一份作業。**

`listStudentTasks`（`apps/web/lib/attempt.ts:1237`）的查詢是：

```
apps/web/lib/attempt.ts:1251-1264
  const memberships = await prisma.classMembership.findMany({
    where: { userId, leftAt: null, role: 'STUDENT' },
  ...
  const rows = await prisma.assignment.findMany({
    where: { targets: { some: { OR: [{ userId }, { classId: { in: classIds } }] } } },
```

**沒有任何一項比對 `joinedAt` 與 `assignment.createdAt`。** 只要班對得上，
這個班從開學以來派過的每一份任務都會出現在他的清單上。

三週、三科、每週一份 = 9 份。其中截止日已過而且不收遲交的，
`state` 會被算成 `MISSED`（`attempt.ts:1321-1322`），畫面上寫的是
「9/12 17:00 截止，沒有作答記錄。要補做請告訴老師。」（`take/page.tsx:219`）。

也就是說一位今天報到的新生，登入第一件事是看到 **9 個紅字的未交紀錄**。
還有一種更糟的：截止時間留白的任務（派卷表單的預設值，見 `情境-出卷派卷` 卡點 18）
`state` 會是 `OPEN`——他可以**現在去寫三週前的隨堂考**，而那份卷子的答案
全班已經檢討過了。

**（二）三週前那幾場考試的統計，今天被改掉了。**

`countRecipients`（`apps/web/lib/assignment.ts:542`）是**每次開頁即時算**的，
沒有任何快照。`/assignments` 的「派給」欄（`assignments/page.tsx:212`）
今天早上是 30，下午變成 35——而那是一場上個月就考完的段考。

同理 `resolveRecipients`（`assignment.ts:440`）是「這份任務派給了誰」的唯一名單，
B3 用它決定誰開得了考卷、B4 用它算應交人數。所以「應交 30、實交 30」的完美紀錄，
在插班生進來的那一刻變成「應交 35、實交 30」。

**嚴重度：會出錯。** 不會壞掉，但你的每一份歷史紀錄都會隨著名冊變動而漂移，
而漂移是無聲的。

**修法建議。**
1. `listStudentTasks` 加一道 `createdAt >= membership.joinedAt` 的過濾，
   或者在 `Assignment` 上加一個 `rosterSnapshotAt`，派發時凍結名單。
   前者一行，後者才是對的。
2. 名冊匯入完成後，如果這個班有 `openAt < joinedAt` 的任務，
   在成功畫面上直接列出來：「這 5 位會看到 9 份先前的任務，其中 2 份還可以作答。
   要讓他們免除，請到那幾份任務把他們個別排除。」——而個別排除這件事現在也做不到（見第 7 項）。

## 2. 學生轉班

**狀況。** 一位學生從忠班轉到孝班。同一科，同一個老師教。

**你會怎麼做。** 找「轉班」。沒有這個東西。實際要做的是兩步：
在 `/classes/[忠班]` 按他那一列的「移出班級」，
再到 `/classes/[孝班]` 匯入一份只有他一列的 CSV。

**實際上做不做得到。** 兩步都做得到，而且 `leaveClass`（`roster.ts:704`）
的確認視窗把後果寫得很清楚（`classes/[classId]/Membership.tsx:62-82`），
還會擋住「考試進行中把人移出」（`roster.ts:730-740`）。
`applyRoster` 對已存在的帳號只加班級關係，所以第二步不會重建帳號、不會產生新密碼。

**但有四件事。**

**（一）沒有人告訴你要做第二步。** 移出的確認視窗說「他的帳號本身不受影響，
如果他同時在別的班，那邊照常」——它沒有說「你現在要去另一個班把他加回去」。
只做第一步的結果是這位學生登入後看到「現在沒有任務」，而名冊上他不在任何班。
這是一個會發生的錯誤，因為兩步之間沒有任何連結。

**（二）他從此看不到忠班的檢討。** `listStudentTasks` 只認 `leftAt: null` 的班級
（`attempt.ts:1252`），所以移出的那一秒，他清單上忠班的每一份考試都消失了——
包含上週剛考完、老師剛放行解析的那一份。

資料還在。`listOwnAttempts`（`apps/web/lib/result.ts:153-179`）只比對
`assignmentId + userId`，**不查班級**，所以 `/take/[assignmentId]/result` 這個網址
還打得開。但沒有任何一頁會給他那個網址。這不是資料遺失，是**入口遺失**——
而對一個學生來說兩者沒有差別。

**（三）忠班那幾場考試的統計，今天又變了。** 與第 1 項同一個原因，方向相反：
`countRecipients` 把他減掉，於是三個月前那場段考的「派給 30 人」變成 29。
移出的確認視窗上寫著「全班統計照樣算他那幾份，你在成績頁上仍然看得到他」
（`Membership.tsx:66-67`）——這句話**只有一半是對的**：
`classStats`（`apps/web/lib/scoring.ts:646`）確實是照 `assignmentId` 查 attempts、
不查名冊，所以他的分數還在那張表上；但 `/assignments` 的應交人數會少一個，
而那兩個數字在不同的頁面上，沒有人會同時看到。

**（四）孝班的老師看不到他在忠班的成績——除非剛好同一科。**
`gradeScopeWhere`（`scoring.ts:903`）與 `teachingSubjectIds`（`scoring.ts:856`）
是**依科目**判定的，不依班級：

```
apps/web/lib/scoring.ts:903-907
  const mine = await teachingSubjectIds(user);
  if (mine === null) return {};
  return { OR: [{ paper: { subjectId: { in: mine } } }, { createdBy: user.id }] };
```

所以孝班的數學老師看得到全補習班每一份數學任務的成績，包含忠班的。
這解決了轉班的問題，但代價是**科目權限完全沒有班級邊界**——
一位只教孝班數學的老師，看得到七個班每一位學生的姓名、學號與分數。

**嚴重度：會出錯。** 每學期 5–10 次，每一次都留下一個對不起來的歷史數字。

**修法建議。**
1. 在班級頁的每一列加一顆「轉到其他班」，一個對話框做完兩步，
   而且把「他會看不到原班的檢討」寫在確認裡。
2. `listStudentTasks` 的班級條件從 `leftAt: null` 放寬成
   「`leftAt` 是 null，或這份任務的 `dueAt` 早於 `leftAt`」——
   離班之前考過的東西應該還看得到。這是一行 where。

## 3. 學生退補

**狀況。** 一位學生退費不來了。

**你會怎麼做。** 找「停用學生帳號」或「退補」。找不到。
班級頁上那一列只有兩顆按鈕：「重設密碼」與「移出班級」
（`classes/[classId]/page.tsx:179-189`）。

**實際上做不做得到。做不到。**

**帳號停不掉。** `/settings/staff` 的「停用」走 `setStaffStatus`（`lib/staff.ts:250`），
而它第一件事就是 `loadStaff`，那一支明確擋掉學生：

```
apps/web/lib/staff.ts:386-391
  if (!STAFF_ROLE_SET.has(user.systemRole)) {
    throw new Error(
      `「${user.displayName}」不是教職員帳號，這一頁動不了它。` +
        '學生帳號請到他所屬的班級頁處理。',
    );
  }
```

而班級頁上並沒有這個功能。這是一句指向空處的錯誤訊息。
`PATCH /api/staff/[userId]` 的 zod schema 只收 `systemRole` 與 `status`
（`app/api/staff/[userId]/route.ts:20-26`），就算繞過畫面直接打 API 也會被 `loadStaff` 擋。

**帳號刪不掉。** `User.deletedAt`（`packages/db/schema.prisma:135`）在全 repo
**只被讀、從來沒有被寫過**——十七處引用全是 `deletedAt: null` 的查詢條件
（`lib/assignment.ts:52`、`lib/staff.ts:90`、`lib/attempt.ts:1246`、`lib/auth.ts:50` 等）。
沒有任何 `deletedAt: new Date()`。

**所以你能做的只有「移出班級」。** 之後的狀態是：

- 帳號 `status` 仍然是 `ACTIVE`，密碼還能用，**他登得進來**
- 登進來看到「現在沒有任務」（`take/page.tsx:50`），因為沒有 `leftAt: null` 的班
- 姓名、學號、email、家長 email、生日、`consentAt` 全部留在 `users` 表裡，**永久**
- 他在名冊頁的「已移出的學生」摺疊區裡，**永遠**（`classes/[classId]/page.tsx:214-249`
  的註解自己說「每一年的轉出都留在裡面」）

**個資法的問題。** 個資法第 5 條的比例原則與第 11 條第 3 項
（特定目的消失或期限屆滿應刪除或停止處理）要求有保存期限。
系統裡：`.env` 沒有任何學生資料保存期限的設定，`worker.mjs` 的三個週期性工作
（`scripts/worker.mjs:59` 清 session、`:66` 解鎖帳號、`:85` 找卡住的匯入）
沒有一個碰使用者資料，`audit_logs` 也沒有任何 pruning。
規格書說稽核保存五年，**沒有任何程式執行那個五年**。

**嚴重度：阻斷（法遵）。** 這不是不方便——一個沒有刪除能力的系統
在個資法下的處境比缺一個功能嚴重。

**修法建議。**
1. 班級名冊那一列加「退補」：一個動作同時寫 `leftAt`、把 `status` 改成 `ARCHIVED`
   （這個 enum 值已經存在，`schema.prisma:79`）、作廢所有 session。
   `UserStatus.ARCHIVED` 目前是一個產生不出來的值。
2. 加一個 `RETENTION_YEARS` 設定與一支週期性工作，
   對 `ARCHIVED` 且超過保存期的帳號做欄位級去識別化
   （姓名 → 「已刪除的學生」、email/家長 email/生日 → null、`deletedAt` 寫入），
   **但保留 `Attempt` 與 `AttemptAnswer`**（見第 16 項）。
3. `loadStaff` 的錯誤訊息在班級頁真的有那顆按鈕之前，是誤導。

## 4. 忘記密碼

**狀況。** 一週大約 5 人次。學生站在櫃檯說登不進去。

**你會怎麼做。** 開 `/classes/[他的班]`，在名冊上找到他，按那一列的「重設密碼」，
把畫面上顯示一次的那組密碼抄給他。

**實際上做不做得到。** 流程本身很順，而且細節做得對：
`resetStudentPassword`（`roster.ts:522`）在同一個交易裡改密碼、清鎖定計數、
作廢所有 session、標記 `mustChangePassword`；明文只出現在那一個回應裡，
不寫 log 也不寫稽核（`app/api/students/[studentId]/password/route.ts:40-42`）；
如果那位學生正在作答，`writingNow`（`roster.ts:479`）會回一句
「這次重設已經把他登出了，請他用新密碼重新登入並回到那份考卷」（`roster.ts:559-561`）。

**問題只有一個，而它是權限的形狀。**

API 允許的角色是四種：

```
apps/web/app/api/students/[studentId]/password/route.ts:31
const MAY_RESET = new Set(['SYS_ADMIN', 'SCHOOL_ADMIN', 'TEACHER', 'SUBJECT_LEAD']);
```

而那顆按鈕只在 `mayEdit` 為真時才畫出來：

```
apps/web/app/(app)/classes/[classId]/page.tsx:56
const mayEdit = isAdmin || (await isHomeroomOf(user.id, classId));
```

`isHomeroomOf`（`lib/auth.ts:98-104`）要求一列
`ClassMembership { isHomeroom: true, leftAt: null }`。

**授課老師沒有那一列。** `assignSubjectTeacher`（`lib/teaching.ts:100-130`）
只建 `ClassSubjectTeacher`，不建 `ClassMembership`。於是一位只被指派授課的數學老師：

- `/classes` 列表：`where` 是 `{ memberships: { some: { userId, leftAt: null } } }`
  （`classes/page.tsx:30`），他一個班都看不到，畫面寫「你還沒有帶任何班」
- `/classes/[classId]`：`mine` 查不到、又不是管理員 → **整頁被 Denied**
  （`classes/[classId]/page.tsx:49-55`）

所以「現場的那一位老師都要處理得了」這個寫在路由檔頭的設計目標
（`students/[studentId]/password/route.ts:14-18`）**在畫面上沒有實現**。
實際能按到的只有管理員與導師。

一週 5 人次、200 位學生 × 三個月 ≈ 60 次，全部落在你身上。
每一次是：登入 → 猜他在哪個班 → 開那個班 → 在 30 列裡找他 →
按重設 → 抄密碼。名冊上**沒有搜尋框**，7 個班你要猜對。

**嚴重度：只是難用。** 但它是這份清單裡頻率最高的一項。

**修法建議。**
1. 最小改動：`mayEdit` 加上「這個班的授課老師」。
   `classSubjectTeacher.count({ where: { userId, classId } }) > 0` 一句查詢，
   而且它與 API 已經允許的範圍一致——現在是畫面比 API 嚴，那是反的。
2. 順手把 `/classes` 的 where 也加上授課關係，否則老師還是進不去（這是 `情境-裝機第一天` 卡點 18）。
3. 加一個跨班的學生搜尋（學號或姓名），只回姓名 + 班級 + 那兩顆按鈕。
   60 次搜尋省下的時間比任何一項功能都多。

## 5. 老師換人

**狀況。** 數學老師李老師離職，新來的張老師接他的三個班。

**你會怎麼做。** 憑記憶。系統沒有任何一頁告訴你「換一位老師要改哪些地方」。

**實際上做不做得到。** 每一步都做得到，但**要走五個地方，而且沒有任何清單**：

| # | 動作 | 在哪裡 | 漏掉會怎樣 |
|---|---|---|---|
| 1 | 建張老師的帳號 | `/settings/staff` → `createStaff`（`lib/staff.ts:130`） | — |
| 2 | 三個班各指派一次授課 | `/classes/[classId]` 的 Teachers 區塊 → `assignSubjectTeacher`（`teaching.ts:100`） | 張老師 `/grades` 是空的、`/papers` 進不去 |
| 3 | 三個班各取消李老師一次 | 同一區塊 → `removeSubjectTeacher`（`teaching.ts:139`） | 李老師還看得到那三個班的成績 |
| 4 | 如果李老師是導師，先 clear 再 set | 同一區塊 → `clearHomeroom`／`setHomeroom`（`teaching.ts:222`／`:196`） | 李老師還改得動名冊、還重設得了全班密碼 |
| 5 | **停用李老師的帳號** | `/settings/staff` → `setStaffStatus`（`staff.ts:250`） | 見下 |

**漏掉第 5 步會出事，而且是這五項裡唯一不可見的。**

假設你做完 1–4，李老師的 `ClassSubjectTeacher` 一列都不剩，
`teachingSubjectIds` 回空陣列。但 `gradeScopeWhere` 是：

```
apps/web/lib/scoring.ts:906
  return { OR: [{ paper: { subjectId: { in: mine } } }, { createdBy: user.id }] };
```

`mine` 是空陣列時第一個條件不成立，**但第二個成立**。
`maySeeGrades`（`lib/scope.mjs:64`）也是同一條規則。

也就是說：**李老師只要還登得進來，就永遠看得到他這學期派過的每一份任務的完整成績**
——包含班上每一位學生的姓名、學號、分數、逐題對錯。這是設計上刻意的
（「看不到自己派出去的任務的結果沒有道理」，`scope.mjs:51-52`），
但它沒有考慮「這個人已經不在了」。

而 `/settings/staff` 上，一位授課指派被清空的老師與一位正常的老師**長得一模一樣**——
那一頁列的是帳號、姓名、角色、狀態，沒有「教哪幾班」。

`setStaffStatus` 本身做得對：停用時在同一個交易裡刪掉他所有 session
（`staff.ts:275-277`），所以他手上開著的分頁下一次點擊就被踢掉。

**另一件沒有出口的事：主授指定不了。** `assignSubjectTeacher` 把 `isPrimary`
給第一位被指派的人（`teaching.ts:120`），之後沒有任何介面改得動它。
李老師走了以後 `removeSubjectTeacher` 會自動把最早指派的那位接上去
（`teaching.ts:161-173`），而那不見得是張老師。目前沒有功能讀這個欄位，
所以現在不痛；等到有了通知或批改責任，它會是錯的。

**嚴重度：會出錯。** 一學期 1–2 次，而漏掉的那一項不會有任何症狀。

**修法建議。**
1. `/settings/staff` 每一列加一欄「授課」：`3 班 · 數學`。
   停用一位還帶著班的老師時，確認視窗把那三個班列出來。
2. `gradeScopeWhere` 的 `createdBy` 分支加上 `status: 'ACTIVE'` 的隱含條件——
   或者更簡單：停用時就已經登不進來了，所以真正的修法是**讓「離職」變成一個動作**，
   一次做完 3、4、5，而不是三個分散的按鈕。
3. 加一個「交接」動作：選舊老師、選新老師，把所有 `ClassSubjectTeacher` 與導師身分
   一次轉過去，寫一筆稽核。

## 6. 改學生的名字

**狀況。** 名冊 CSV 打錯字（「王大明」打成「王大民」），或學生改名。
兩百筆名冊裡一定有幾個。

**你會怎麼做。** 找「編輯」。名冊表格上沒有。
再匯入一次改好的 CSV——沒有用。

**實際上做不做得到。做不到。** 這一項 `docs/功能清單.md` 第十一節第 14 項已經記過，
這裡只補三件當時沒展開的：

**（一）重匯 CSV 不會更新姓名，而畫面說它成功了。**

```
apps/web/lib/roster.ts:305-352
  let user = await tx.user.findFirst({ where: { username: row.username } });
  if (!user) { user = await tx.user.create({ ... }); created++; }
  await tx.classMembership.upsert({ ... update: { leftAt: null } });
  linked++;
```

`findFirst` 找到就跳過 `create`，而**沒有任何 `user.update`**。
匯入完成的畫面會說「沒有新增帳號——名冊上的學生都已經有帳號了，只是把他們加進這個班」
（`RosterImport.tsx:78`）。這句話是對的，但櫃檯讀到的意思是「匯進去了」。
名字沒變。

**（二）「停用舊的、建新的」這條退路也是堵的。**
`@@unique([tenantId, username])`（`schema.prisma:157`）之下，
停用的帳號仍然佔著那個學號，而 `deletedAt` 沒有寫入端（第 3 項）。
所以「王大民」的補救是給他一個新學號，然後他過去三個月的作答、成績
全部掛在舊帳號上——那正是第 8 項要用的資料。

**（三）你自己的名字也改不掉。** 這一項對主任特別有感：
`User.displayName` 在全 repo 只在 `user.create` 時寫過（`roster.ts:319`、`staff.ts` 的 createStaff），
沒有任何自助修改。導覽列右上角那個名字（`layout.tsx` 傳給 `Nav`）打錯了就是一輩子。

**嚴重度：會出錯。** 不阻斷，但每學期都發生，而且沒有任何出口。

**修法建議。** 三處各加一個欄位就好：
1. `PATCH /api/staff/[userId]` 的 zod schema 收 `displayName`，`StaffEditor` 加一個輸入框。
2. 班級名冊那一列加「編輯」，只改 `displayName` 與 `guardianEmail`，寫 `USER` 類稽核。
3. `applyRoster` 對既有帳號比對 `displayName`，不同時在**試算**畫面上列出來
   （「第 12 列：王大民 → 王大明，會更新姓名」），讓人明確按下去才改。
   靜靜地跟著改是危險的——同名同姓不同人的學號打錯時會覆蓋掉另一個人。

## 7. 一份作業要重派

**狀況。** 兩種，每個月都會發生一次：
（a）上週那份數學小考派錯班了，本來要給忠班，選成了孝班；
（b）忠班有 6 個人沒交，想單獨給他們一次補交機會。

**你會怎麼做。** 開 `/assignments`，找到那一份，按「調整」。

**實際上做不做得到。做不到。**

`AssignmentTools.tsx` 的「調整」對話框有六個欄位：名稱、開放時間、截止時間、
遲交、作答次數、成績開放時機。送出時的 payload 是：

```
apps/web/app/(app)/assignments/AssignmentTools.tsx:127-140
  await submitJson(`/api/assignments/${assignment.id}`, {
    method: 'PATCH',
    json: { title, openAt, dueAt, allowLate, maxAttempts, releasePolicy },
  });
```

**沒有 `targets`。** 而 API 收得了它（`app/api/assignments/[assignmentId]/route.ts:31-36`
的 zod schema 有 `targets: { classIds, userIds }`），
`updateAssignment` 也會轉發（`lib/assignment.ts:291-293`），
`setAssignmentTargets`（`lib/assignment.ts:315`）整支寫好了、
連「不能把已經作答的人拿掉」都擋了（`assignment.ts:339-353`）。
**整條路從畫面斷在第一步。**

於是：

**（a）派錯班。** 如果孝班還沒有人開始作答，你可以按「取消派發」
（`AssignmentTools.tsx:101-105`，只在 `attempts === 0` 時才畫出來），
然後重新建一份。如果已經有一個人點開了，`deleteAssignment` 會擋
（`assignment.ts:391-397`：「已經有 N 份作答記錄，不能刪除」），
而換對象又做不到——**這份錯的任務會永遠留在孝班每一位學生的清單上**，
永遠算進孝班的應交人數。唯一能做的是把截止時間改成過去，
讓它變成一份全班未交的紀錄。

**（b）讓 6 個人補交。** 正確的做法是把那 6 位加進 `targets` 的 `userIds`
並把作答次數加一——`setAssignmentTargets` 明說「加人隨時可以（補考的那兩位）」
（`assignment.ts:313`）。做不到。實際上只能：把整份任務的截止時間往後延，
於是**全班 30 個人都可以再寫一次**，包含已經交過的 24 位。

**嚴重度：阻斷。** 這是每月會發生、而且完全沒有繞道的事。

**修法建議。** 這是這份清單裡改動最小、回報最大的一項：
在「調整」對話框裡加一個班級多選 + 學生多選，把 `targets` 一起送出去。
資料來源（`classes`、`students`）在 `/assignments` 的 server component 裡
已經查好了（`assignments/page.tsx:91`、`:117`），
`NewAssignment.tsx:171-249` 的選擇器可以整段複用。
伺服器端的規則、權限、錯誤訊息全部已經在了。

## 9. 看一個班整學期的狀況

**狀況。** 段考後的班務會議。哪幾個學生在退步？哪一個章節全班都不會？

## 10. 期末結算

**狀況。** 學期結束。舊學年度怎麼收？新學年怎麼開？學生怎麼升級？

**你會怎麼做。** 開 `/settings/years`，期待有「結算」或「封存」。

**實際上做不做得到。**

`/settings/years` 上每一列只有兩顆按鈕：「編輯」（改名稱與起訖日）
與「設為當前」（`settings/years/YearEditor.tsx:131`、`:135-142`）。
API 只有 `GET`、`POST`、`PATCH`——**沒有 DELETE**
（`app/api/academic-years/route.ts:19,42`、`[yearId]/route.ts:26`）。
`lib/academicYear.ts` 只 export 三支：create、update、setCurrent。
沒有 archive、沒有 close、沒有 rollover。

**而最要命的是：`isCurrent` 幾乎不 scope 任何東西。**

全 repo 對 `isCurrent` 的使用只有五處，其中四處是顯示用的
（`classes/page.tsx:33`、`:52`、`:74`，`api/classes/route.ts:28`）。
**唯一有行為的一處是：**

```
apps/web/app/(app)/classes/NewClass.tsx:19
  years.find((y) => y.isCurrent)?.id ?? years[0]?.id ?? ''
```

——開班對話框裡預選哪一年。就這樣。

`/classes` 列出所有年度的所有班（`classes/page.tsx:27-36`，where 只有
「不是管理員就限自己有份的」，沒有年度條件）。
`/grades`、`/assignments` 沒有任何年度欄位。
`listStudentTasks` 沒有年度條件。
首頁的「N 位學生還沒有家長同意」（`app/(app)/page.tsx:238-240`）
是全租戶 count，不分年度。

**所以「開新學年」實際上是這樣：**

1. `/settings/years` 建「116學年度」、設為當前 —— 這一步 30 秒，做得到
2. `/classes` 開 7 個新班 —— 一次一個對話框
3. 每個班匯入名冊 CSV —— 學生帳號 username 沒變，所以 `applyRoster` 會
   `findFirst` 到既有帳號、只加班級關係（`roster.ts:305`）。**這一段是對的**，
   不會產生重複帳號，也不會重發密碼
4. 每個班重新指派授課老師與導師 —— 一次一筆（`情境-裝機第一天` 卡點 22）
5. **然後呢**

第 5 步沒有。舊的 7 個班：

- 還在 `/classes` 列表上，永遠（`deactivateClass`（`roster.ts:124`）
  **沒有任何呼叫端**，也沒有 `PATCH /api/classes/[classId]` 這條路由）
- 名冊上每一位學生的 `leftAt` 還是 null
- 於是 `listStudentTasks` 對每一位學生同時回**新舊兩個班**的任務，
  舊班那幾十份會排在他的「已完成」與「已逾期」裡
- `countRecipients` 對舊任務照樣算得出人數
- `/grades` 與 `/assignments` 的 60／100 筆上限，被新舊兩年的任務一起佔

**要把舊班收乾淨，唯一的辦法是 200 次「移出班級」**，
每一次一個確認對話框（`Membership.tsx:52-93`），而且要打開七個班的名冊逐列按。

**沒有「升級」的概念。** 學生從高二升高三，系統裡的表現是「他在兩個班裡」。

但沒有任何介面會寫 `leftAt` 以外的東西。

**嚴重度：阻斷。** 這一項一年只發生一次，所以到第一個學年結束前沒有人會發現。

**修法建議。**
1. **年度結算動作**：`/settings/years` 每一列加「結算」。

2. **班級沿用**：開班對話框加「從舊班複製名冊」，選一個舊班，

3. **年度篩選**：`/classes`、`/grades`、`/assignments` 三頁預設只顯示當前學年度，

4. `Class` 加 `PATCH` 路由，把 `renameClass` 與 `deactivateClass` 接上——
   兩支函式都寫好了、都有稽核，只是沒有人叫得到。

## 11. 磁碟滿了

**狀況。** 半夜。什麼東西先滿？我怎麼知道？滿了會怎樣？

**先看它們在哪裡。** Docker 部署的每一樣東西都在同一個檔案系統上：

| 東西 | 位置 | 誰會清 |
|---|---|---|
| Postgres 資料 | `postgres-data` volume | autovacuum（只回收空間，不縮檔） |
| **WAL 歸檔** | `postgres-wal` volume | **只有備份容器**（`deploy/backup/entrypoint.sh:56` 的 `prune_wal`） |
| **MinIO 物件**（題本原檔、頁面影像） | `minio-data` volume | **沒有人** |
| **備份 tarball** | `${BACKUP_DIR}`＝`/var/backups/yunzhi` | 備份容器（`entrypoint.sh:138-140`），保留 30 天 |
| 容器日誌 | `/var/lib/docker/containers` | json-file driver，`100m × 5` per 容器（`docker-compose.yml:16-20`） |
| **audit_logs** | Postgres | **沒有人**（規格說保存五年，沒有任何程式執行它） |
| **ai_usage_logs** | Postgres | **沒有人** |
| **import_jobs / import_pages** | Postgres | **沒有人** |

Docker 具名 volume 全部在 `/var/lib/docker/volumes`，也就是 `/`。
`BACKUP_DIR=/var/backups/yunzhi`（`.env:228`）除非另外掛，也是 `/`。
**所以「磁碟滿了」等於全部一起滿。**

**先滿的是備份。而且是設計造成的。**

排程備份的實作在 `deploy/backup/entrypoint.sh`，它與 `deploy/scripts/backup.sh`
**是兩份不同的程式**。容器版每天做的事（`entrypoint.sh:76-143`）：

```
deploy/backup/entrypoint.sh:41
  mc mirror --quiet --preserve "yz/${S3_BUCKET}" "${dest}"
```

**每一份每日備份都包含整個 MinIO bucket 的完整複本。** 不是增量，是全量。
而 MinIO 裡放的是 300 dpi 的頁面影像（`apps/ai/pipeline/normalize.py:37`
`TARGET_DPI = 300`）——A4 在 300 dpi 是 2480×3508 像素，一頁 PNG 約 0.5–2 MB。

保守估：13 科、每科 3 位老師、一學期各匯入 4 份 40 頁的題本
= 156 份 × 40 頁 ≈ 6 200 頁 ≈ **6 GB**，加上原始 PDF。
PNG 已經壓過了，`tar -czf` 幾乎不會再小。

**6 GB × 30 天保留 = 180 GB，只為了同一批不會變的圖片。**

而且沒有任何一道防線：

- 容器版的 `do_backup`（`entrypoint.sh:76`）**完全沒有空間檢查**。
  手動版的 `backup.sh:57-65` 有，但它算的是 `pg_database_size × 2 + 2GB`
  ——**沒有把物件儲存算進去**。
- WAL：`archive_timeout = 900`（`deploy/postgres/postgresql.conf:30`）保證
  每 15 分鐘至少一個 16 MB 段，下限約 1.5 GB／天，保留 14 天
  （`WAL_ARCHIVE_RETENTION_DAYS=14`，`.env:85`）≈ 21 GB 穩態。
  **而清它的是備份容器。備份容器停了，WAL 就永遠不清。**
- 匯入的頁面影像永遠不刪：`deletePrefix`（`lib/storage.ts:152`）
  全 repo 只有一個呼叫端，而且是上傳失敗時的回滾
  （`app/api/import/route.ts:283`）。**校對完、入庫後，那 40 張 PNG 留著，沒有出口。**
  `getObject`（`storage.ts:105`）與 `signedGetUrl`（`storage.ts:124`）也沒有呼叫端——
  也就是那些圖既刪不掉、也看不到。

**我怎麼知道？** 只有一條路：自己去跑 `doctor.sh`。

```
deploy/scripts/doctor.sh:216-227
for path in / "${BACKUP_DIR:-/var/backups/yunzhi}"; do
  ...
  if (( ${used:-0} > 90 )); then fail ... elif (( ${used:-0} > 80 )); then soft ...
```

寫得很好，而且失敗訊息說得出後果（「磁碟寫滿會讓考試中斷且 Postgres 無法寫 WAL」）。
**問題是沒有任何東西會自動跑它。** 全 repo 沒有 cron、沒有 systemd timer、
沒有 compose 服務會呼叫 `doctor.sh`——它只出現在 `upgrade.sh:72`／`:199`
與各份文件的「請執行」裡。

Prometheus 的 `node_filesystem_avail_bytes` 告警需要 node_exporter，
而 compose 裡沒有任何 exporter，也沒有 Alertmanager
（`功能清單` 第十一節第 9 項已詳述）。

**滿了會怎樣？** 三件事同時發生：

1. Postgres 寫不進 WAL → 所有寫入交易失敗 → 考試中的每一次存檔都 500
2. 備份容器的 `pg_dump` 失敗 → 它記一行日誌 `log "pg_dump 失敗"` 就返回，
   而 `overdue()`（`entrypoint.sh:149`）在超過 26 小時沒成功時回 true，
   於是 while 迴圈**每約 90 秒重試一次 pg_dump**（`entrypoint.sh:172-181`）——
   在一台已經滿了的機器上，這會讓情況更糟
3. `doctor.sh` 的服務檢查清單是
   `postgres redis minio web worker ai caddy`（`doctor.sh:102`）——
   **`backup` 不在裡面**。而備份容器的 healthcheck 只看心跳檔的新鮮度
   （`docker-compose.yml:479`），心跳在迴圈裡無條件寫（`entrypoint.sh:180`），
   **所以一個天天失敗的備份容器，狀態是綠的**

**嚴重度：會出錯。** 每年 1–2 次，而且第一次會是在你不知道的時候。

**修法建議。**
1. 備份不要每天全量複製物件。最小改動：只在第一份與每週一份做全量，
   其餘只備資料庫（`backup.sh` 已經有 `--no-objects`）；
   或改成 `mc mirror` 到一個獨立的 `objects/` 目錄再硬連結。
2. `backup.sh` 的空間估算把 `mc du` 的結果加進去。容器版加上同一道檢查。
3. `doctor.sh:102` 的服務清單加 `backup`。
4. 排一個 systemd timer 或 compose 服務，每天跑一次 `doctor.sh --json`，
   把 failure 數寫進一個檔案；首頁待辦讀它，出現「系統健檢有 N 項失敗」。
   這是唯一能讓主任在不看終端機的情況下知道出事的路。
5. 加一支週期性工作清理已入庫超過 N 天的匯入工作的頁面影像
   （`deletePrefix(importPrefix(...))` 已經寫好了）。
   `documentJson` 留著，圖片刪掉——校對已經結束了。

## 12. 有人反映系統很慢

**狀況。** 三位老師說「最近很慢」。學生說交卷要等。

**你會怎麼做。** 找一頁「系統狀態」。沒有。

**實際上有什麼。**

**應用層：零。** `apps/web/lib/route.ts`（98 行）與 `lib/page.ts`（28 行）
是每一支 API 與每一頁的外殼，**兩者都沒有任何一行 console 或計時**。
Prisma 的 log 只在 `LOG_LEVEL=debug` 時開 query（`lib/prisma.ts:19-23`），
而那會把每一句 SQL 都印出來，正式環境開不得。
`/api/metrics` 這條路由不存在（`功能清單` 第十一節第 9 項）。

所以「哪一頁慢」「哪一支 API 慢」「慢了多久」——**沒有任何資料**。

**資料庫層：有，而且設定是對的。**

```
deploy/postgres/postgresql.conf:59, 63, 64, 77-79
log_min_duration_statement = 1000
log_lock_waits = on
log_temp_files = 10MB
shared_preload_libraries = 'pg_stat_statements'
```

`OPERATIONS.md:122-140` 給了三段可用的 SQL（最慢的查詢、資料表大小、膨脹）。
配合 `db-shell.sh --readonly`（`deploy/scripts/db-shell.sh:14`）可以查。
**這是唯一真的能用的診斷路徑，而它要求你會寫 SQL。**

慢查詢日誌走 stderr（`postgresql.conf:57-58`），也就是 `docker compose logs postgres`。
compose 有 loki 服務（`docker-compose.yml` 的 monitoring profile），
但**沒有 Promtail 或任何 log shipper**，所以 Loki 是空的。

**`doctor.sh` 查得到兩個真正的先兆：** 連線數逼近上限
（`doctor.sh:151-162`，>85% 報 fail）與閒置交易超過 10 分鐘
（`doctor.sh:165-166`，會擋住 autovacuum）。這兩項是對的。

**但它給的解法指向一個在 Docker 模式下無效的旋鈕：**

```
deploy/scripts/doctor.sh:156
  "接近上限，交卷尖峰會被拒。調高 POSTGRES_MAX_CONNECTIONS 或降低 DATABASE_POOL_MAX"
```

`POSTGRES_MAX_CONNECTIONS=200`（`.env:274`）只被 `deploy/scripts/install.sh:237`
讀取——**那是原生安裝的路徑**。Docker 部署掛的是唯讀的
`deploy/postgres/postgresql.conf`（`docker-compose.yml` 的 postgres volumes），
裡面 `max_connections = 200` 是寫死的。
`POSTGRES_SHARED_BUFFERS` 同理（只在 `install.sh:236`）。

也就是說 `OPERATIONS.md:57-75` 的整段容量調校，在推薦的 Docker 部署上
**改了 `.env` 不會有任何效果**，而且沒有錯誤訊息。

**已知會隨時間變慢的地方。** 這幾個第一天不痛：

- `/assignments` 的 `countRecipients`（`lib/assignment.ts:542`）固定三次查詢，
  但第三次是對整批班級的 `classMembership.findMany`——班級與成員只增不減
- `monthlyTokensUsed`（`scripts/import-pipeline.mjs:1068-1077`）
  把當月每一列 `ai_usage_logs` 撈到 Node 裡再 reduce，
  而 `AiBudgetCounter` 那張為此設計的表沒有任何寫入端（見第 13 項）
- `audit_logs` 只增不減，而 `/grades` 與 `/assignments` 都沒有分頁——
  Postgres 要對愈來愈大的表做 `ORDER BY ... LIMIT 61`

**嚴重度：只是難用。** 但它的形狀是「出事時你沒有工具」。

**修法建議。**
1. `lib/route.ts` 的 `scopedRoute` 外殼加一行：超過 1 秒的請求印
   `[slow] METHOD path 1234ms userId`。一行程式，換到「哪一支慢」的答案。
   `lib/page.ts` 同理。
2. 補上 `/api/metrics`（Prometheus 的 scrape job 已經指著它了，
   `deploy/monitoring/prometheus.yml`），或至少一頁 `/settings/health`
   把 `doctor.sh --json` 的結果與 `pg_stat_statements` 的前十名畫出來。
3. Docker 模式讓 `postgresql.conf` 支援環境變數覆寫
   （compose 的 `command` 加 `-c max_connections=${POSTGRES_MAX_CONNECTIONS}`），
   或把 `OPERATIONS.md` 與 `doctor.sh:156` 的建議改成 Docker 模式真正有效的做法。

## 14. 要升級到新版

**狀況。** 廠商發了 v0.22.0。我要升上去。

**你會怎麼做。** 照文件：更新程式碼，跑 `./deploy/scripts/upgrade.sh`。

**實際上做不做得到。流程本身是這份 repo 裡寫得最好的東西之一。**

`upgrade.sh` 八步（`upgrade.sh:7-15`）：安全檢查 → 記錄回滾點 → 升級前備份
（帶 `pre-upgrade` 標籤，不受保留期清除）→ 建置新版（**在停機之前**，
失敗時服務還好好跑著，`upgrade.sh:103-111`）→ 維護模式（Caddy 回一頁
說「你先前的作答已經儲存」的中文頁，不是 502）→ 遷移 → 滾動重啟 →
健康驗證，失敗自動回滾（`upgrade.sh:141-153` 的 ERR trap）。
備份失敗就中止：「沒有退路就不升級」（`upgrade.sh:95`）。

**但第 1 步的安全檢查是死的。**

```
deploy/scripts/upgrade.sh:54-57
active_exams="$(pg_scalar "SELECT count(*) FROM information_schema.tables WHERE table_name='exam_sessions'")"
if [[ "${active_exams}" == "1" ]]; then
  in_progress="$(pg_scalar "SELECT count(*) FROM exam_sessions WHERE status='IN_PROGRESS'")"
```

**`exam_sessions` 這張表不存在。** 作答的表叫 `attempts`
（`packages/db/schema.prisma:1501` 的 `@@map("attempts")`）。
全 repo 出現 `exam_sessions` 的只有 `upgrade.sh` 這兩行。

所以 `active_exams` 永遠是 `0`，整個 `if` 區塊被跳過——
連 else 分支的 `ok "沒有進行中的考試"` 都不會印。
畫面上那一段就只是**空的**，看起來像是檢查通過了。

**後果：升級不會被考試擋住。** 第 6 步 `app_stop`（`upgrade.sh:160`）
會把 web 與 worker 停掉。正在作答的學生：

- 前端沒有任何本機持久化——全 repo **沒有 IndexedDB、沒有 localStorage、
  沒有 sessionStorage**（grep 結果為空）。答案只在記憶體與伺服器
  （`情境-學生應考` 卡點 22）
- 所以維護頁那句「你先前的作答已經儲存」（`upgrade.sh:132`）
  只對**已經送到伺服器的那幾題**成立
- `OPERATIONS.md:181` 印給櫃檯的降級流程寫著
  「學生的作答存在瀏覽器 IndexedDB，恢復後會自動續傳。**請學生不要關閉分頁**，
  這是最重要的一句話」——**那個 IndexedDB 不存在**
- `OPERATIONS.md:174` 寫著「`upgrade.sh` 會主動偵測進行中的考試並拒絕執行」——它不會

三份文件對同一件事給了三個都不成立的保證。

**回滾。** `rollback.sh` 的流程是對的，但有兩個要知道的：

**（一）回滾會讓升級後的資料消失，而這是設計。**
`rollback.sh:5-9`、`:58-60`、`upgrade.sh:216` 都講得很白。
超過 24 小時會多警告一次（`rollback.sh:42-50`）。

**（二）用 tarball 部署的話，回滾可能整條路是死的。**

```
deploy/scripts/rollback.sh:93-105
elif docker image inspect "yunzhi/web:${PREVIOUS_VERSION}" >/dev/null 2>&1; then
  ok "找到舊版映像"
else
  warn "找不到 yunzhi/web:${PREVIOUS_VERSION} 的映像，需要重新建置。"
  warn "這通常表示曾執行過 docker image prune。"
  if [[ -d "${YZ_ROOT}/.git" ]] && git ... ; then compose build
  else die "無法取得舊版程式。請手動 checkout 舊版標籤後再執行本腳本。"
```

離線安裝走的是 tarball（`INSTALL.md:326-337`：
`build-offline-bundle.sh` 產出 3–5 GB 的 tar.gz，解開就是 `yunzhi/`）——
**那裡面沒有 `.git`**。所以只要舊映像不在了，`rollback.sh` 就 die。

而「舊映像不在了」最常見的原因是什麼？**磁碟滿的時候跑 `docker image prune`。**
第 11 項與這一項在真實世界會連在一起。

**嚴重度：阻斷（考試中升級這一項）。**

**修法建議。**
1. `upgrade.sh:54-57` 的表名改成 `attempts`，狀態欄位是 `status`
   （`schema.prisma:1470` 附近），值是 `IN_PROGRESS`。
   而且 `if` 的條件要反過來寫——查不到表時應該是 **warn**（「無法確認是否有人在考試」），
   不是靜靜跳過。
2. `OPERATIONS.md:174` 與 `:181` 兩句話要改：前者等第 1 點修好，
   後者要刪掉 IndexedDB 的說法，改成「已經送到伺服器的答案還在，
   最後幾題可能會漏。恢復後請學生回到那份考卷檢查」。
   這一段是要印出來放櫃檯的，錯的比沒有更糟。
3. `rollback.sh` 在找不到 `.git` 且找不到映像時，
   至少把「去哪裡拿舊版 tarball」寫進錯誤訊息。
4. `upgrade.sh` 在成功後不要只留 24 小時的口頭承諾——
   把 `pre-upgrade` 備份的路徑也寫進 `deployment_records`
   （現在只寫了 `backupPath`，`upgrade.sh:205-207`，這一項是對的）。

## 15. 資料庫掛了

**狀況。** 早上八點半，學生說登不進去。

**我怎麼發現？** 從電話。

`readyz`（`app/api/readyz/route.ts:61-69`）會打資料庫與 Redis，掛了就回 503。
Caddy 的 `health_uri` 指著它（`deploy/caddy/Caddyfile:64`），
`WEB_REPLICAS` 預設是 1（`docker-compose.yml:170`），所以沒有健康的實例可以導——
學生看到的是 502。

**沒有任何東西會通知你。** Prometheus 的 `up{job=~"yunzhi.*"} == 0` 那條規則
是九條裡唯一引用了存在的指標的，但 compose 與 `prometheus.yml` 都
**沒有 Alertmanager**（`功能清單` 第十一節第 9 項），
所以它觸發只會在 Prometheus 的網頁上變紅。而 monitoring 是一個
要手動 `--profile monitoring up -d` 才會起來的 profile。

`Notification` 那三張表沒有任何寫入端（`功能清單` 第十一節第 11 項）。

**注意一件事：`readyz` 不檢查 MinIO。** `checkStorage` 沒有呼叫端。
MinIO 掛掉時 `readyz` 回 `ready: true`、`doctor.sh` 的 `svc.minio` 會抓到
（`doctor.sh:102` 的清單裡有它），但如果你沒跑 doctor，
症狀是「考試正常、匯入全部失敗」而健康檢查全綠。

**怎麼還原。** 這一段做得很完整。

`restore.sh`（317 行）：驗校驗碼（不符就 die，`restore.sh:78-86`）→ 解密 →
比對 schema hash（不符要打 `RESTORE ANYWAY`，`restore.sh:115-120`）→
**先備份現況**（`restore.sh:124-129`，失敗就 die：「沒有退路就不做還原」）→
要打 `RESTORE` 確認 → 停應用 → 清空 public schema **但保留擴充功能**
（`restore.sh:173-216`，這一段的註解解釋了為什麼不用 `pg_restore --clean`——
它會產生 `DROP EXTENSION vector` 而應用帳號動不了，
配上 `--exit-on-error` 就是每一次還原都在第一步失敗）→
平行 `pg_restore`（`-j`，`restore.sh:219-230`）→
**以結果驗證而非結束碼**（`restore.sh:222-245`）→ 還原物件儲存 → 重啟 → 計數檢查。

**停多久。** `restore.sh:299-303` 會印實測秒數當作 RTO 參考值。
`DISASTER-RECOVERY.md:120-145` 給的整機重建估計是：裝 OS 30 分 + 取回程式與 .env
+ 安裝 15 分 + 還原 10 分到 1 小時。承諾的 RTO 是 4 小時。

**兩個要注意的。**

**（一）時間點還原（PITR）是手動的。** `restore.sh --to` 只解壓 WAL 到一個目錄
然後印出手冊位置（`restore.sh:249-262`）。重放要照
`DISASTER-RECOVERY.md:72-118` 一步一步做：停服務、設 recovery target、
看日誌等 "archive recovery complete"。半夜一個人做這件事，是這份文件裡
唯一真的需要事前演練過的操作。

**（二）排程備份的 manifest 不含 schemaHash。**
容器版寫的是 `name / createdAt / appVersion / source / includesObjects / encrypted`
（`entrypoint.sh:105-108`），**沒有 `schemaHash`**。
而 `restore.sh:108` 讀不到時 `b_hash` 是 `unknown`，
於是 `restore.sh:115` 的相容性檢查整段被跳過。
手動 `backup.sh` 寫的 manifest 有（`backup.sh:121-130`）。
也就是說：**日常還原用的那些備份，恰好是沒有版本保護的那一批。**

**嚴重度：會出錯。** 還原能力是有的，發現能力是零的。

**修法建議。**
1. 容器版 manifest 補上 `schemaHash`（一句 SQL）。
2. `readyz` 加上 `checkStorage`——或者不加（AI 服務不列入是對的），
   但至少 `doctor.sh` 的輸出要更容易被看到（見第 11 項第 4 點）。
3. 最重要的：**排一次 PITR 演練，把 `DISASTER-RECOVERY.md:72-118` 走完一遍，
   並把實際耗時寫回文件。** `verify-restore.sh` 已經寫好而且會記
   `restore-drills.log`（`verify-restore.sh:214-217`），
   `doctor.sh:259-275` 也會在超過 92 天沒演練時報 fail——
   但 README 自承從來沒有實際跑過。

## 16. 家長要求刪除孩子的資料

**狀況。** 一位家長來信，依個資法第 11 條要求刪除孩子的個人資料。

**你會怎麼做。** 找刪除。

**實際上做不做得到。做不到。全 repo 沒有任何一條刪除使用者的路徑。**

- `User.deletedAt`（`schema.prisma:135`）只被讀、從未被寫（見第 3 項）
- `setStaffStatus` 明確擋掉學生帳號（`staff.ts:386-391`）
- 班級名冊那一列只有「重設密碼」與「移出班級」（`classes/[classId]/page.tsx:179-189`）
- 沒有 `DELETE /api/students/...` 這條路由
- 沒有任何保存期限設定、沒有任何清理工作

能做的只有：移出班級。他的姓名、學號、email、家長 email、生日、
同意時間、每一次作答、每一題答案、每一次登入的稽核紀錄
全部原樣留在資料庫裡，而且**每一份備份都帶著它們，保留 30 天**（第 11 項），
外加 `pre-upgrade`／`pre-uninstall`／`pre-restore` 標籤的備份**永遠不刪**
（`backup.sh:183-185`、`entrypoint.sh:139`）。

**「刪了成績統計會怎樣」。** 這個問題值得認真回答，因為它是不做刪除的常見藉口，
而在這個 schema 裡答案是清楚的：

`Attempt.userId` 的外鍵是 Cascade（`schema.prisma:1466` 區塊），
所以真的 `DELETE FROM users` 會把作答與答案一起帶走，
`classStats`（`scoring.ts:646`）的每一個統計都會少一個人——
平均會變、答對率的分母會變、級分對照會變。
**已經印出來給家長看過的成績單，數字會對不上。**

正確的做法是**去識別化而不是刪除**：把 `displayName` 換成
「已刪除的學生（2026-07）」、`username` 換成一個不可回溯的代號、
email／家長 email／生日／`a11yProfile` 清空、`deletedAt` 寫入。
`Attempt` 與 `AttemptAnswer` 留著——那是統計的來源，而去識別化之後它不再是個資。

schema 已經為此準備好了：所有題庫層的反向關聯是 `SetNull` 而不是 Cascade
（`schema.prisma:139-141` 的註解：「老師離職時題目與校對記錄要留著，
只是不再指向一個已刪除的帳號」）。同樣的設計思路只差沒有套到學生身上。

**一個必須一起處理的地方。** `ImportJob.rightsDeclaredName`
（`schema.prisma:1029`）是聲明人姓名的快照，
schema 註解解釋得很清楚：`rightsDeclaredBy` 會 SetNull，
但**誰聲明的這件事必須留著**，否則刪掉任何一位曾聲明過權利的老師帳號
都會撞上 `import_jobs_rights_declared` 這個 CHECK。
做刪除功能時這一條會是第一個絆倒人的地方，而錯誤訊息完全看不出原因。

**稽核不能刪。** `audit_logs` 的資料庫觸發器強制只新增不修改
（`schema.prisma:246-250` 的註解）。這是對的——個資法的刪除權
不及於為履行法定義務所必要的紀錄。但要在流程上寫清楚，
否則「都刪了」這句話對不上。

**嚴重度：阻斷（法遵）。**

**修法建議。**
1. 一支 `anonymizeStudent(userId, actorId)`：一個交易，
   改欄位、寫 `deletedAt`、作廢 session、寫一筆 `USER` 類稽核
   （before 記原本的學號，after 只記代號）。
2. 班級名冊的「已移出的學生」那一區加一顆「刪除個資」，
   要求打出學生姓名確認（與整班重設密碼同一種確認強度，
   `api/classes/[classId]/passwords/route.ts:56`）。
3. **告訴家長備份的事。** 現有備份裡的資料要等 30 天（或標籤備份的無限期）
   才會自然汰除，這一點要寫在回覆家長的制式信裡，也要寫進
   `docs/OPERATIONS.md`。順便處理標籤備份永不刪除這個矛盾——
   `pre-upgrade` 的備份留三年是合理的維運需求，但它含全體學生個資。

**狀況。** 兩種：學校要一份成績；或者三年後我們要換系統。

搜尋 `Content-Disposition`、`text/csv`、`download=`、`toCsv`、`application/vnd.ms-excel`
在 `apps/web` 底下的結果只有一筆，而且是**匯入**的 accept 屬性：

```
apps/web/app/(app)/classes/[classId]/RosterImport.tsx:140
  accept=".csv,text/csv,text/plain"
```

`lib/csv.mjs` 只有 `decodeCsv`／`parseCsv`／`matchColumns`——**只讀不寫**。

名冊匯入後的初始密碼表（`RosterImport.tsx:110`）與

成績、題庫、名冊、作答明細——一頁都印不出來，一個檔案都下載不了。

**所以要給學校一份成績，實際流程是：** 開 `/grades/[assignmentId]`，
用滑鼠框選那張表，貼進 Excel，手動整理欄位。一份任務一次。
而超過 60 份之後你連那一頁都找不到（第 9 項）。

**換系統的問題更大。** 三年的題庫（`questions`、`question_options`、
`explanations`、`question_knowledge_points`）、三年的成績、
每一份題本的 `documentJson`（QIF 標準交換格式，
`schema.prisma:1063-1078`，「抽取邏輯改版後要能重跑而不必再付一次模型的錢」）——
**這些全部只出得去一條路：`pg_dump`。**

而 `pg_dump` 出來的是 custom 格式（`backup.sh:72-74` 的 `-Fc`），
只有 `pg_restore` 讀得懂，而且加密了。要交給另一家廠商，
你得先解密、還原到一個空資料庫、再自己寫 SQL 撈。

**諷刺的是，這個系統定義了一份完整的題目交換格式**
（`docs/qif-1.1.schema.json`，1 000 多行的 JSON Schema），
匯入端完整實作，**匯出端一行都沒有**。

**嚴重度：阻斷。** 而且它是那種你直到要用的那一天才會發現的阻斷。

**修法建議。** 三支路由，每一支不到 100 行：
1. `GET /api/grades/[assignmentId]/export.csv` — 一份任務的分數表 + 逐題對錯。
   資料來源 `classStats` 已經全部算好了。
2. `GET /api/classes/[classId]/export.csv` — 名冊（學號、姓名、家長信箱、同意狀態）。
3. `GET /api/export/questions.qif.json` — 依科目匯出題庫，
   格式用已經定義好的 QIF 1.1。這一支同時解決「換系統」與「備份題庫」。

三支都要記 `SYSTEM` 類稽核（誰在什麼時候匯出了什麼），
因為匯出全班成績是一個該被記錄的動作。
CSV 記得輸出 BOM——櫃檯的 Excel 沒有 BOM 會把中文變成亂碼。

## 18. 稽核

**狀況。** 有人問「上週三是誰改了這個學生的分數」。

**寫入端做得非常完整。** 全 repo 有 20 處 `auditLog.create`，
涵蓋六個分類（`schema.prisma:252-262`）。跟這個問題直接相關的四處：

| 動作 | 位置 | 記了什麼 |
|---|---|---|
| 單份重新計分 | `lib/scoring.ts:286-300` | `before: { autoScore, totalScore }`、`after`、`reason`、**變了哪幾題**（`changed.slice(0,50)`） |
| 全班重新計分 | `lib/scoring.ts:373-390` | 份數、變動份數、失敗數，以及**分數變了的人全部列出來，不截斷** |
| 作廢作答 | `lib/scoring.ts:468-482` | 作廢前的狀態與分數（「家長問『原本考幾分』時，這是唯一還說得出來的地方」） |
| 撤銷作廢 | `lib/scoring.ts:531-545` | 回到哪個狀態、分數 |

還有一個細節做對了：學生與教職員的密碼重設用**同一個 action 名稱**
`auth.password_reset`（`staff.ts:340-353` 的註解：
「個資事件調查要的是『這個帳號的密碼被誰動過幾次』這一條時間線，
而同一件事分散在兩個 action 名稱底下，查的人會只翻其中一個然後說『沒有記錄』」）。

資料庫層以觸發器強制只新增不修改（`schema.prisma:246-250`），
索引也開對了：`[tenantId, category, createdAt]`、`[tenantId, targetType, targetId]`、
`[actorId, createdAt]`（`schema.prisma:284-286`）。

**查詢端：沒有畫面。**

`功能清單` 第十一節第 15 項已經記了「沒有任何頁面顯示 `audit_logs`」。
這裡補上實際查一次要做什麼：

```bash
# 1. 先找租戶（沒有它 RLS 會讓每個查詢回 0 列而且不報錯）
./deploy/scripts/db-shell.sh -c 'SELECT id,name FROM tenants'

# 2. 找學生的 userId
./deploy/scripts/db-shell.sh --tenant <id> --readonly \
  -c "SELECT id FROM users WHERE username='S1140312'"

# 3. 找他的 attempt id（因為 audit 的 targetId 是 Attempt，不是 User）
./deploy/scripts/db-shell.sh --tenant <id> --readonly \
  -c "SELECT id, \"assignmentId\" FROM attempts WHERE \"userId\"='...'"

# 4. 才查得到
./deploy/scripts/db-shell.sh --tenant <id> --readonly \
  -c "SELECT \"createdAt\", action, \"actorId\", before, after FROM audit_logs
      WHERE \"targetId\" IN (...) ORDER BY \"createdAt\" DESC"

# 5. actorId 是 cuid，還要再查一次 users 才知道是誰
```

**五次查詢，而且中間三次是為了把「一個學生的名字」翻譯成
「稽核表裡的 targetId」。** `targetType='Attempt'` 這個設計是對的
（一次計分動的就是一份作答），但它讓「這位學生的分數被誰動過」
這個最自然的問題，變成一段要串三張表的 SQL。

`db-shell.sh` 本身做得好：`--readonly` 用 `default_transaction_read_only=on`
（`db-shell.sh:49`），`--tenant` 用 PGOPTIONS 在連線期設 GUC（`:45-47`），
而且沒指定 tenant 時會警告「RLS 之下多數查詢會回 0 列——那不是資料不見了」
（`db-shell.sh:58`）。這句話會省下一次無謂的資料遺失事故調查。

**還有一件事沒有人做：稽核沒有保存期限，也沒有清理。**
規格書說保存五年（`schema.prisma:250` 的註解），
`worker.mjs` 的三個週期性工作沒有一個碰它。所以它只會長。
五年後怎麼清、清了之後怎麼證明清得對——現在沒有答案。

**嚴重度：只是難用。** 但它是「出事時你要拿得出來」的那一類，
而出事時你不會想現學 SQL。

**修法建議。**
1. 一頁 `/settings/audit`（只給 `SCHOOL_ADMIN` 與 `SYS_ADMIN`）：
   篩選分類、日期區間、行為人、以及**一個學生／教職員的搜尋框**。
   後者要在查詢時自動展開成「這個人的 userId + 他所有 attempt 的 id」，
   因為那正是每一次調查的第一步。
2. 每一列顯示行為人姓名（join users）、動作的中文說明、
   以及 before/after 的差異。`GRADE` 類的 metadata 已經有 `changed` 陣列了。
3. 加一支週期性工作，把超過保存期的稽核搬到冷儲存或刪除，
   並把這個動作本身也記一筆。

# 第一個月不痛、第三個月會痛的事

依痛的程度排序。每一項的共同形狀是：**上線驗收時它是綠的。**

### 1. `/grades` 60 筆、`/assignments` 100 筆，而兩頁互相指向對方

`grades/page.tsx:21`、`:136-141`；`assignments/page.tsx:16`、`:192-197`。

第一週：兩頁都列得完，提示不會出現。
第五週：`/assignments` 越過 100。第三個月：`/grades` 上最舊的是兩週前的。
沒有分頁、沒有搜尋、沒有任何篩選，而兩頁的提示互相把人推給對方。

**開學第一個月的每一場考試，從第三個月起在畫面上不存在。**
資料完好，入口消失。這一項讓第 8、9 項從「不好做」變成「做不到」。

### 2. 沒有期末結算，而學年度不 scope 任何東西

`isCurrent` 唯一有行為的使用是 `NewClass.tsx:19` 的下拉預選。
`deactivateClass`（`roster.ts:124`）沒有呼叫端，班級沒有 `PATCH` 路由。

第一年：只有一個學年度，完全無感。
第二年開學：舊的 7 個班還在列表上、200 位學生的 `leftAt` 還是 null、
`listStudentTasks` 對每個人同時回新舊兩年的任務、
`/grades` 與 `/assignments` 的上限被兩年份的資料一起佔。
要收乾淨是 200 次確認對話框。

### 3. 沒有刪除、沒有保存期限、沒有匯出

`User.deletedAt` 從未被寫；`setStaffStatus` 擋掉學生（`staff.ts:386`）；
全 repo 零匯出。

第一個月：沒有人退補、沒有人要資料。
第三個月：十幾位退補學生的完整個資留在庫裡，帳號還登得進來，
而且每一份備份都帶著他們。第一位家長依個資法第 11 條來信時，
你**沒有任何動作可以做**。三年後要換系統時，資料只出得去 `pg_dump` 一條路。

### 4. 名冊變動會回溯改寫歷史統計

`countRecipients`（`assignment.ts:542`）與 `resolveRecipients`（`assignment.ts:440`）
即時計算，沒有快照。

第一週：名冊不動，數字穩定。
第三個月：插班 5 位、轉出 8 位、退補 12 位之後，
上個月那場段考的「派給 30 人」變成 27，而下個月又會變。
每一次都無聲。你在班務會議上報的數字，兩週後拿出來對不上。

### 5. MinIO 與備份只長不消

`deletePrefix` 只在上傳失敗的回滾裡（`api/import/route.ts:283`）；
排程備份每天全量複製整個 bucket（`entrypoint.sh:41`）；保留 30 天。

第一個月：3 份題本、120 張 PNG、備份每份 200 MB。
第三個月：40 份題本、1 600 張 PNG、**每一份每日備份帶著同樣的 1.6 GB，
存 30 份**。而 `backup.sh` 的空間檢查只算資料庫大小（`backup.sh:59-65`），
容器版連檢查都沒有。

### 6. 一個沒有畫面的稽核與一個沒有畫面的 AI 帳單

`audit_logs` 記得完整、`ai_usage_logs` 也記得完整，兩者都只能下 SQL。
`AiBudgetCounter` 是死表，`AI_PRICING` 預設空的所以成本欄永遠 0，
預算只在每個匯入工作的起點檢查一次（`import-pipeline.mjs:1099`）。

第一個月：AI 用量小、沒有人問稽核。
第三個月：帳單來了，你只有 token 數沒有金額；
家長申訴時你要現學五段 SQL 才查得到誰改了分數。

### 7. 授課老師進不去班級頁，於是密碼重設全落在主任身上

`classes/page.tsx:30` 與 `classes/[classId]/page.tsx:45-56` 都查 `ClassMembership`，
而 `assignSubjectTeacher`（`teaching.ts:100`）只建 `ClassSubjectTeacher`。

第一週：5 人次，主任處理得完。
第三個月：每週 5 人次已經累積成 60 次，
每一次都是「登入 → 猜他在哪個班 → 在 30 列裡找他」，而名冊沒有搜尋框。

### 8. `upgrade.sh` 的考試偵測查了一張不存在的表

`upgrade.sh:54` 查 `exam_sessions`，實際表名是 `attempts`。

第一次升級（沒有人在考試）：完全正常，畫面上看不出那一段被跳過。
第三個月的某次升級（剛好有一個班在考）：學生被直接踢出，
而 `OPERATIONS.md:174` 白紙黑字保證這不會發生。

### 9. 換老師的五個步驟裡有一個是不可見的

漏掉停用帳號 → 離職老師靠 `gradeScopeWhere` 的 `createdBy` 分支
（`scoring.ts:906`）永遠看得到他派過的每一份任務的完整成績。

一學期 1–2 次。發生的當下沒有任何症狀。

### 10. 姓名永遠改不掉，而錯字是累積的

第一份 200 人的名冊有 3 個錯字。第二學期又匯了 60 位新生，再多 1 個。
每一個都是永久的，而且補救（換學號）會把那個人的歷史成績切成兩半。

# 資料會真的掉的情境

以下每一條都是**確定的路徑**，不是理論風險。附上觸發條件與現有的防線。

### A. 回滾時保險備份失敗，然後照樣覆蓋

```
deploy/scripts/rollback.sh:66-68
"${YZ_SCRIPTS_DIR}/backup.sh" --tag "pre-rollback" --quiet >/dev/null \
  || warn "保險備份失敗，仍繼續回滾。"
...
deploy/scripts/rollback.sh:80
"${YZ_SCRIPTS_DIR}/restore.sh" "${BACKUP_PATH}" --no-safety-backup --yes
```

保險備份失敗只 warn，然後呼叫 `restore.sh` 時帶 `--no-safety-backup`
（那是對的，否則會備兩次）。**兩者合起來的結果是：
如果 `backup.sh` 失敗，「現在」的資料就沒有任何副本，而下一句直接覆蓋它。**

`backup.sh` 最常見的失敗原因是空間不足（`backup.sh:63-65` 的 die）。
而你什麼時候會回滾？升級出問題的時候。什麼常讓升級出問題？磁碟。
**這兩個條件會同時成立。**

對照組：`restore.sh:124-129` 對同一件事的處理是 `die "安全備份失敗。沒有退路就不做還原。"`
——同一個作者、同一個判斷、兩支腳本兩種結果。

**修法：`rollback.sh:68` 的 `warn` 改成 `die`，並提供 `--force` 讓人明確選擇。**

### B. 磁碟寫滿 → Postgres 停寫，而備份容器把它推得更深

WAL 歸檔只由備份容器清（`entrypoint.sh:56` 的 `prune_wal`，
在 `do_backup` 的最後一行 `:142` 才呼叫）。
備份失敗時 `do_backup` 在 `pg_dump` 那一步就 `return 1`（`entrypoint.sh:83-85`）——
**`prune_wal` 永遠跑不到。**

於是：磁碟滿 → 備份失敗 → WAL 不清 → 磁碟更滿。
而 `overdue()` 讓迴圈每約 90 秒重試一次 pg_dump（`entrypoint.sh:172-181`），
每次都在一台滿了的機器上寫暫存檔。

Postgres 寫不進 WAL 就停止接受寫入 → 考試中的每一次存檔失敗。
學生前端沒有本機持久化（無 IndexedDB／localStorage），
所以**那段時間寫的答案在關掉分頁的那一刻就沒了**。

**修法：`prune_wal` 移到 `do_backup` 外面、無條件執行；
失敗重試加指數退避；`doctor.sh:102` 的服務清單加 `backup`。**

### C. 備份天天失敗，而三個指示燈都是綠的

1. 容器 healthcheck 只看 `/tmp/backup-daemon-alive` 的新鮮度
   （`docker-compose.yml:479`），而心跳在迴圈裡無條件寫（`entrypoint.sh:180`）
   → 備份失敗不影響健康狀態
2. `doctor.sh:102` 的服務清單沒有 `backup` → 就算它 unhealthy 也不會被報出來
3. `doctor.sh:246-252` 的 `backup.age` 要**超過 48 小時**才報 fail
   （26–48 小時只是 warn）

唯一會發現的方式是有人主動跑 `doctor.sh`，而沒有任何排程會跑它。

**修法：備份失敗時寫一個 `/backups/.last-failure` 檔，
healthcheck 與 doctor 都檢查它；首頁待辦讀 doctor 的結果。**

### D. 物件儲存備份失敗只是一句 warn

```
deploy/scripts/backup.sh:113
  warn "物件儲存匯出失敗。題目文字仍在資料庫中，但**圖片與題本原檔不在這份備份裡**。"
deploy/backup/entrypoint.sh:31, 45
  log "未設定物件儲存，略過（還原時會缺少題本原檔與附圖）"
  log "物件儲存複製失敗"
```

備份照樣完成、照樣算數、`doctor.sh` 的 `backup.age` 照樣綠。
manifest 裡的 `includesObjects: false` 是唯一的痕跡，
而還原時 `restore.sh:265` 是 `[[ -d "${WORK}/objects" ]]` ——
目錄不在就**靜靜跳過**，不警告。

結果：還原完成、資料庫完好、題目文字都在，
**每一道「如右圖」的題目變成一片空白，每一份題本原檔消失**，
而完成訊息說「資料表 68 張、使用者 213 位」看起來完全正常。
`restore.sh:314` 有提醒「隨機開啟幾道題目，確認圖片顯示正常」——
但那是給人看的一句話，不是檢查。

**修法：manifest 記物件數量；還原時比對，缺了就 fail 而不是跳過。**

### E. `BACKUP_ENCRYPTION_KEY` 遺失 = 所有備份數學上無法還原

`backup.sh:146-155` 用 `openssl enc -aes-256-cbc -pbkdf2 -iter 200000`，
`BACKUP_ENCRYPTION_ENABLED=true` 是預設值（`.env:237`）。
`restore.sh:90` 沒有金鑰就 die。

`docs/UNINSTALL.md:146` 與 `DISASTER-RECOVERY.md:129-130` 都警告了
（「沒有那把金鑰，備份檔在數學上無法還原」），
`OPERATIONS.md:104` 也提醒輪替時要留舊金鑰。**但沒有任何機制。**
金鑰在 `.env` 裡，而 `.env` 只在**同一台機器上**——
機器毀了，備份也就毀了，就算異地複本還在。

`BACKUP_REMOTE_*` 四項在 `.env:241` 起全是空的（預設不設定異地備份），
所以預設狀態是：備份與資料庫在同一顆磁碟上，金鑰與備份在同一台機器上。

**修法：`doctor.sh` 加一項：`BACKUP_ENCRYPTION_ENABLED=true` 而
`BACKUP_REMOTE_ENDPOINT` 空的 → fail，訊息說「備份與資料庫在同一顆磁碟上」。
安裝流程強制要求把金鑰記到別的地方（打字確認一次）。**

### F. `docker image prune` 讓 tarball 部署的回滾變成死路

`rollback.sh:93-105`：找不到舊映像時要靠 `.git` 重建，
離線 tarball 部署（`INSTALL.md:326-337`）沒有 `.git` → `die`。

而 `docker image prune` 正是磁碟滿時最自然的第一個動作。
做完之後，如果那次升級有問題，你只剩 `--code-only`（保留新 schema、跑舊程式，
`rollback.sh:53-56` 自己警告「有風險」）或者從備份重建整台機器。

**修法：`upgrade.sh` 成功後把舊版映像 `docker save` 成一個檔案，
放在 `${BACKUP_DIR}/images/`，保留兩版。**

### G. 學期中把人移出班級，他的檢討入口消失

不是資料遺失，但對使用者是同一件事。

`listStudentTasks`（`attempt.ts:1252`）只認 `leftAt: null` 的班，
移出的那一秒他清單上該班的每一份考試消失。
`listOwnAttempts`（`result.ts:153-179`）不查班級，所以
`/take/[assignmentId]/result` 這個網址還打得開——但沒有任何一頁會給他那個網址。

**修法見第 2 項第 2 點。**

### H. 卡在 `IN_PROGRESS` 的作答，沒有人收就永遠算不出分數

`功能清單` 第十一節第 2 項已詳述。這裡補時間維度的部分：
首頁待辦會列出「N 份作答卡在進行中」（`app/(app)/page.tsx:221-232`），
但那個連結指向 `/grades` 列表，而列表沒有任何一欄說得出是哪一份任務有卡住的。

三個月之後，`/grades` 只列最近 60 份——**如果那份卡住的任務已經滑出 60 筆之外，
待辦上的數字會一直在，而你點過去永遠找不到它。**
學生寫過的答案還在資料庫裡，只是沒有任何路徑走得到。

**修法：待辦的連結直接帶篩選（`/grades?stranded=1`），
或在成績列表加一欄「卡住」。**

### I. 整班重設密碼之後離開頁面 = 30 個人明天登不進去

`resetClassPasswords`（`roster.ts:585`）在一個交易裡換掉全班的密碼雜湊，
明文只在那一次回應裡（`api/classes/[classId]/passwords/route.ts:65`）。
`ResetPassword.tsx:225` 有「列印這一頁」，但如果印表機沒紙、
或者有人不小心按了「完成」、或者瀏覽器當掉——**那 30 組密碼就沒了**。

不算資料遺失（再重設一次就好），但那一次的代價是隔天早上 30 個人同時登不進來，
而其中沒有一個人知道為什麼。防線已經很厚了（要打出班級名稱、
考試中一律拒絕、確認視窗說明後果），這裡只是提醒它是一個不可逆的動作。

**修法：列印之前不讓「完成」變成 primary；或者在關閉前再確認一次
「你已經印出來了嗎」。**

## 一句話總結

這套系統的**單次操作**幾乎每一項都做得對——交易邊界、稽核、確認視窗的措辭、
錯誤訊息裡的下一步，都比一般的自架系統好得多。

它缺的是**時間**：沒有一個地方承認「這件事會發生第兩百次」
（名冊變動、密碼重設、家長約談）、
「這份資料會累積三年」（分頁、保存期限、匯出、磁碟）、
或者「這一年會結束」（結算、升級、封存）。

如果只能修三件事，是這三件：
**第 7 項（重派，改動最小）、第 9 項的分頁與篩選（解鎖第 8 與第 9）、
以及 A 那條回滾的 `warn` 改成 `die`（防止唯一一條確定會掉資料的路）。**
