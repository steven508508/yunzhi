## 這份清單怎麼讀

這份清單的目的只有一個：**分清楚「業主現在按得到的功能」與「程式碼裡存在但按不到的東西」。**
這兩者在原始碼裡長得幾乎一樣，在驗收會議上卻是完全不同的兩件事。所以每一項功能後面
一定帶一個標註，三選一：

**可用** —— 使用者從畫面上點得到，而且整條路徑通到底。判定方式是從
`apps/web/app/(app)/**` 的頁面或元件往回追，確認真的有一個 `<Button onClick>`、
`<Form onSubmit>`、`<Link>` 或 server action 呼叫到那支 API，而那支 API 又真的
呼叫到 lib 函式。「lib 有 export」不算數。

**只有後端** —— lib 函式或 API 路由存在、邏輯正確、甚至有測試，但**畫面上沒有任何入口**。
要用它只能自己打 API 或改網址列。這一類東西在示範時看不出來，在驗收清單上卻常被寫成「有」。

**只有資料結構** —— `schema.prisma` 有欄位或 enum 值，但沒有任何一行程式寫入它。
資料庫裡那一欄永遠是預設值。這一類最危險：畫面上可能還有一欄在顯示它，
而它永遠顯示「—」。

逐項清點下來，明確標註的項目是 **可用 118 項、只有後端 30 項、只有資料結構 11 項**
（v0.20.0 時是 103／28／12）。另外還有 **18 張資料表**（原 19 張）
與 **17 個欄位或 enum 值**完全沒有任何程式寫入（第九節列出），
以及 **3 支 AI 端點**沒有任何呼叫端（第四節）。

> 上面這一段的數字是 **v0.21.0** 的。v0.27.0 的規模已經完全不同：
> 資料表 **68 張**、頁面 **47 個**、API 路由 **94 支**、`lib` 檔案 **92 個**、
> 單元測試檔 **41 個**、遷移 **16 份**（本節其餘的分類比例沒有重新盤點）。
> 這幾個數字是可以直接數出來的，所以先更新；「可用／只有後端／只有
> 資料結構」的分類要逐項追程式碼，沒有重驗就不改。

逐項證據在下面各節。最後一節「以為有、實際上沒有」列出業主或老師會合理期待存在、
但實際不存在的功能——**那一節比前面所有節都重要**，因為前面各節的每一個「可用」
都是真的，而真正會造成驗收爭議的是那些沒有被寫進任何清單的空缺。

## 一、頁面

**v0.21.0 時**系統共 22 個頁面：`(app)` 群組內 20 個（登入後、有導覽列），
群組外 2 個（`/login`、`/password`，刻意沒有導覽列）。

> v0.27.0 實際是 **47 個頁面**。下面這幾張表列的是其中 22 個，
> 中間五個版本新增的（智慧老師、能力分析、家長端、通知、監考、
> 升學輔導、級分預測、學習歷程）**沒有列進來**。

班級頁的「授課老師與導師」區塊是整套權限模型的接點，值得單獨說明。它畫成上下兩塊，
因為那是兩種不會互相涵蓋的職權：**授課老師**綁在「班 × 科」上（寫進
`ClassSubjectTeacher`），拿到的是那個班那一科的成績檢視與改分權；**導師**跨科目
（寫進 `ClassMembership`，`role: TEACHER`、`isHomeroom: true`、`leftAt: null`），
拿到的是班務權——改名冊、匯入名冊、重設全班密碼。兩者可以同時指派給同一個人。
只有管理員動得了這一塊，理由寫在 `apps/web/lib/teaching.ts` 的檔頭：指派發出去的是
權限而不是排課表。取消指派要走確認視窗並列出後果（那位老師從此看不到，而且不會收到通知），
指派則不用——指派錯了畫面上立刻多一列。

## 五、計分規則

### 5.1 逐題計分

| 題型 | 規則 | 出處 | 標註 |

### 5.2 三條貫穿的規則

**不確定就交給人，不猜。** 每個計分函式都可能回 `needsReview: true` 與
`earnedScore: null`。觸發條件包括：沒有標準答案、選項總數不明、標準答案指到不存在的選項、
作答選項編號超出範圍、選填格數對不上、寫法無法確定是否等值（`√2` 對 `1.414`、
`50%` 對 `0.5`、`Co` 對 `CO`）、版面快照對不上作答、不認得的題型。

**`scoreNote` 說人話。** 每一題都附一句解釋，例如
「答錯 1 個選項：(5 − 2×1)/5 = 3/5 的配分，得 3 分（滿分 5 分）」。

**`scoreNote` 不寫出正確答案。** 它存在 `AttemptAnswer` 上，
而解析何時放行由 `Assignment.releasePolicy` 決定；計分順手寫進答案等於繞過那個設定。

### 5.3 數值處理

答案文字正規化（`normalizeAnswerText:65`）做四件事：NFKC（全形數字、斜線、句點、加號）、
各種破折號與真減號 `−` 一律變 ASCII `-`、去掉所有空白（含全形）、頓號與全形逗號變半形。

數值比較用 **BigInt 有理數交叉相乘**（`parseRational:125`），不用 `parseFloat`——
`0.1 + 0.2 !== 0.3` 在計分上的後果是兩個數學上相等的答案被判不同，
而且只在特定數值上發生。單位保留不換算，`0.03公尺` 對 `3公分` 交給老師判。

分數收斂到小數第六位（`roundScore:218`），因為浮點加總會讓一份 60 題的卷子
變成「總分 79.99999999999999」。組卷畫面移除題目時的總分預覽也用同一支函式
（`Composer.tsx` 引用 `roundScore`）。

### 5.4 整份卷子

`gradeAttempt(items, answers)` 回傳每題結果與五個總計。
**`autoScore` 只加「這次真的算出分數的題」**——需人工確認與非選題的 `earnedScore` 是 null，
不當成 0 加進去，否則畫面上會出現一個看起來已經確定、其實還沒改完的分數。

寫回資料庫時（`lib/scoring.ts:230`）：

- 只寫 `isCorrect`、`earnedScore`、`scoreNote` 三欄，**學生選了什麼不會被改**。
- **「不確定」不可以蓋掉「有人確定過」**：`row.earnedScore !== null` 的題目重算時保留原分數並計入總分。
- 還有 `pendingManual` 或未解決的 `needsReview` 時，狀態停在 `SUBMITTED` 而不是 `GRADED`——
  一份含作文的卷子只算完客觀題就標「已評分」，那 25 分永遠不會被補上。

### 5.5 級分與五標

| 能力 | 規則 | 標註 |
|---|---|---|
| 各科學測滿分 | `GSAT_FULL_SCORE`：國文／英文／數A／數B 100、**社會 144、自然 128**。查不到回 `null`，**絕不預設 100**。權威來源是 `Subject.gsatFullScore`，這份表是後備。 | 可用 |
| 級距 L | 該科到考考生前 1% 的平均原始總分 ÷ 15，算到小數第五位。**同分的人一起算**（300 人取前 3 名，若第 3、4 名同分則取 4 個）。 | 可用 |
| 級分換算 | `min(15, ceil(X / L))`。`min` 那一項是定義的一部分不是保險——L 必然使 `15L < 滿分`，高分群照定義寫會算出 16、17 級分。`ceil` 帶 epsilon，避開分界點的浮點誤差。 | 可用 |
| 小樣本三層策略 | 到考 ≥ 300（`MIN_COHORT`）→ `COHORT` 用本次分布；人數不足但有歷史錨定級距 → `HISTORICAL_ANCHOR` 標為**估計值**；兩者皆無 → `UNAVAILABLE`，改給百分位。 | 第一與第三層可用；第二層見下 |
| 歷史錨定級距 | `gsatLevels(scores, { anchorInterval, difficultyFactor })`。`lib/scoring.ts:794` 呼叫時**沒有傳第二個參數**，所以 `anchorInterval` 恆為 null。這條路徑在正式環境永遠走不到。 | 只有後端 |
| 累計百分比 | `percentileOf`，與大考中心的「累計人數百分比」同一慣例。班級成績表的「百分位」欄用它。 | 可用 |
| 級分對照表 | `levelTable` 產生每一級對應的原始分區間（左開右閉，與官方一致）。沒有任何畫面顯示。 | 只有後端 |
| 五標 | `fiveStandards`：頂標第 88 百分位、前標 75、均標 50、後標 25、底標 12 的考生級分，不含缺考生。受同樣的最小樣本限制。沒有任何呼叫端。 | 只有後端 |

實務上班級人數幾乎一定不足 300，所以成績頁的級分區塊多半顯示「人數不足」。
**那不是缺陷，那就是它要說的話**——給出一個不可靠的級分，學生會當真並據以填志願。

## 六、權限模型

### 6.1 六種角色

`SystemRole` 有六個值：`STUDENT`、`GUARDIAN`、`TEACHER`、`SUBJECT_LEAD`、
`SCHOOL_ADMIN`、`SYS_ADMIN`。

判定散在四個地方，但它們共用同一份底層規則：

- `lib/nav.ts` —— 導覽列與區域存取。`navFor()` 決定畫哪幾個連結，`mayUse()` 決定要不要擋，
  **是同一份清單**。只藏連結不擋頁面的話，學生把網址改成 `/bank` 就看得到整個題庫。
- `lib/auth.ts` —— `canEditSubject`（科目職權）、`isHomeroomOf`（導師職權）。這兩種會重疊。
- `lib/scope.mjs` —— 純函式，有 21 項測試。`subjectScope` 回 `null` 代表不受科目限制；
  **認不得的角色回空陣列而不是 null**，權限預設往「看不到」倒。
- `lib/scoring.ts` / `lib/assignment.ts` —— 把上面的規則套進 Prisma 查詢
  （`gradeScopeWhere`、`assignableClassIds`）。

### 6.3 那個前提現在成立了

上表中所有標「◐」的格子，判定依據都是 `ClassSubjectTeacher`（科目授課名單）
或 `ClassMembership.isHomeroom`（導師）。在 v0.20.0 這兩張表**沒有任何程式會寫入**，
所以整欄「老師」實際上是空的：一個 `TEACHER` 帳號登得進來，但每一頁對他都是空的。
v0.21.0 補上了寫入端，這一節記錄重驗的結果——因為「有一個指派畫面」與
「那個畫面真的接到權限判定」是兩件事，而中間任何一環接錯，症狀都是
「指派了但他還是看不到」，沒有錯誤訊息。

逐條追下來，三條路都通：

| 判定 | 讀什麼 | 誰寫進去 | 對得上嗎 |
|---|---|---|---|
| `lib/auth.ts` 的 `canEditSubject` | `classSubjectTeacher` 有沒有 `{userId, subjectId}` | `lib/teaching.ts:119` 的 `assignSubjectTeacher` 寫 `{classId, subjectId, userId}` | 對得上。**注意它不看 classId**——指派一個班的化學，就取得化學科全域的出題與校對權（`lib/auth.ts` 的檔頭寫明這是刻意的）。 |
| `lib/scope.mjs` 的 `subjectScope` ／ `lib/scoring.ts` 的 `teachingSubjectIds` | `classSubjectTeacher` 依 `userId` 取 `distinct subjectId` | 同上 | 對得上 |
| `lib/scoring.ts` 的 `gradeScopeWhere`、`mayGrade`、`mayViewGrades` | 建立在 `teachingSubjectIds` 上 | 同上 | 對得上 |
| `lib/assignment.ts` 的 `assignableClassIds` | `classSubjectTeacher` 的 `classId`，**聯集** `classMembership` 中 `role != STUDENT` 且 `leftAt: null` 的 `classId` | 前者同上；後者由 `lib/teaching.ts:200` 的 `setHomeroom` upsert `{role:'TEACHER', isHomeroom:true, leftAt:null}` | 對得上 |
| `lib/auth.ts` 的 `isHomeroomOf` | `classMembership` 的 `{userId, classId, isHomeroom:true, leftAt:null}` 三個條件 | `setHomeroom` 寫的正是這三個 | 對得上 |

取消的那一側也對：`removeSubjectTeacher` 直接 delete 那一列（`teaching.ts:158`），
而 `clearHomeroom`（`teaching.ts:230`）**同時**把 `isHomeroom` 關掉並寫 `leftAt`。
第二點是必要的：只關 `isHomeroom` 的話，那一列仍然是 `role != STUDENT` 且 `leftAt: null`，
`assignableClassIds` 會繼續把這個班算成他派得了卷的班——也就是導師欄上已經沒有他，
他卻還派得動這個班的任務。那種「看起來取消了、實際上沒取消」的權限最難發現，
而原始碼的註解顯示這一點是被想過的。

至於帳號本身：`lib/staff.ts:171` 的 `createStaff` 是正式程式碼裡第二個
`user.create`（另一個是名冊匯入，只建 STUDENT），能建出 `TEACHER`、`SUBJECT_LEAD`、
`SCHOOL_ADMIN`、`SYS_ADMIN` 四種（`ASSIGNABLE_ROLES`），而且 `STUDENT` 與 `GUARDIAN`
被明確排除。所以「老師」那一欄現在是真的。

### 7.4 上傳把關

`POST /api/import` 的檢查順序（`app/api/import/route.ts`）：

1. 學生與家長直接 403。
2. `Content-Length` 先擋一次（500 MB），避免把 500 MB 讀進記憶體才發現超量。
3. 檔案數 ≤ 10、單檔 ≤ 200 MB、合計 ≤ 500 MB。
4. **魔術位元組判定格式**（`lib/filetype.ts`），不信任副檔名。支援 PDF、JPEG、PNG、
   WebP、HEIC、DOCX／ODT（ZIP 容器是唯一需要副檔名輔助的情況）。
   被拒時給的是具體建議，不是「不支援的格式」——`.doc`、`.rtf`、`.html`、`.zip` 各有一句話。
5. Content-Type 與副檔名依**內容**決定，不用使用者給的。
6. 權利聲明驗證（`lib/rights.ts` 的 `validateDeclaration`）：出版社掃描不得設為可匯出、
   只有歷屆試題可以設為公開，資料庫層另有 CHECK 約束擋同一件事。
7. SHA-256 重複偵測，除非勾了 `allowDuplicate`。
8. 失敗時 `deletePrefix` 清掉已上傳的部分。

標註：**可用**。`tests/upload-guards.test.mjs` 有 11 項，e2e 另有 4 項驗資料庫層的授權約束。

### 7.5 解析的權利控管

`Explanation` 分 `rawBody`（匯入原文）與 `layers`（結構化分層）。
學生的檢討頁 `lib/result.ts` 的 select **根本沒有 `rawBody` 那一欄**，
所以畫面上顯示的一律是 `layers`。

`licenseScope = TENANT_NO_EXPORT` 的解析在畫面上不提供複製、下載、列印的便利功能，
列印時整塊解析不出現，只留一行「這一題的解析只授權線上閱讀，不列印」。
這擋不住截圖，也不打算擋——它要做到的是**系統本身沒有幫忙散布**。

權利基礎為 `UNVERIFIED` 的原文詳解**一個字都不顯示**（資料庫的
`explanations_unverified_must_rewrite` CHECK 擋的就是這件事），
畫面顯示「這一題的詳解還在整理中」。標註：**可用**（但見第十一節第 7 項）。

每一份解析下方標示來源：本班老師撰寫／大考中心參考解答／AI 依原始詳解改寫／AI 生成／匯入的詳解，
並附模型名稱與出處。

### 8.3 背景工作者

`apps/web/scripts/worker.mjs` 註冊三個週期性工作，全部**跨租戶**執行

| 工作 | 間隔 | 做什麼 |
|---|---|---|
| `cleanup-sessions` | 10 分 | 刪除過期 session |
| `unlock-accounts` | 5 分 | 解鎖已過鎖定期的帳號 |
| `detect-stuck-imports` | 5 分 | 找出因行程被 kill 而永遠停在中間狀態的匯入，標成失敗並寫明原因。**不自動重跑**——重跑要花錢，該由人決定。 |

細節與仍然沒解決的部分見第十一節第 2 項。

| 姓名打錯了改不掉 | 改得掉。`PATCH /api/staff/[userId]` 現在收 `displayName`／`username`／`email` |

另外，v0.21.0 沒有的**學習歷程輔助與面試準備**也上線了（4 個頁面、9 支 API）。

> 上面這張表只確認到「畫面、API、lib 三層都在」。**它不等於「功能正確」**
> ——那要靠 `tools/` 底下那十三支端到端測試，而那些測試在 v0.27.0
> 之前沒有被任何 runner 或 CI 跑過（見下面第 4 項）。

### 還沒有補上的

#### 1. 校對介面仍然只能改答案，不能改題幹

`saveReviews` 的白名單（`lib/candidates.ts`）允許改 14 個欄位，
但 `Review.tsx` 只送兩種東西：`state`（校畢／存疑／刪除）與 `answerKeys`
（全檔唯一的一處 `patch(...)`）。題幹、題型、配分、選項、知識點在校對
畫面上仍然是唯讀。

**但這一項的後果比 v0.21.0 輕**：入庫之後 `/bank/[questionId]` 已經編輯得動，
所以 AI 抽錯題幹不再是「只能重新匯入一次」，而是「先入庫再改」。
出版社專屬題型的確認也有畫面了（`CustomTypes.tsx`）。

#### 2. 未確認權利的詳解仍然停在「整理中」

匯入時權利基礎是 `UNVERIFIED` 的話，`lib/commit.ts` 會把
`qualityFlags.explanationPendingRewrite` 設成 true，學生的檢討頁顯示
「這一題的詳解還在整理中，整理好之後會出現在這裡」（`lib/result.ts` 讀它）。

**全 repo 仍然沒有任何一行把這個旗標清掉。** 所以那句「整理好之後會出現」
還是一個不會兌現的承諾。

#### 3. 監控堆疊仍然收不到任何指標，告警也沒有出口

這一項在 v0.27.0 **只做了誠實化，沒有做功能**：

- `web:3000/api/metrics` 與 `ai:8000/metrics` 兩條路由仍然不存在
- compose 裡仍然沒有 `postgres_exporter`、`node_exporter`、Alertmanager
- `loki` 有起，但仍然沒有 Promtail 或任何 log shipper，所以 Loki 是空的
- `.env` 的 `ALERT_WEBHOOK_URL` 仍然標著【尚未實作】

差別在於 `deploy/monitoring/prometheus.yml` 不再去抓不存在的目標
（那會讓 `up` 永遠是 0、「服務不可用」永遠亮紅燈），`alerts.yml` 的六條
規則全部改成註解並寫明「要打開需要先有什麼」。

**現在真正在做健康檢查的是 `./deploy/scripts/doctor.sh`**，而它要人自己跑
或自己排進 cron（`docs/OPERATIONS.md` 的監控一節有現成的 cron 設定）。

#### 4. 端到端測試在 v0.27.0 之前沒有人在跑

`tools/` 底下有十三支端到端測試，而 `npm run test:e2e` 只跑得到其中兩支；
另外十一支沒有被任何 shell 或 npm script 引用，也不在 CI 裡。
於是那三百多項只有在有人記得手動一支一支跑的時候才會被執行，
而部署文件把它們寫成「全過」。

v0.27.0 起 `tools/e2e-import.sh` 用萬用字元把十三支全部跑完（一支失敗
就整體失敗並印出是哪一支），並加進 CI 的 `e2e` job。
`tools/deploy-check.mjs` 另有一項會擋下「新增一支卻沒有人跑」。

## 附錄：判定方法

**「可用」怎麼判的。** 從 `apps/web/app/(app)/**` 與 `apps/web/components/**` 抓出
所有 `fetch(` 與 `submitJson(` 的目標，逐一對回 `apps/web/app/api/**/route.ts`；
server action 則從 `'use server'` 往回找呼叫它的 `<Button onClick>` 或 `<Form onSubmit>`。
`lib` 有 export 但沒有走到畫面的，一律不算。

**「只有後端」怎麼判的。** 對 `apps/web/lib/*.ts`、`*.mjs` 的每一個 export
跑一次全 repo 的 word-boundary 搜尋（排除 `node_modules`、`.next`、定義檔本身
與它的 `.d.ts`），再逐一確認呼叫端是不是測試或死碼。
**搜尋結果不截斷**——ripgrep 的輸出順序在多執行緒下不固定，接一個 `head -N`
就可能剛好把唯一的那個真呼叫端切掉，判成死碼。這一版是踩過之後才發現的。

**「只有資料結構」怎麼判的。** 對 `schema.prisma` 的 48 個 model 各跑一次
`\.<camelCase>\s*\n?\s*\.(create|createMany|update|updateMany|upsert|delete|deleteMany)`
（跨行，因為 `tx.questionKnowledgePoint` 那一類的鏈式呼叫會換行）
與巢狀寫入 `<field>:\s*\{\s*(create|connectOrCreate|createMany|upsert)`，
排除 `.sql`、`.prisma` 與這份文件本身，再手動把測試夾具（`tools/e2e-*`、
`tools/commit-shim.mjs`、`apps/web/tests/`）的命中剔掉——**只有正式程式碼的寫入才算數**。

**測試數量怎麼來的。** Node 是實際執行 `node --experimental-strip-types --test
apps/web/tests/*.test.mjs` 的輸出（`# tests 269 / # pass 269`）；
Python 是 `grep -c "^def test_"` 的加總；e2e 是 `grep -c "await test('"` 的結果
（`tools/` 自 v0.20.0 以來沒有變動，所以 52 與 22 這兩個數字沿用）。

**RLS 涵蓋範圍怎麼來的。** 實際執行 `node tools/rls-check.mjs --static`，
輸出為「共 48 張表：租戶表 1、直接 21、間接 22、全域 4」，全部通過。
