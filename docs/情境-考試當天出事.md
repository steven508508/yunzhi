# 情境測試：考試當天在現場處理狀況

**受測者設定**：週五 14:00，高三忠 32 人在教室考數學模擬考，60 分鐘 25 題，
用 iPad 與自己的手機。**監考的是數學老師（`TEACHER`，透過 `ClassSubjectTeacher`
指派教高三忠的數學，不是這個班的導師）**，主任（`SCHOOL_ADMIN`）在辦公室待命。
考卷派出去時用的是預設值：`mode = EXAM`、`releasePolicy = ON_DUE`、
`maxAttempts = 1`、不隨機、不遲交。

**時間壓力**：考試進行中，每一件事只有幾分鐘可以處理，而且全班在等。
所以這一份問的不是「系統做不做得到」，是**「監考老師一個人、三分鐘內，
在他登入得進去的那幾個畫面上，做不做得完」**。

**測試方式**：唯讀走查 v0.21.0 的程式碼，逐條追到畫面上有沒有那顆按鈕、
按得動按不動。沒有修改任何程式，沒有連外網。

**與其他文件的關係**：

- `功能清單.md` 第十一節列的是「以為有、實際沒有」的功能缺口。這一份問的是
  **那些缺口在考試當天的哪一分鐘會現形，以及現場的人當下有沒有別的路走**。
  §11-1（不能改標準答案、不能送分）與 §11-2（卡住的作答找不到）是這一份裡
  第 12、13、10 三個狀況的骨架，但那一節沒有說**老師在現場會先走哪幾條死路**，
  而走死路的時間就是全班在等的時間。
- `情境-出卷派卷.md` 走的是考前一週，`情境-學生應考.md` 走的是學生自己的手機。
  兩份都已經很完整，重疊處只註記關聯不重寫。特別是：卡點 27（忠班放行洩題給孝班）
  在本文第 15 條裡只補一件事——**考完那一刻老師手上還有沒有補救的動作**。

# 開考前

## 狀況 1｜兩位學生說登不進去

### 狀況

13:55，兩位學生舉手說登不進去。有四種可能：密碼打錯、帳號被鎖、
家長同意沒登錄、帳號停用。

### 你會怎麼做

走過去看他們的螢幕，然後去名冊上查那兩位的帳號狀態。

### 實際上做不做得到

**看螢幕這一步是有用的。** 伺服器區分五種結果，畫面上是三句話
（`app/api/auth/login/route.ts:38-46`）：

| 伺服器判定 | 學生螢幕上的字 |
|---|---|
| 帳號不存在（`lib/password.ts:59-63`） | 帳號或密碼不正確 |
| 密碼錯（`lib/password.ts:78-91`） | 帳號或密碼不正確 |
| 帳號被鎖（`lib/password.ts:65-68`） | 連續登入失敗過多，請於 **N** 分鐘後再試 |
| 家長同意未登錄 → `PENDING_CONSENT`（`lib/password.ts:70-72`） | 此帳號目前無法登入，請洽管理員 |
| 帳號停用 → `SUSPENDED` | 此帳號目前無法登入，請洽管理員 |

後兩種在畫面上一模一樣，但**學生帳號實際上停用不了**——`/settings/staff`
明確拒絕非教職員帳號（`lib/staff.ts:387-392`：「這一頁動不了它」），
而系統裡沒有任何一支把學生設成 `SUSPENDED` 的路徑。所以第四句話在學生身上
只會是「家長同意沒登錄」。**四種原因現場分得出來，這一點是好的。**

**壞的是接下來那一步。** 兩種修法都在班級名冊頁上：

- 登錄家長同意 → `ConsentButton`（`app/(app)/classes/[classId]/page.tsx:144`）
- 重設密碼 → `ResetOne`（同檔 `:179`）

而**監考的數學老師打不開那一頁**。`app/(app)/classes/[classId]/page.tsx:45-55`：

```ts
const mine = await prisma.classMembership.findFirst({
  where: { classId, userId: user.id, leftAt: null },
  select: { id: true },
});
if (!isAdmin && !mine) return <Denied ... why="你不在這個班的名冊裡。" />;
```

授課老師的指派寫的是 `ClassSubjectTeacher`（`lib/teaching.ts:119`），
**不寫 `ClassMembership`**（那一張只有導師指派 `lib/teaching.ts:200` 與
名冊匯入 `lib/roster.ts:345` 會寫）。所以科任老師的 `mine` 是 null，
整頁被擋。而 `/classes` 列表對他也是空的（`app/(app)/classes/page.tsx:27-29`
只查 `memberships: { some: { userId } }`），畫面上寫「你還沒有帶任何班」。

更刺眼的是：**這兩支 API 本來就允許 `TEACHER`**——
`app/api/students/[studentId]/password/route.ts:33` 的 `MAY_RESET` 含 `TEACHER`，
consent 那一支也是（`app/api/students/[studentId]/consent/route.ts:24`），
而且那支路由的檔頭寫著理由：「學生是在櫃檯或教室裡跟**現場的那一位老師**講的，
而要求他去找導師或管理員，等於這個功能在最需要的那一刻不存在」。
**規則寫對了，畫面把它關起來了。**

另外一個小陷阱：鎖定的失敗計數只有在**成功登入**或 worker 的
`unlock-accounts`（`scripts/worker.mjs:65-71`，每 5 分鐘一次）時才歸零。
15 分鐘的鎖到期後、worker 還沒跑到的那個空窗裡再打錯一次，
`failed = 5 + 1 >= MAX_FAILED`（`lib/password.ts:79-88`）→ **立刻再鎖 15 分鐘**。
學生會覺得「不是說 15 分鐘就好了嗎」。

### 花多久

打電話給主任，唸兩個學號，等他點兩下，再把新密碼唸回來給學生。**5–8 分鐘**，
而且要占用主任。如果主任剛好不在座位上，這場考試就開不了。

### 嚴重度

**嚴重**。不是資料錯，是現場的人沒有權限做一件他被授權做的事。
考試當天登不進去的人幾乎一定不只一個。

### 修法建議

1. `app/(app)/classes/[classId]/page.tsx` 的存取判定加上
   `classSubjectTeacher.findFirst({ userId, classId })`——與 `assignableClassIds`
   （`lib/assignment.ts:614-634`）同一個口徑：科任老師本來就派得了卷給這個班。
   `mayEdit` 是否也放寬可以再議，但**至少要看得到名冊與帳號狀態**。
2. 名冊表格加一欄「登入狀態」，顯示 `lockedUntil` 是否還在有效期內。現在
   `帳號狀態` 那一欄（`:157-166`）只看 `status`，被鎖的帳號顯示「可登入」。
3. `lib/password.ts` 的失敗計數在鎖到期後就該歸零，不要靠 worker 補。

## 狀況 2｜「我的清單裡沒有這份考試」

### 狀況

一位學生說 `/take` 上沒有這份數學模擬考。要判斷是他該收到而沒收到（系統的問題），
還是他本來就不在派發名單裡（派卷時漏掉了）。

### 你會怎麼做

去任務那一頁，打開這份任務，看派給了哪幾個班、名單裡有沒有他。

### 實際上做不做得到

**打不開。系統裡沒有「這份任務的內頁」。**

`/assignments` 是一張表，欄位是：任務、試卷、模式、**派給（一個數字）**、
開放→截止、時限、已作答、成績、操作（`app/(app)/assignments/page.tsx:200-269`）。
**沒有一欄說得出派給了哪幾個班。** 點任務名字沒有連結，點「調整」打開的是
設定對話框，而 `AssignmentTools.tsx` 從頭到尾沒有 targets 這個欄位
（`app/(app)/assignments/AssignmentTools.tsx:39-50` 的 `EditableAssignment`
只有 id / title / openAt / dueAt / allowLate / maxAttempts / releasePolicy / attempts）。

名單本身是算得出來的：`resolveRecipients`（`lib/assignment.ts:440-448`）
回的是完整的 `Recipient[]`，帶姓名、學號、**帳號狀態**、透過哪幾個班收到的、
是不是個別指定。它的檔頭寫著「這是唯一一份『這份任務派給了誰』」。

**而它只有兩個呼叫端**（全 repo 搜過）：`lib/attempt.ts:269`（判斷這位學生
開不開得了考卷）與 `app/api/assignments/[assignmentId]/route.ts:76`
——後者在 PATCH 之後把它算出來，然後 `return NextResponse.json({ recipients: recipients.length })`，
**只回一個數字，名單當場丟掉**。

沒有 `GET /api/assignments/[assignmentId]`。沒有 `/assignments/[assignmentId]` 頁面。
`app/(app)/assignments/` 底下只有 `page.tsx`、`NewAssignment.tsx`、`AssignmentTools.tsx`。

所以老師手上只有「派給 31 人」這個數字，而班上有 32 個人。**少的那一個是誰，
系統一個字都不說。**

繞路也繞不過去：班級名冊頁對科任老師是關的（狀況 1），
而且就算打得開，名冊上的是「這個班有誰」，不是「這份任務派給了誰」——
兩者在有個別指定或有人剛離班時就會不一樣。

### 花多久

**查不出來。** 現場唯一能做的是請那位學生先用別的方式應考（紙本），
考完再研究。

### 嚴重度

**阻斷**。這是派卷這條線上最後一個沒有出口的地方：
`情境-出卷派卷.md` 卡點 22 已經指出派完之後只給一個數字，
而本文要補的是——**那個數字對不起來的時候，現場沒有任何辦法往下追**。

### 修法建議

做一頁 `/assignments/[assignmentId]`，只要三塊：任務設定、**收件名單
（`resolveRecipients` 直接就是它的形狀，含 `status` 與 `classNames`）**、
以及每個人現在的作答狀態。這一頁同時解掉狀況 10 的「找不到是哪一份」。
`Recipient` 那個型別的註解（`lib/assignment.ts:415`）本來就寫著
「`PENDING_CONSENT` 的學生登不進來，**畫面上要標出來**」——
那個畫面到現在還沒有。

## 狀況 3｜時間設錯了，開考前五分鐘改得掉嗎

### 狀況

13:55 發現開放時間設成了明天 14:00。

### 你會怎麼做

到 `/assignments`，找到那一份，按「調整」，把開放時間改成現在，存檔。

### 實際上做不做得到

**做得到，而且是這 15 條裡最乾淨的一條。**

`AssignmentTools.tsx` 的「調整」對話框裡有開放時間與截止時間兩個
`datetime-local`（`:168-183`），送出走 `PATCH /api/assignments/:id`。
`updateAssignment`（`lib/assignment.ts:262-270`）明確把 `openAt` / `dueAt`
放在**不凍結**的那一組：

```ts
// 以下幾項在進行中改是正常的：延長截止、開放遲交、多給一次機會…
if (patch.openAt !== undefined || patch.dueAt !== undefined) { ... }
```

而且現在沒有任何人開始作答（`openAt` 在未來，`startAttempt` 的
`lib/attempt.ts:340-342` 會擋），所以 `started === 0`，連凍結欄位都動得了。

時區也對：`toLocalInput`（`AssignmentTools.tsx:60-65`）特地處理了
「不能直接 `iso.slice(0,16)`」那個會差八小時的坑，而且檔案裡寫了為什麼。

科目權限：`mayEdit(a.paper.subjectId)`（`app/(app)/assignments/page.tsx:110-111`）
→ 數學老師教數學，按鈕畫得出來；伺服器端 `canEditSubject` 再擋一次。

### 花多久

**40 秒。** 導覽列點「派卷」→ 最上面那一列（依 `createdAt desc` 排）
→ 調整 → 改一個欄位 → 儲存。

### 嚴重度

**輕**。唯一的殘留風險是狀況 2 的同一件事：畫面不說這一列是派給哪個班的，
所以同時派了忠孝仁三個班（三份任務）的時候，老師只能靠自己取的任務名稱分辨。
改錯一份不會有任何提示。

### 修法建議

`/assignments` 的表格加一欄「對象」，直接列班名。`countRecipients`
（`lib/assignment.ts:542-588`）已經把 `assignmentTarget` 整批查出來了，
順手帶回 `classId` 再 join 一次班名，不多一次往返。

# 考試中

## 狀況 4｜iPad 當機重開，「我前面寫的不見了」

### 狀況

14:20，一位學生的 iPad 白畫面重開。他重新登入、點回考卷，說前面寫的都不見了。

### 你會怎麼做

先讓他自己看畫面（其實答案應該還在），同時我自己去查伺服器上到底存了幾題。

### 實際上做不做得到

**學生那一側是對的。** `/take/[assignmentId]` 開機時先問
`GET /api/attempts?assignmentId=…`，拿到 `openAttemptId` 就直接接續，
**不重新呼叫開始作答**（`app/(app)/take/[assignmentId]/page.tsx:172-175`）；
伺服器端 `startAttempt` 也一樣，找到 `IN_PROGRESS` 且沒過期的就回
`resumed: true`，**絕不開第二份**（`lib/attempt.ts:354-361`，註解寫了為什麼）。
答案從 `loadAttemptForStudent` 重新灌回畫面，而且游標自動跳到第一題沒寫的
（`take/[assignmentId]/page.tsx:148-151`）。丟掉的只有當機前那 1.2–8 秒
還在防抖佇列裡的東西（`DEBOUNCE_MS = 1200`、`SAFETY_FLUSH_MS = 8000`，同檔 `:73-74`）。

**老師那一側看得到，但那個數字是錯的。**

`/grades/[assignmentId]` 有一塊「未完成的作答」
（`app/(app)/grades/[assignmentId]/page.tsx:287-372`），
在考試進行中列的就是全班 32 個人，每一列有：姓名、學號、
**已作答 N / 25**、開始時刻、狀態（作答中／時間到未交卷）。
這一塊做得很好——它甚至在「還沒有人交卷」那一支之前就渲染
（`:284-286` 的註解說明了為什麼）。

問題出在 N 怎麼算的。`lib/scoring.ts:701` 與 `:737`：

```ts
_count: { select: { answers: true } },
...
answered: a._count.answers,
```

**那是 `AttemptAnswer` 的列數，不是有寫東西的題數。** 同一個系統裡
`lib/attempt.ts:894-919` 的 `countAnswered` 是這樣算的：

```ts
function hasAnswer(r) {
  if (r.answerKeys.length > 0) return true;
  if (r.answerText && r.answerText.trim() !== '') return true;
  ...
}
```

兩種情況會讓列存在但沒有答案：

- **學生按了「標記待複查」**。`take/[assignmentId]/page.tsx:723` 送的是
  `{ flagged: !mine.flagged }`，`saveAnswer` 照樣 upsert 一列
  （`lib/attempt.ts:650-661`），`answerKeys` 是空陣列。
- **學生點了選項又點一次取消**。`pick()` 在單選重複點時回 `[]`
  （`take/[assignmentId]/page.tsx:414-416`），送出去把 `answerKeys` 覆蓋成空。

一份 25 題的卷子，學生標了 5 題待複查、清掉 2 題，
老師看到的是「已作答 18/25」而學生自己畫面上的計數是 11。**兩個都是系統算的。**

這個數字直接決定狀況 10 的判斷（「這一份收出來有沒有意義」，
`UnfinishedAttempt.answered` 的註解自己這樣寫，`lib/scoring.ts:635`），
也直接印在「代為結算」的確認視窗上（`Finalize.tsx:41-44`）。

另外：**這一頁不會自己更新**（`export const dynamic = 'force-dynamic'`
只保證每次請求重算，沒有輪詢）。監考老師要一直按 F5。

### 花多久

**1 分鐘**（找到任務 → 開成績頁 → 找那一列）。但拿到的是一個偏高的數字。

### 嚴重度

**嚴重**。不是因為它會讓誰少拿分，是因為**老師會照著它做決定**：
看到「已作答 22/25」就放心讓他繼續，實際上他只寫了 11 題。

### 修法建議

`classStats` 的 `openAttempts` 查詢把 `_count` 換成實際的
`answers: { select: { answerKeys: true, answerText: true, answerSlots: true } }`

## 狀況 5｜「我按交卷沒反應」

### 狀況

14:50，一位學生說他按了交卷，畫面沒有變化。要判斷他到底交了沒有。

### 你會怎麼做

重新整理成績頁，看他在「全班」那張表裡還是在「未完成的作答」裡。

### 實際上做不做得到

**判斷得出來，而且很快。** 兩張表是互斥的：
`classStats` 的 `attempts` 只查 `SUBMITTED / GRADED`（`lib/scoring.ts:668`），
`openAttempts` 只查 `IN_PROGRESS`（`:690`）。所以他一定只出現在其中一張裡，
不會兩張都有或兩張都沒有。

**但幫不了他。** 如果他還在「未完成」那一列，老師手上的按鈕是：

- **「代為結算」** — 畫不出來。`stranded` 為 false 時那一格顯示的是
  一段灰字「還在作答時間內」（`app/(app)/grades/[assignmentId]/page.tsx:347-351`），
  而且伺服器端也會拒絕：`checkFinalizeOnBehalf`（`lib/attemptClock.mjs:104-109`）
  回「這位學生還在作答時間內。現在收掉會把他正在寫的考卷抽走」。
  這個限制本身是對的（理由寫在 `:68-82`），但它的代價就是這一格。
- **「作廢這一份」** — 畫得出來，但那是把他的成績砍掉，不是幫他交卷。

好消息是**他的答案早就在伺服器上了**（自動存檔每 1.2 秒／保底 8 秒一次），
所以就算他一直交不出去，到 15:00 時間一到，那一份會變成 `stranded`，
老師按「代為結算」就會照常計分（`finalizeAttempt` 會把 `submittedAt`
回填成 `expiresAt`，`lib/attempt.ts:787-798`）。分數是對的。

要現場告訴他這件事，老師得自己知道上面這一整段。**畫面上沒有寫。**
那一列的狀態欄只寫「作答中 · 15:00 到期」。

### 花多久

**1 分鐘**判斷完，然後跟他說「你繼續寫，時間到我幫你收」。

### 嚴重度

**中**。成績不會錯，但現場的兩個人都不知道這件事會自己好。

### 修法建議

「未完成的作答」那一列，`stranded` 為 false 時把灰字從
「還在作答時間內」改成「還在作答時間內，{expiresAt} 之後可以代為結算」。
一句話的成本，換掉一次現場的慌張。

## 狀況 6｜第 12 題的選項有錯字

### 狀況

14:30，三個學生同時舉手：第 12 題選項 (3) 少了一個負號。

### 你會怎麼做

先判斷「改得掉嗎」，再判斷「該不該改」。

### 實際上做不做得到

**改不掉。兩條路都是死的。**

**路一：改題目本身。** 沒有任何畫面可以編輯一道已入庫的題目。
`/bank` 底下只有 `page.tsx`，是一張唯讀表格。校對介面（`Review.tsx`）
就算重新打得開（見狀況 12），改的也是 `ImportCandidate` 不是 `Question`。
全 repo 的 `question.update` 只有一處：`lib/commit.ts:309`，
而且它只寫 `qualityFlags`。`questionOption` 在正式程式碼裡連一次寫入都沒有
（只在 `tools/` 的測試夾具裡出現）。

**路二：把這一題從卷子上換掉。** `requireEditablePaper`
（`lib/paper.ts:562-578`）擋死：

```
「數學模擬考」已經有 32 人開始作答（…），現在改題目，
改之前與改之後的人拿到的會是不同的卷子…
```

**而「該不該改」這個問題有一個反直覺的答案：即使改得掉，也不該用改題目的方式。**

`Attempt.layout` 這個快照擋得住的東西**比想像中少**。它存的是
`questionId / order / score / optionOrder`（`lib/attempt.ts:123-138`）——
**題號、配分、選項的先後順序**。它**不存題幹與選項的文字**：
`loadAttemptForStudent`（`:997-1017`）每次都從 `Question` 現查 `content` 與
`options.content`。所以：

| 改什麼 | 快照擋得住嗎 | 對已經寫過那一題的人 |
|---|---|---|
| 改錯字（選項文字） | **擋不住** | 下次重新整理就看到新的文字，答案不動。這一種其實是安全的 |
| 改配分 | 擋得住 | 沿用開始作答時的分數 |
| 改題序、選項順序 | 擋得住 | 完全不受影響 |
| **刪一個選項** | **擋不住，而且靜默** | `orderOptions`（`lib/attempt.ts:1140-1144`）遇到快照裡有、題庫裡沒有的選項直接 `continue`——**那個選項從畫面上消失，而學生已經存下的 `answerKeys` 還指著它**，計分時判成答錯 |
| **改標準答案** | 不適用 | 計分時現查（`lib/scoring.ts:174-185`），全班一起變 |

也就是說：**改一個錯字是這幾件事裡唯一安全的，而它偏偏是唯一被完全擋死的。**

### 花多久

不用花時間，因為沒有入口。現場唯一能做的是走到黑板前面大聲說
「第 12 題選項三，那個 2 前面要有負號」。

### 嚴重度

**嚴重**。25 題的模擬考裡有一題印錯，這是每次都會發生的事。
口頭更正在 32 人的教室裡有效，在線上分散作答時無效。

### 修法建議

不要做「考試中改題目」——那個決定是對的。要做的是**「這一題有勘誤」的公告機制**：
`Assignment` 上加一個 `notice` 欄位，老師在成績頁或任務頁打一句話，
作答畫面在題號欄下方顯示一條紅色橫幅，`getAttemptStatus`（每 30 秒的校時，
`lib/attempt.ts:543-561`）順手帶回來就好——那支 API 本來就每 30 秒跑一次，
而且刻意做得很輕。這比「能改題目」安全得多，也解決得了同一個現場問題。

### 狀況

14:35，走到後排看到一位學生的 Safari 開了第二個分頁在查 Google。

當場把他那一份作廢，並且讓他馬上登出。

`/grades/[assignmentId]` → 「未完成的作答」那一列 → 「作廢這一份」

if (attempt.status !== 'IN_PROGRESS') {

`attemptVoid.mjs:75-77` 的檔頭斷言「`saveAnswer` 與 `submitAttempt` 都會回
『這份作答已經被作廢，請找老師處理』」，**那句註解是錯的**。

實際後果：作弊的學生看到「這份考卷已經交出去了」，會以為自己不小心按到交卷，
然後舉手說系統壞了——而老師這時正打算不動聲色。

### 花多久

**2 分鐘**（開成績頁 → 找那一列 → 打理由 → 確認）。

**中**。處置本身完整（不佔作答次數、可撤銷、有稽核），只是訊息說錯話，

1. `saveAnswer` 的狀態檢查分開 VOIDED：

2. 把 `revokeAllSessions` 接到作廢那條路徑上，或者在成績頁加一顆
   「讓這位學生登出」。作弊處置的下一步本來就是把人請出考場。

## 狀況 8｜全班網路斷了 10 分鐘，要延長時間

### 狀況

14:25 到 14:35，補習班的網路整個斷掉。恢復之後全班要求延長 10 分鐘。

### 你會怎麼做

到任務設定裡把作答時限從 60 分改成 70 分。

### 實際上做不做得到

**完全做不到，而且是兩層都做不到。**

**第一層：`timeLimitMin` 在有人開始作答之後就凍結了。**
`lib/assignment.ts:232-237` 把它交給 `guard()`，`:251-258` 直接丟例外：

```
已經有 32 人開始作答，作答時限不能再改了——
改了之後，已經開始的人與還沒開始的人拿到的是不同的考試…
```

`AssignmentTools` 甚至不畫這個欄位，理由寫在檔頭 `:18-27`：
「把那幾欄畫出來再讓伺服器擋，等於請老師去試」。

**第二層（更關鍵）：就算凍結解開了，也沒有用。**
`expiresAt` 在開始作答的那一刻算好寫死（`lib/attempt.ts:399-418`）：

```ts
const bounds = [];
if (assignment.timeLimitMin) bounds.push(now.getTime() + timeLimitMin * 60_000);
if (assignment.dueAt && assignment.dueAt > now) bounds.push(assignment.dueAt.getTime());
const expiresAt = bounds.length ? new Date(Math.min(...bounds)) : null;
```

全 repo 搜過 `expiresAt`：**它只被寫入這一次**（`:418`），之後所有地方都是讀。
沒有任何一支函式會在任務設定變動之後重算已經開始的作答的到期時刻。

這件事有一個更嚴重的推論，而且它打到的是一個**被文件明確宣傳的功能**。
`lib/assignment.ts:24-25` 寫著：

> 沒鎖住的是截止時間、遲交、次數、解析開放時機與派發對象——那幾樣
> **本來就是要在進行中調整的**（最常見的請求就是「再延一天」）。

**「再延一天」對已經開始作答的人沒有作用。** 一份沒設時限、只設截止時間的作業，
學生 20:00 開始寫（`expiresAt` = 當時的 `dueAt` = 23:00），老師 22:00 把截止
延到明天——他的 `expiresAt` 還是 23:00，23:00 一到就寫不進去了。**延長只嘉惠
還沒開始的人。** 而畫面上老師看到的是「已延長」，學生看到的是「時間到」。

反方向也一樣：`AssignmentTools.tsx:181` 的提示寫著
「要立刻結束這場考試，把它改成現在」，`assignment.ts:394-397` 的錯誤訊息也這樣說。
**那不會停止正在寫的 32 個人**——`attemptWritable`（`lib/attemptClock.mjs:47-51`）
只看 `attempt.expiresAt`，不看 `assignment.dueAt`。它只擋得住還沒開始的人。

### 花多久

**沒有可以花的時間。** 現場唯一的處置是宣布這 10 分鐘算在考試裡，或者
把整場作廢重考（32 次「作廢這一份」，每次要打理由，加上再約一個時段）。

### 嚴重度

**阻斷**。補習班的網路是熱點分享（`情境-學生應考.md` 的設定：20–50 Mbps
分給 50 台 iPad），斷線不是意外，是週期性事件。而「延長時間」是監考老師
在紙筆時代每學期都會做好幾次、成本是講一句話的事。

### 修法建議

1. `Attempt` 加一欄 `extraSeconds`（預設 0），`attemptWritable` 與
   `remainingSeconds` 一律用 `expiresAt + extraSeconds`。成績頁的
   「未完成的作答」區塊加一顆「全部延長 N 分鐘」，寫稽核。
   這不會讓「已開始的人與沒開始的人拿到不同考試」——它讓**所有人**
   都多 N 分鐘，那正是老師要的。
2. 順手修「再延一天」：`updateAssignment` 改動 `dueAt` 時，把
   `attempt.expiresAt === 舊的 dueAt` 的那些 `IN_PROGRESS` 一起更新。
   或者更乾淨——`attemptWritable` 同時看 `assignment.dueAt`，讓到期時刻
   變成 `min(expiresAt, dueAt)` 的即時計算而不是快照。
   **這一條要修，不然那句「最常見的請求就是再延一天」是一個沒有兌現的承諾。**

14:40，一位學生說很不舒服要去保健室，這一份不算，下週補考。

- 延後截止時間會連帶把**全班的解析開放時間**往後推——`releasePolicy = ON_DUE`

- 撤銷作廢那一顆的說明寫得很誠實：沒交過卷的撤銷之後回到 `IN_PROGRESS`，
  而「作答的時鐘在作廢期間照樣在走」（`Void.tsx:180-186`）。
  所以正確做法就是**留著作廢、讓他重新開始**，而畫面上就是這樣寫的。

### 花多久

**3 分鐘**（作廢 2 分 + 改截止 1 分）。

### 嚴重度

**輕**。功能完整、訊息誠實、預設值安全。唯一的缺口是上面那個
「延後截止會延後全班的檢討開放」沒有被說出來。

### 修法建議

改截止時間的對話框，若 `releasePolicy === 'ON_DUE'` 而且已經有人交卷，
加一句：「這份任務設定為截止後開放檢討。往後延會讓已經交卷的 {n} 位
學生多等到 {新截止}」。判斷用現成的 `releaseControl` 就好。

把 `submittedAt` 回填成 `expiresAt`（不收遲交時），所以成績單上不會出現
一段沒有作答發生的空白區間，遲交統計也不會誤判；
接著 `gradeOnSubmit` 自動計分（`:841`），沒寫的題目一律 0 分。

**有一個情況會走進死路。** 如果這份任務**既沒設時限也沒設截止**
（`NewAssignment.tsx:54-56` 三個欄位的預設值都是空字串），
學生開始作答時 `expiresAt` 是 `null`。這時：

- 首頁待辦**算他卡住**（`page.tsx:228-231` 的 OR 條件包含
  `assignment: { allowLate: false, dueAt: { lt: now } }`）
- 成績頁**不算他卡住**（`attemptStranded`，`lib/attemptClock.mjs:64-66`，
  只看 `expiresAt`；null → `attemptWritable` 為 true → 不是 stranded）
- 所以那一列顯示的是灰字「還在作答時間內」，**沒有代為結算鈕**
- 而且 `checkFinalizeOnBehalf`（`:95-103`）會回：
  「這一份沒有作答時限也沒有截止時間…**要結束這場考試，請把任務的截止時間改成現在**」

**——而那正是老師剛剛做過的事**（他為了結束考試才去改截止時間，
首頁才因此把這幾份算成卡住）。錯誤訊息叫他去做一件他已經做完的事，
而做完之後這一格還是不動。兩個畫面對同一件事給出相反的答案。

### 花多久

知道是哪一份：**3–4 分鐘**（含 3 次確認視窗）。
不知道是哪一份（週一早上）：逐份點開，60 份任務最壞要點 60 次。
踩到上面那個死路：**永遠出不來**，除非進資料庫。

### 嚴重度

**中**（知道是哪一份時）／**阻斷**（踩到 `expiresAt = null` 那一格時）。

### 修法建議

1. `/grades` 加一欄「卡住」。`gradeScopeWhere` 那一句本來就在查 assignment，
   多帶一個 `_count` 或一次 groupBy 就有。首頁那個連結才有意義。
2. **統一 stranded 的定義。** 首頁與 `attemptStranded` 現在是兩份實作，
   而 `attemptClock.mjs` 的檔頭正好在講為什麼不能有兩份
   （「三份各自寫一個 `if` 的話，最可能不一致的是邊界那一秒」）。
   正確的做法是讓 `attemptStranded` 也吃 `assignment.dueAt / allowLate`，
   首頁改成呼叫它。
3. 順帶解掉 `checkFinalizeOnBehalf` 那句自我矛盾的錯誤訊息。

### 實際上做不做得到

先講好消息：**這個錯誤是看得見的。** 各題答對率那張表的 `Rate` 元件

每次都從 `Question` 現查 `answerKeys`，**所以只要答案改得掉，
重新計分就會全班修正**。資料層完全準備好了。

**問題是那個「改」沒有任何入口。**

#### 死路一：題庫頁

`/bank` 底下只有 `page.tsx`，唯讀表格。沒有編輯、沒有詳情、沒有連結。

#### 死路二：組卷頁

#### 死路三：重新打開校對介面（**這一條最耗時間，因為它看起來會成功**）

`app/(app)/import/[jobId]/page.tsx:13` 的 `REVIEWABLE` 集合是：

```ts

```

**包含 `COMMITTED`。** 所以老師從 `/import` 點回那份已經入庫的題本，
校對介面完整地打開了。第 7 題在畫面上，答案欄可以點，
`patch({ answerKeys: keys })`（`Review.tsx:188`）送出去，

**寫入成功、沒有任何警告**。

按下去之後：`POST /api/import/[jobId]/commit` 查的是
`state: 'CONFIRMED', questionId: null`（`route.ts:35-37`）→ 0 筆 →

一樣一題都撈不到。）

所以老師的體驗是：**改了、存了、看起來成功了，然後入庫說「沒有題目」。**
題庫裡的 `Question.answerKeys` 一個位元都沒有動，而 `ImportCandidate` 上
現在存著一份與題庫不一致的答案。這是全流程裡最容易讓人以為自己修好了的地方。

#### 死路四：全班重新計分

`/grades/[assignmentId]` 的「全班重新計分」按得動，確認視窗甚至寫著
「這 32 位學生的分數會用**現在的標準答案**重新計算」，

> 例如「第 7 題標準答案原為 (2)，更正為 (3)」或「第 12 題全班送分」

**——系統用自己的 UI 文案描述了一個它做不到的動作。**
題目沒變，`gradeAttemptById` 重跑出來的結果與上次逐位元相同。
稽核裡會留下一筆 `grade.recalculate`，`changed` 是空陣列。
老師看到「0 位學生的分數有變動」，然後不知道發生什麼事。

#### 還有沒有別的？

- **逐題手動給分**：不存在。`lib/scoring.ts:236-243` 明確保留了
  「有人手動給過分」的路徑（`row.earnedScore !== null` 時保留原分數），
  資料層準備好了，**但沒有任何 API 或畫面寫得進那個值**

- **重新匯入這一題、組新卷、重派**：學生要重考。
- **進資料庫**：`deploy/scripts/db-shell.sh` 存在，但那是主任跟廠商的事，
  不是週五下午能發生的事，而且要繞過 RLS。

### 花多久

走完四條死路：**約 15 分鐘**，其中死路三會讓人以為自己成功了。
真正修好：**做不到**。

### 嚴重度

**阻斷**。而且是全系統最貴的一個缺口，理由有三：

1. **它的發生機率接近 1。** 標準答案是 AI 從 PDF 抽出來的
   （`功能清單.md` §4），`answerOrigin` 這個欄位的存在就承認了這件事。
   一份 25 題的卷子抓錯一題不是意外。
2. **它影響全班而不是一個人。** 4 分乘 32 人。
3. **系統的 UI 三個地方向老師承諾了這個功能**：`/grades` 頁首的說明文字
   （`app/(app)/grades/page.tsx:122-126`）、`Regrade.tsx:116` 的範例、
   以及 `regradeAssignment` 的函式註解（`lib/scoring.ts:322-326`）。

### 修法建議

**這是下一版最該做的一件事。** 最小可行的形狀是一頁
`/bank/[questionId]`，只給科目授課老師，只能改四樣：
`answerKeys`、`answerSlots`、`answerText`、`scoringRule`，
每一次改動寫稽核（`category: 'QUESTION'`），並且在畫面上直接列出
「這一題被 N 份卷子用著、其中 M 份已經有人作答」，改完給一顆
「順便把那 M 份重新計分」。

在那之前，**至少要把死路三堵起來**：
`REVIEWABLE` 拿掉 `COMMITTED`，或者在校對介面上把已入庫的候選題
（`questionId != null`）標成唯讀並顯示「這一題已經在題庫裡，
在這裡改不會影響它」。現在的行為是**靜默地寫進一個不會被讀的地方**。

「老師還沒有開放這份考試的成績與檢討。」**答案當場收回去。**

明天孝班考完之後，再到 `/grades/[assignmentId]` 按「放行成績與檢討」
（`ReleaseControl`），兩班同時開放。而且 `/grades` 列表上會有
「待放行」的紅字提醒（`page.tsx:129-135`），忘不掉。

**但整條動線上沒有一個字提過這件事**：

- 派卷表單的 `releasePolicy` 下拉沒有任何關於「同一份卷子派給多個班」的警語。
- 忠班的成績頁不會說「這份卷子還有另外兩份任務沒考」。
  `attemptsOnPaper`（`lib/paper.ts:517-522`）算得出「這份卷子被哪些任務用著」，
  但它只被 `requireEditablePaper` 用來擋編輯，**沒有任何畫面顯示它**
  （`情境-出卷派卷.md` 卡點 24 記錄的是組卷頁那一側）。
- 15:00 那一刻是自動發生的，沒有通知、沒有待辦、沒有紅字。

### 花多久

**知道要做的話 1 分鐘。不知道的話 0 秒——而它已經漏了。**

### 嚴重度

**嚴重**。分兩班考同一份卷子是補習班的常態（教室不夠、班別不同）。
補救動作存在而且很便宜，但觸發它需要老師自己想到，而他剛監考完一場考試。

### 修法建議

在派卷表單與成績頁各加一道，都用現成的資料：

1. **派卷時**：選了卷子之後，如果 `attemptsOnPaper` 顯示這份卷子已經被
   其他任務用著，在 `releasePolicy` 那一格下面顯示
   「這份卷子還有 N 個任務（{班名}），最晚考到 {日期}。
   選『截止後開放』的話，這一班的答案會在 {本任務截止} 對他們公開。」
2. **首頁待辦**：加一項「有 N 份任務即將開放檢討，而同一份卷子還有班級沒考」。
   判定是一次 join：`assignment.dueAt` 已過／即將到 且 `releasePolicy = ON_DUE`
   且同 `paperId` 還有 `dueAt` 在未來的任務。

# 考試當天必備、但現在沒有的東西

依「當天出現機率 × 出事代價」排序。前三名的代價都是**成績本身是錯的**，
第四、五名的代價是**現場停擺**。

### 第 1 名：改標準答案 ＋ 全班送分

**機率**：接近 1。答案是 AI 從題本抽的，25 題抓錯一題是常態。
**代價**：全班 32 人、每人 4 分，而且改不掉。
**現在的狀態**：資料層完全就緒（`gradeAttemptById` 現查 `answerKeys`、
`lib/scoring.ts:236-243` 保留人工分數的路徑、重新計分的稽核完整），
**只差一頁編輯畫面**。而系統的 UI 在三個地方已經向老師承諾了它
（`/grades` 頁首、`Regrade.tsx:116` 的範例、`regradeAssignment` 的註解）。
**最小形狀**：`/bank/[questionId]`，只能改答案相關的四個欄位，寫稽核，
改完直接給一顆「重新計分受影響的 M 份」。加上 `ExamPaperItem.awardAll` 送分旗標。
**同時要做**：把 `REVIEWABLE` 裡的 `COMMITTED` 拿掉（狀況 12 的死路三），
它現在會讓老師以為自己改好了。

### 第 2 名：延長進行中的作答時間

**機率**：中高。熱點分享的網路，60 分鐘裡斷一次是可預期的。
**代價**：全班少 10 分鐘，而且完全沒有補救動作——32 人重考是唯一選項。
**現在的狀態**：`expiresAt` 全 repo 只寫一次（`lib/attempt.ts:418`），
之後沒有任何路徑改得動它。`timeLimitMin` 又被凍結。**兩層都堵死。**
**連帶的 bug**：`lib/assignment.ts:24-25` 宣稱「最常見的請求就是『再延一天』」，
而延長 `dueAt` **對已經開始作答的人沒有作用**；反過來「把截止改成現在」
也停不掉正在寫的人。這一條要一起修。
**最小形狀**：`Attempt.extraSeconds`，成績頁的「未完成的作答」上加一顆
「全部延長 N 分鐘」。或者更乾淨：讓到期時刻變成
`min(expiresAt, assignment.dueAt)` 的即時計算，不再是純快照。

### 第 3 名：一份任務的收件名單（＋ 任務內頁）

**機率**：高。「我沒收到」在每一場 30 人以上的考試裡幾乎都會出現一次。
**代價**：查不出來，而且會連帶讓狀況 10（找不到是哪一份卡住）與
狀況 3（分不清三個班的三份任務）都變慢。
**現在的狀態**：`resolveRecipients`（`lib/assignment.ts:440`）回的東西
**正好就是這一頁需要的形狀**——姓名、學號、`status`、透過哪幾個班收到、
是不是個別指定，連註解都寫著「`PENDING_CONSENT` 的學生登不進來，
畫面上要標出來」。它只有兩個呼叫端，而且畫面那一端把名單丟掉只留一個數字。
**最小形狀**：`/assignments/[assignmentId]`，三塊：設定、收件名單（含帳號狀態）、
每個人現在的作答狀態（進行中／已交／卡住／未開始）。這一頁一次解掉三個狀況。

### 第 4 名：科任老師打得開自己教的班的名冊

**機率**：高。開考前登不進去的學生每場都有。
**代價**：現場停擺 5–8 分鐘，而且要占用主任；主任不在就開不了考。
**現在的狀態**：兩支 API（重設密碼、登錄家長同意）**本來就允許 `TEACHER`**，
而且路由檔頭寫了理由（「要求他去找導師或管理員，等於這個功能在最需要的
那一刻不存在」）。擋住的是頁面層的 `ClassMembership` 檢查
（`app/(app)/classes/[classId]/page.tsx:49-55`），
而授課指派寫的是 `ClassSubjectTeacher`，兩張表對不上。
**最小形狀**：那一道檢查加上 `classSubjectTeacher.findFirst({ userId, classId })`，
與 `assignableClassIds`（`lib/assignment.ts:614-634`）同一個口徑。
順手加一欄「登入狀態」顯示 `lockedUntil`——被鎖的帳號現在在名冊上顯示「可登入」。

### 第 5 名：老師看得到單一學生的作答卷 ＋ 交卷時間

**機率**：中高。家長電話不一定當天來，但一週內一定來。
**代價**：說不出「他幾點交的、寫了哪幾題」，而系統其實全部記著。
**現在的狀態**：`Attempt.submittedAt` 已經被 `classStats` 查回來了
（`lib/scoring.ts:447`），只是沒放進 `scores` 的 map，所以全班表上沒有那一欄
——**這是一行的事**。逐題那一頁要多做一點，但 `loadAttemptResult`
（`lib/result.ts:199`）已經寫好了，只差把 `userId` 比對換成 `mayGrade`。
稽核記錄（`attempt.start` / `attempt.submit` / `auth.login`）全部有寫、
全部沒有畫面。
**附帶價值**：有了逐題畫面，`功能清單.md` §11-3（非選題沒有評分介面）
就只剩一個輸入框的距離，而 `lib/scoring.ts:236-243` 那條路徑已經在等它了。

## 名次外，但當天會被問到的四件小事

| 缺口 | 一句話 | 修法 |
|---|---|---|
| 成績頁不會自己更新 | 監考中要一直按 F5 才看得到誰交了 | 加一個 30 秒輪詢，或至少一顆「重新整理」 |
| 作廢後學生看到的是「已經交出去了」 | `saveAnswer`（`lib/attempt.ts:607-609`）沒有分開 VOIDED，而 `attemptVoid.mjs:75-77` 的註解斷言它有 | 分出 `err.conflict('VOIDED', …)` |
| 首頁與成績頁對「卡住」給相反答案 | 兩份 stranded 判定（`app/(app)/page.tsx:228-231` vs `lib/attemptClock.mjs:64-66`），`expiresAt = null` 時互相矛盾，錯誤訊息還叫老師去做他剛做過的事 | 讓 `attemptStranded` 吃 `dueAt / allowLate`，首頁改成呼叫它 |
| 延後截止會延後全班的檢討 | 為一個人補考，另外 31 個人多等一週。系統不說 | 改截止的對話框在 `ON_DUE` 時加一句警語，判定用現成的 `releaseControl` |

## 做得好的地方（重構時不要弄壞）

這一輪走查裡有四塊明顯是為了「考試當天」設計的，而且經得起現場：

- **作廢與撤銷作廢**（`lib/attemptVoid.mjs` ＋ `Void.tsx`）。允許 `IN_PROGRESS`
  （抓到作弊就是在考試中）、理由必填、不佔作答次數、可撤銷、確認視窗說得出
  「他還沒交卷，按下去等於當場終止他的考試」。狀況 7 與狀況 9 靠它。
- **版面快照**（`Attempt.layout`）。題序、選項順序、配分三樣鎖住，
  而這三樣正是改了會讓全班被誤判又完全沒有跡象的。
- **交卷與計分解耦**（`gradeOnSubmit` 包在 try 裡，`lib/attempt.ts:856-885`）。
  「沒算到分是看得見的，交卷失敗不是」——這句話決定了狀況 11 為什麼順。
- **`checkFinalizeOnBehalf` 只准收已經寫不進去的**（`lib/attemptClock.mjs:68-82`）。
  老師收不掉正在寫的考卷，這是對的，代價只是狀況 5 那一句灰字說得不夠。

## 附錄：判定方法

**「按得到嗎」怎麼判的。** 從 `app/(app)/**` 與 `components/**` 抓出所有
`fetch(`、`submitJson(` 與 server action 的呼叫端，逐一對回
`app/api/**/route.ts`；`lib` 有 export 但沒有走到畫面的一律不算。
特別對三支做了全 repo 的 word-boundary 搜尋確認呼叫端：
`resolveRecipients`（2 個，其中畫面那一端只取 `.length`）、
`revokeAllSessions`（0 個）、`getObject / signedGetUrl`（0 個）。

**「權限到不到得了」怎麼判的。** 對「監考的數學老師」這個具體身分
（`systemRole = 'TEACHER'`、有 `ClassSubjectTeacher(高三忠, 數學)`、
沒有 `ClassMembership`）逐頁跑一次 `mayUse` / `scopedPage` 的判定，
再對照該頁內部的第二道檢查。`/classes/[classId]` 就是這樣測出來的——
導覽列畫得出「班級」，列表是空的，內頁被擋。

**時間估計怎麼來的。** 點擊數是實際數頁面上的互動元素（含確認視窗的
兩次點擊與必填理由的輸入），沒有計網路延遲；「打電話找主任」那一項
按一次通話 3 分鐘加對方操作 2 分鐘估。

**`expiresAt` 只寫一次怎麼確認的。** `grep -rn "expiresAt"` 全 repo
（排除 `node_modules`、`.next`），30 個命中逐一分類：1 個寫入
（`lib/attempt.ts:418`）、7 個 select 宣告、其餘全部是讀取或註解。
`timeLimitMin` 的凍結另外從 `updateAssignment` 的 `guard()` 追到
`AssignmentTools` 沒有畫那個欄位。

**答案改不掉怎麼確認的。** `question.update` / `questionOption.*` 全 repo
搜過：正式程式碼只有 `lib/commit.ts:309`（寫 `qualityFlags`），
其餘全在 `tools/` 的測試夾具裡。再從 `commitJob` 的候選題查詢
（`where: { jobId, state: 'CONFIRMED', questionId: null }`，`lib/commit.ts:93-94`）
確認重新入庫撈不到已入庫的候選題，以及 commit 路由的 400 分支
（`route.ts:35-44`）確認按鈕按下去會失敗。
