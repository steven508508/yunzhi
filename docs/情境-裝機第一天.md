## 第 0 步：解開 tarball，先讀 README

`README.md` 是我唯一認得的入口。它寫得很好——第 9 到 41 行用一張表告訴我
這套系統現在做得到什麼、什麼還沒做，第 60 到 73 行「上線第一天會遇到的三件事」

### 卡點 1：一頁版部署文件叫你 `git checkout v0.20.0`　【阻斷】

**你看到什麼。** `docs/中午部署.md` 第 3 行寫「版本 **v0.20.0**｜2026-07-29」，
第 35 到 36 行的第一個指令是：

```bash
git clone <你的 repo> yunzhi && cd yunzhi
git checkout v0.20.0
```

**你會怎麼想。** 「文件寫 v0.20.0，那就 checkout v0.20.0，總不會錯。」

**實際上發生什麼。**

- `VERSION` 檔的內容是 `0.21.0`。
- `git tag -l` 有 `v0.20.0` 也有 `v0.21.0`，所以那一行 checkout **會成功**，
  不會有任何錯誤訊息。
- `README.md:5` 也寫「版本 **v0.20.0**（2026-07-29）」。`docs/UBUNTU.md:228`
  的驗證範例寫 `{"appVersion":"0.20.0"}`；`docs/UBUNTU.md:653`（升級一節）
  同樣叫你 `git checkout v0.20.0`。
- 而 `docs/功能清單.md:758-760` 明說：v0.20.0 的第 1、2、16 項
  （**沒有老師帳號與授課指派、沒有科目**、`/api/version` 打不通）
  是在 v0.21.0 才修好的。git log 的那個 commit 訊息就是
  「補上三個『裝起來就是死路』的缺口：科目、教職員帳號、授課老師」。

也就是說：照著一頁版做，我會裝出一個**沒有任何科目**的系統
（`/import/new` 的科目下拉是空的、`/papers` 按新增卷子直接失敗、
`/knowledge` 顯示「還沒有科目」），而畫面上沒有任何地方說得出原因。
`apps/web/lib/subjects.mjs` 的檔頭把這個後果寫得很清楚：
「整套系統開箱即無法使用，而畫面上沒有任何地方說得出原因。」

`tools/deploy-check.mjs` 有一項「VERSION 與最新的 git tag 一致」而且通過了——
它檢查的是 `VERSION` 對 tag，**沒有檢查文件裡寫的版本字串**。

**修法建議。**

1. `docs/中午部署.md:36` 與 `docs/UBUNTU.md:653` 的 `git checkout v0.20.0`
   改成 `git checkout "v$(cat VERSION)"`，或直接拿掉（`git clone` 預設就是最新）。
2. `README.md:5`、`docs/中午部署.md:3`、`docs/UBUNTU.md:228` 的版本字串更新。
3. 在 `tools/deploy-check.mjs` 加一項：掃 `README.md` 與 `docs/*.md` 裡的
   `v\d+\.\d+\.\d+`，任何一個大於或小於 `VERSION` 就失敗。這一項寫得出來，
   而且它擋的正是「照著文件做反而裝錯版本」。

我照 `README.md:81-88`：

```bash
cp .env.example .env
```

`gen-secrets.sh` 跑起來很清楚。實測產生六項：

### 卡點 2：三份文件三組不同的「.env 至少要改的六項」　【會出錯】

**你看到什麼。** 三份文件都有一節叫「至少要改的」，內容互不相同：

| 文件 | 位置 | 它說要改什麼 |
|---|---|---|
| `README.md` | 第 85 行 | `APP_DOMAIN`、`APP_URL`、`AI_*` |
| `docs/中午部署.md` | 第 55-66 行 | `APP_DOMAIN`、`APP_URL`、**`AUTH_SECRET`**、**`POSTGRES_PASSWORD`**、**`BACKUP_ENCRYPTION_KEY`**、`AI_*` |
| `docs/UBUNTU.md` | 第 134-143 行 | `APP_DOMAIN`、`APP_URL`、`TLS_MODE`、`ACME_EMAIL`、`BOOTSTRAP_ADMIN_EMAIL`、`AI_PROVIDER` |

**實際上發生什麼。**

`docs/中午部署.md:61-63` 叫我用 `openssl rand -base64 48` **自己產** `AUTH_SECRET`、
`POSTGRES_PASSWORD`、`BACKUP_ENCRYPTION_KEY`。這三個欄位在 `.env.example` 裡
全部標著 `[自動]`（第 86、125、249 行），而檔頭第 6 行寫著
「標示 `[自動]` 者由 `gen-secrets.sh` 產生，**不要手填**」。

更麻煩的是那一節的指令區塊（第 34-43 行）**完全沒有 `gen-secrets.sh`**：

```bash
cp .env.example .env
chmod 600 .env
$EDITOR .env
./deploy/scripts/docker-install.sh
```

照這個順序走，`REDIS_PASSWORD`、`S3_SECRET_KEY`、`GRAFANA_ADMIN_PASSWORD`、
`BOOTSTRAP_ADMIN_PASSWORD` 全是空的。系統救得回來（`docker-install.sh:64-70`
在 `.env` 已存在時會補跑一次 `gen-secrets.sh`），但那次補跑是
`>/dev/null`——見卡點 6。

**這是「我做錯了會怎樣」沒有答案的那一類**：我照著一頁版手填了 `AUTH_SECRET`，
系統照樣跑得起來，沒有人告訴我我用的是一個比 `gen-secrets.sh` 弱、
而且我自己記在便條紙上的字串。

**修法建議。** 讓 `.env.example` 成為唯一的真相來源：三份文件的「要改哪幾項」
全部刪掉，改成一句「跑 `./deploy/scripts/gen-secrets.sh --show`，它會列出還沒填的」，
然後把 `--show` 擴充成同時列出 `[必填]` 而尚未填、以及仍是 `.env.example` 範例值的欄位
（`tools/install-dryrun.sh:344-360` 已經有這段邏輯，抽出來共用即可）。

### 卡點 4：`AI_PROVIDER=mock` 是預設值，而畫面上沒有任何地方說　【會出錯】

**你看到什麼。** `.env.example:153` 的預設值是 `AI_PROVIDER=mock`。
`docs/UBUNTU.md:57-58` 說「一個 AI 服務的 API 金鑰。**第一次安裝可以先不用**」。

我的金鑰要等公司採購，那就先 mock 裝起來，反正之後改就好。

**實際上發生什麼。**

- `tools/install-dryrun.sh:415` 把它列成**提醒**（`!`）不是必須處理：
  「AI 功能會回傳假資料。驗證安裝可以，正式使用前要填真的金鑰。」
- `deploy/scripts/docker-install.sh:214-218` 同樣是 `warn`。
- `deploy/scripts/preflight.sh:427-428` 只在**不是** mock 而金鑰空著時才失敗。
- **`apps/web` 整包沒有任何一處出現 `AI_PROVIDER` 這個字串。**
  沒有橫幅、沒有標籤、`/import/new` 上不會說「你現在用的是假的」。

所以我上傳一份真的題本，管線會跑完，會產出結構完整的題目，而每一題的
`content` 是「這是 mock 讀出來的題幹，不是真的題目」（`apps/ai/providers.py:573`）。
唯一的線索是候選題的信心值（mock 給 0.5 或 0.1，見 `providers.py:655、677`），
低於 `Review.tsx:362` 的 `0.8` 門檻，所以側註會顯示
「AI_PROVIDER=mock，內容是假的，不可入庫」（`providers.py:590`）——
但那是一行擠在「校對者請注意」清單裡的字（`Review.tsx:456-467`），
而且**沒有任何東西擋住入庫**。

這是典型的「我會不會以為做完了但其實沒有」：整條動線綠燈跑完，
題庫裡有東西，卷子組得出來，考試派得出去，而題目是假的。

**修法建議。** 在 `apps/web/app/(app)/layout.tsx` 加一條全站橫幅：
`process.env.AI_PROVIDER === 'mock'` 時顯示「目前是安裝驗證模式，
AI 產出的題目與解析都是假資料，不要拿來考學生」。成本一行，
擋掉的是一整份假的考卷。次佳解：`lib/commit.ts` 在 mock 模式下拒絕入庫。

除非你自己接 exporter，否則不要開」。

### 卡點 6：初始管理員密碼的橫幅會被吞掉，之後還會印出一組假的　【會出錯】

**你看到什麼。** `gen-secrets.sh:149-157` 會印一個很醒目的方框：

```
════════════════════════════════════════════════════════
 初始管理員密碼（只會顯示這一次）
════════════════════════════════════════════════════════
   帳號：admin
   密碼：oRHeLkenmcE6RQp0
════════════════════════════════════════════════════════
 首次登入後系統會**強制**你更換密碼。
 更換之後，建議把 .env 中的 BOOTSTRAP_ADMIN_PASSWORD 清空。
```

**實際上發生什麼。三個問題疊在一起。**

**一、那個方框在最常見的路徑上看不到。**
`.env` 已經存在時（我照 README 先 `cp` 再手動跑過一次），
`docker-install.sh:68` 與 `ubuntu-install.sh:138` 呼叫的是
`gen-secrets.sh >/dev/null`——整個方框進了 `/dev/null`。
救回來的是安裝結尾的橫幅：`docker-install.sh:295` 說「密碼　見 .env 的
`BOOTSTRAP_ADMIN_PASSWORD`」，`ubuntu-install.sh:906` 直接把值印出來。
所以拿得到，但「只會顯示這一次」這句話從一開始就不成立——它一直躺在 `.env` 裡。

**二、照著建議清空之後，重跑安裝會產生一組沒有用的新密碼。**
`gen-secrets.sh:144-145` 的邏輯是「`BOOTSTRAP_ADMIN_PASSWORD` 是空的就產一組」。
我照著它第 156 行的建議清空之後，下一次為了改設定重跑
`docker-install.sh`（第 68 行，靜默），它會產生一組新的隨機密碼寫進 `.env`，
然後第 295 行的完成橫幅告訴我「密碼　見 .env 的 `BOOTSTRAP_ADMIN_PASSWORD`」。

那組密碼**不是任何帳號的密碼**。`migrate-and-seed.mjs:86-113` 只在
`admin` 帳號不存在時才用它建帳號；帳號已經存在就只印一行

### 卡點 13：名冊匯入的交易沒有設時限，而文件叫你一次匯 200 人　【會出錯，可能阻斷】

**你看到什麼。** 兩份文件對同一件事的說法相反：

- `README.md:62-63`：「名冊匯入**建議分班做**。……200 人大約要等一分鐘。」
- `docs/UBUNTU.md:546-551`：「**兩百人的名冊大約要等一分鐘，畫面會停著不動
  ——那是正常的。**……匯入路由的上限設在 5 分鐘，**兩百人有很大的餘裕**。」

而且 `docs/UBUNTU.md:552-555` 還特地安撫我：

> 如果你在 v0.20.0 之前試過匯入而失敗，錯誤是 `Transaction already closed`
> ——那是舊版的問題（超過約 16 人的名冊必定整份失敗），**這一版已經修掉**，
> 直接重匯即可。

**你會怎麼想。** 文件說兩百人有很大的餘裕、說那個錯誤已經修掉了。
那我當然一次匯 200 人——省得分 7 次。

**實際上發生什麼。**

那次修正修的是 **bcrypt**：`lib/roster.ts:366-419` 的 `mintPasswords`
把 200 次雜湊（每次 0.31 秒）搬到交易外面。這一段做對了，
註解也寫得很清楚。`maxDuration = 300`（`api/classes/[classId]/roster/route.ts:33`）
解決的是 HTTP 逾時。

**但交易本身還在，而且沒有設時限。**

```ts
// apps/web/lib/roster.ts:303
await prisma.$transaction(async (tx) => {
  for (const row of plan.rows) {
    let user = await tx.user.findFirst({ ... });     // 每一位一次
    if (!user) { user = await tx.user.create({ ... }); }  // 新生再一次
    await tx.classMembership.upsert({ ... });        // 每一位再一次
  }
});
```

- Prisma 互動式交易的**預設上限是 5 秒**，而全 repo 沒有任何一處設定
  `timeout` 或 `transactionOptions`——我用
  `grep -rn "timeout:\|maxWait" apps/web` 確認過，零命中。
  `lib/prisma.ts` 建構 `PrismaClient` 時也沒帶。
- 更要緊的是租戶隔離的成本：`lib/prismaClient.mjs:38-52` 把**每一次操作**
  都包成一個含三句 SQL 的批次（兩次 `set_config` ＋ 真正的查詢）。
  它自己的註解說「代價是每次查詢多一次往返」。

所以 200 位新生在這個迴圈裡是 200 × 3 個 Prisma 操作 = **約 600 次往返、
1800 句 SQL**，全部要在 5 秒內做完。30 人的班（約 270 句）大概沒問題；
200 人在忙碌的機器上不是。

而失敗的樣子是：`route.ts:79-84` 直接把 `e.message` 丟回前端，
`RosterImport.tsx:59` 原樣顯示。我會在畫面上看到一行英文
（`Transaction already closed: ...` 或 `Transaction API error`）——
**正是那份文件剛剛告訴我已經修掉的那一行**。

同一個結構也在 `resetClassPasswords`（`lib/roster.ts:639`）：
整班重設密碼，一位一次 `user.update` ＋ 一次 `session.deleteMany`。

**我沒有真的跑過 200 人的匯入**（這個沙箱沒有資料庫），所以我不能斷言
它一定失敗。但我能斷言三件事：交易沒有設 `timeout`、每個操作被放大成三句、
以及**文件正在鼓勵我做那件最危險的事並保證它安全**。

**修法建議。**

1. `lib/roster.ts:303` 與 `:639` 的 `$transaction` 加上第二個參數
   `{ timeout: 120_000, maxWait: 10_000 }`。一行。
2. 迴圈裡的三次查詢改成三次批次：先 `findMany` 把既有帳號一次撈出來、
   `createMany` 建新帳號、`createMany`＋`updateMany` 處理入班關係。
   往返從 600 次降到個位數。
3. `docs/UBUNTU.md:546-555` 與 `README.md:62-63` 統一。在修好 1 之前，
   兩邊都應該說「**分班匯入**」。
4. `route.ts:79-84` 對 Prisma 的原始錯誤做一次翻譯：訊息含
   `Transaction` 時改成「這份名冊太大，資料庫在寫到一半時逾時了，
   **整份都沒有匯入**。請分成每次 40 人以內再試。」
